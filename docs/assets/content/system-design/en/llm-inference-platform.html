An LLM inference platform serves large language models at scale: it turns a fleet of expensive GPUs into a low-latency, high-throughput API for chat, completion, and embeddings. This is a building-block design with an unusual bottleneck — the GPU — so the interesting decisions are about batching, memory (KV cache), parallelism, and scheduling, not just stateless web tiers. It is also the foundation the agentic and RAG systems build on.

The mental model that anchors a strong answer: a GPU is a fixed pool of compute and HBM memory, and your job is to keep it busy without blowing the memory budget. Almost every decision below — continuous batching, paged attention, parallelism — exists to push GPU utilization and tokens/sec up while keeping tail latency (TTFT/TPOT) bounded.

Clarifying questions (scope it first)

The right architecture depends heavily on the workload, so pin these down before designing:

  • Latency-sensitive chat or batch/offline? Interactive chat optimizes TTFT and streams tokens; batch (evals, embeddings, summarization) optimizes throughput and can tolerate queueing.
  • One model or many? A single hot model lets you pack GPUs tightly; many models (or LoRA adapters) need routing, multiplexing, and cold-start/load policy.
  • Model size vs GPU memory? Does the model fit on one GPU, or does it need tensor/pipeline parallelism across several? That changes the whole serving topology.
  • Context length and output length? Long contexts blow up the KV cache and cap concurrency; short prompts with long outputs are decode-bound.
  • Multi-tenant fairness needed? If yes, you need per-tenant quotas and a scheduler that prevents one big request from starving others.

Requirements

Functional

  • Serve chat / completion requests, with token streaming (server-sent events).
  • Serve multiple models and an embeddings endpoint.
  • Support function-calling passthrough and stop conditions / max tokens.

Non-functional

  • Low TTFT (time-to-first-token) and steady TPOT (time-per-output-token).
  • High throughput (tokens/sec) and high GPU utilization — GPUs are the cost.
  • Autoscaling under bursty load; graceful queueing.
  • Multi-tenant fairness and quota.

Why LLM serving is different

A request is not a single function call. Generation has two phases: a prefill that processes the whole prompt in one pass, then an autoregressive decode loop that emits one token per step, each step depending on all previous tokens. Two consequences drive the whole design:

  • A request occupies the GPU for many steps (one per output token), not one shot.
  • Each step must re-read the attention state of all prior tokens — cached in the KV cache, which dominates GPU memory.

Back-of-the-envelope estimation

Sizing for a 13B-parameter model on 40 GB GPUs:

  • Weights: 13B params × 2 bytes (FP16) ≈ 26 GB — fits one 40 GB GPU, leaving ~14 GB for KV cache.
  • KV cache: roughly ~0.5-1 MB per token for this model; a 2k-token context ≈ ~1-2 GB per request → only ~7-14 concurrent requests per GPU. KV cache, not compute, caps the batch.
  • Throughput: decode is ~30-50 tokens/s per sequence; batched, a GPU emits hundreds-to-thousands of tokens/s in aggregate.
  • Fleet: capacity is set by concurrent KV-cache budget and context length, not raw QPS — holding 1000 concurrent 2k-context chats needs on the order of ~70-140 GPUs.

Worked example. Take the 13B model on a 40 GB GPU: weights eat ~26 GB, leaving ~14 GB for KV cache. If one 2k-token request needs ~1.5 GB of KV, the GPU holds only ~9 concurrent requests — so the memory budget, not FLOPs, sets the batch size. Now suppose decode runs at ~40 tokens/s per sequence: with a batch of 9 the GPU emits ~360 tokens/s aggregate. To serve 1000 concurrent chats you need ~1000/9 ≈ 112 GPUs just for KV residency. This is why paged attention (no per-request contiguous reservation, ~4x less waste) and quantization (INT8/FP8 weights free up HBM for more KV) directly raise concurrency: every GB saved on weights or fragmentation becomes more requests in the batch. It also shows why a single 8k-context request is ~4x more expensive than a 2k one — long contexts are the real capacity killer.

Core APIs

  • POST /v1/chat/completions — {model, messages[], max_tokens, temperature, stream} → SSE stream of token deltas (or one full response).
  • POST /v1/completions — raw prompt completion.
  • POST /v1/embeddings — {model, input[]} → vectors.
  • GET /v1/models — list served models.
  • Streaming: Server-Sent Events; each event carries a token delta, terminated by a done marker.

High-level architecture

Request lifecycle and streaming

The gateway authenticates, enforces quota, and routes to a worker pool for the requested model. The worker runs prefill, then streams tokens out of the decode loop as they are produced — so the user sees the first token quickly (low TTFT) even though the full answer takes longer.

Continuous batching

GPUs are efficient only when work is batched. Naive "static" batching waits to collect a batch, runs it to completion, and only then accepts new requests — so a long request holds up short ones and the GPU idles at the tail. Continuous batching (a.k.a. in-flight batching) instead operates at the granularity of a single decode step: after every step, finished requests leave the batch and waiting requests join it. This keeps the GPU saturated and slashes queueing latency.

KV cache and paged attention

Each running request keeps a KV cache — the per-token attention keys/values — that grows by one entry per generated token. KV cache, not model weights, is usually the memory bottleneck and it caps how many requests fit in a batch. Classic allocators reserve a contiguous block for each request's max length, wasting memory. Paged attention borrows the OS virtual-memory idea: split the cache into fixed blocks and allocate them on demand via a block table, so memory is used only for tokens actually generated and can be shared (e.g. across beams or a common prompt prefix).

Parallelism for large models

A model too big for one GPU is split across several:

  • Tensor parallelism: shard each layer's matrices across GPUs that cooperate on every token (needs fast interconnect, e.g. NVLink).
  • Pipeline parallelism: place different layers on different GPUs and stream activations between stages.

These combine: tensor-parallel within a node, pipeline-parallel across nodes. The platform hides this behind the "worker" abstraction — one logical worker may be several GPUs.

Scheduling, autoscaling, and queueing

The scheduler balances two goals in tension: throughput (big batches) vs latency (don't make a request wait). It admits as many requests as KV-cache memory allows, prioritizes to protect TTFT, and applies per-tenant fairness. Because GPUs are scarce and slow to start (weights must load), autoscaling is coarse and queue-aware: scale on queue depth / GPU utilization with generous warmup, and shed or queue load gracefully at the limit.

Further optimizations

  • Prefix / prompt caching: reuse the KV cache for a shared system prompt across requests — big TTFT win for agents.
  • Speculative decoding: a small draft model proposes several tokens that the big model verifies in one step, raising tokens/sec.
  • Quantization: serve in INT8/FP8 to fit bigger models and more KV cache per GPU.
  • Multi-adapter (LoRA): serve many fine-tunes on one base model by swapping small adapters.

Storage & technology choices

  • API gateway (Envoy / NGINX / Kong): auth, API keys, per-tenant rate limiting and quotas, routing to the right model pool.
  • Serving runtime: the GPU workers run a real inference engine — vLLM (PagedAttention), NVIDIA TensorRT-LLM / Triton, or TGI — which implement continuous batching and the KV cache.
  • Model weights: large immutable files → blob/object storage (S3-like), pulled to local NVMe and mmap'd into GPU memory on warm-up; a model registry (metadata in PostgreSQL) tracks versions.
  • KV cache: lives in GPU HBM, not a database — it is ephemeral per request; prefix/prompt cache can be backed by Redis or a local store for reuse.
  • Queue: a fast in-memory/Redis queue (or the scheduler's own admission queue) holds requests waiting for batch slots.
  • Orchestration/autoscaling: Kubernetes + KEDA / a custom autoscaler driven by queue depth and GPU utilization.
  • Metrics/logs: Prometheus + Grafana for TTFT/TPOT/utilization; usage events flow over Kafka to analytics/billing consumers.
  • Usage ledger (billing source of truth): billing needs an idempotent durable record, not just a Kafka event — a usage ledger / billing event store keyed by request_id with the final token count, using upsert/finalize semantics so a worker crash, retry, or consumer replay can't double-count or undercount. Kafka transports the events; the ledger is the authoritative record invoices are built from.

Why these: weights are huge + write-once → object storage; KV cache is the latency-critical hot state → GPU memory (the scarce resource you size around). The token-generation hot path has deliberately no big relational DB on it — the bottleneck is GPU memory. Usage is split off that path: Kafka transports usage events, while the billing source of truth is the idempotent usage ledger, finalized at stream end (keyed by request_id), not in the per-token loop.

Consistency & guarantees

LLM serving has a different guarantee profile than a typical CRUD service:

  • Non-deterministic by default: with temperature > 0 the same prompt yields different outputs; reproducibility needs a fixed seed and greedy decoding, and even then floating-point/batching order can vary results slightly.
  • At-most-once generation: a request is not safe to blindly retry — a half-streamed response that fails should be restarted cleanly, not resumed mid-stream, and side-effecting tool calls must carry their own idempotency. Bill on tokens actually sent to the client, finalized idempotently in the usage ledger keyed by request_id so a crash or retry neither double-charges nor loses usage.
  • No cross-request transactions: each request is independent; the only shared state is the read-only weights and an optional prefix cache, which is a pure optimization (a miss just recomputes).
  • Fairness, not strict ordering: the scheduler guarantees quota/fairness across tenants, not FIFO — a short request may overtake a long one. Make that explicit rather than promising ordering.

When (not) to use a dedicated inference platform

  • Build it when: you serve your own/open models at scale, need cost control over GPUs, low/steady TTFT, multi-tenant quotas, or data-residency that rules out a third-party API.
  • Don't bother when: traffic is low or spiky and a hosted API (OpenAI/Anthropic/Bedrock) is cheaper than idle GPUs — managing GPU fleets is real operational cost.
  • Wrong framing when: the task is classic ML (ranking, small classifiers) — those don't need autoregressive decode infrastructure; or when latency needs are sub-10ms, which token-by-token generation cannot meet.

Pitfalls and talking points

  • KV cache is the limit: batch size is bounded by memory, not compute — size capacity by context length, not just QPS.
  • Long context blows up memory: a 100k-token prompt is a huge KV cache; isolate or rate-limit it.
  • Cold start: loading tens of GB of weights takes time — keep warm pools, never scale from zero under load.
  • Tail latency: one very long generation in a batch slows everyone's TPOT — cap max tokens, consider priority lanes.
  • TTFT vs throughput: bigger batches raise throughput but can hurt TTFT — tune admission, don't maximize batch blindly.

Key takeaways

  • LLM serving is GPU-bound and stateful per request (the KV cache), unlike a normal stateless web tier.
  • Continuous batching at the decode-step granularity keeps GPUs saturated and cuts latency.
  • Paged attention manages KV cache like OS paging — no over-reservation, shareable blocks.
  • Tensor + pipeline parallelism serve models bigger than one GPU.
  • Scheduling trades TTFT vs throughput; autoscaling must be warmup- and queue-aware.
