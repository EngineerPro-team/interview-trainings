Designing a chat system like Telegram is about moving small messages between hundreds of millions of devices with low latency, correct ordering, and seamless multi-device sync. This chapter builds a Telegram-style messenger from first principles: the connection layer, message storage and ordering, multi-device sync, group fanout, presence, and end-to-end encrypted secret chats.

The crux of chat design is two deceptively hard guarantees living on top of an otherwise simple "store-and-forward" system: per-chat ordering (every device sees the same message order) and multi-device sync (a message read on the phone shows as read on the laptop). The trick that makes both tractable is a per-chat monotonic sequence number — once each message has an authoritative position, ordering, dedup, and "what have I not seen yet" sync all reduce to comparing integers.

Clarifying questions (scope it first)

  • 1:1, small groups, or huge channels? A million-member broadcast channel is a different problem (shared log, pull) than a 1:1 chat (push) — clarify the largest group size.
  • Multi-device required? If one account spans phone + desktop + web, you need a server-side per-device sync cursor, not just per-user.
  • End-to-end encryption? If secret chats are E2E, the server can't read or fan out content — it only routes ciphertext between two devices (no multi-device, no server search).
  • Ordering strength? Per-chat total order is the usual answer; global ordering across chats is unnecessary and expensive.
  • Retention? Store-forever history vs ephemeral/expiring messages changes the storage and cost model.

Requirements

Functional

  • 1:1 and group chats with text and media.
  • Delivery and read receipts (sent, delivered, seen).
  • Multi-device sync — the same account stays consistent across phone, desktop, web.
  • Offline delivery — messages queued while a recipient is offline.
  • Presence (online / last seen) and typing indicators.
  • Secret chats with end-to-end encryption (device-to-device).

Non-functional

  • Low latency message delivery (tens of ms within a region).
  • Ordering — messages in a chat are seen in a consistent order on every device.
  • Durability — an acknowledged message is never lost.
  • Scale — 100M+ daily users, millions of concurrent connections.

Back-of-the-envelope estimation

  • Users: 100M DAU, ~40 messages sent/user/day → ~4B messages/day ≈ 46k writes/s average, ~5x peak ≈ 230k writes/s.
  • Storage: ~300 bytes/message (metadata + text) × 4B/day ≈ 1.2 TB/day; with 3x replication ≈ 3.6 TB/day (media goes to blob storage separately).
  • Connections: ~10-20M concurrent devices; at ~50k connections/gateway → ~200-400 gateways.
  • Fanout: a 1:1 chat is ~1 delivery, but a 100k-member channel turns one write into 100k reads — the reason large groups use a shared log.

Worked example. Take the fanout decision concretely. A 1:1 message is one write + one push — trivial. A 50-member group with push-on-write is 1 write → 50 deliveries; at 230k writes/s of group traffic that is millions of pushes/s, but still cheap because each member's "inbox" is just a pointer advance. Now a 1,000,000-member channel: push-on-write would mean 1 message → 1M inbox writes — a write amplification that melts the system and wastes work on the ~90% of members who are offline or never open it. So large channels flip to pull / shared log: the message is written once to the channel's log, and each client reads from its last-seen sequence number when it opens the chat. This is the classic fanout-on-write (small chats, low latency) vs fanout-on-read (huge channels, avoid amplification) split — the same trade-off as a social feed, decided per chat by membership size.

Core APIs

  • POST /sendMessage — {chat_id, client_msg_id, text | media_ref} → {seq, date} (client_msg_id makes the send idempotent).
  • GET /getUpdates — {pts, limit} → {updates[], new_pts} (multi-device sync).
  • GET /getHistory — {chat_id, from_seq, limit} → list of messages.
  • POST /markRead — {chat_id, up_to_seq}.
  • POST /sendTyping — {chat_id} (ephemeral, short TTL).
  • WebSocket events (server to client): new_message, read_receipt, presence.

High-level architecture

Clients hold a persistent connection (WebSocket / long-lived TCP) to a stateless gateway. The gateway forwards to a message service that persists into a per-chat store and fans out to recipients. A session registry tracks which gateway currently holds each device, so a message can be pushed to an online recipient; a push service handles the offline case.

Connection layer and sessions

Connections are stateful but the gateways are logically stateless: any gateway can serve any user, and the mapping "this device is connected to that gateway" lives in a shared session registry (e.g. Redis). When a device connects, the gateway registers it; when the message service needs to deliver, it looks up the gateway and forwards. A heartbeat keeps the entry fresh and detects dead connections.

Sending a message

Every message carries a client-generated id (idempotency key) so retries do not create duplicates. The subtle part is who assigns the order: under concurrent sends from multiple message-service instances, you need a single ordering authority per chat — a chat sequencer / partition owner (one owner per chat_id, or a log partitioned by chat_id with a single consumer, or a conditional counter via LWT). That owner dedups by client_msg_id, allocates the next monotonic seq, then persists to the durable message store before the sender is acked. A wide-column store alone (clustering by seq) only stores an already-assigned order — it does not safely allocate one under contention.

Storage and ordering

Once the sequencer has assigned each message a per-chat seq, messages are stored keyed by chat and ordered by that sequence number. A wide-column store (e.g. Cassandra) partitioned by chat_id with seq as the clustering key gives cheap appends and efficient "fetch the last N messages" / "fetch since seq" reads. The clustering key only sorts an order that already exists — it is not what allocates the order.

Multi-device sync

A Telegram account is cloud-based: messages live on the server, and every device reconciles to the same state. Each account keeps a global update sequence (Telegram calls it pts — "points"). A device stores the last pts it has seen; on reconnect it calls "give me updates since pts" and replays whatever it missed. New events advance pts, so devices converge no matter when they were last online.

Group chats

Two models, mirroring news-feed fanout:

  • Fanout on write (small groups): copy the message into each member's delivery path when sent. Fast reads, more write amplification.
  • Shared log (large groups / channels): store one copy in the group's message log; members read from it. Avoids huge write amplification for a channel with millions of subscribers.

Presence and typing

Presence is high-volume and low-value-per-event, so it is kept cheap: a device sends a periodic heartbeat; missing a few marks it offline ("last seen"). Typing indicators are ephemeral fan-out events with a short TTL — never persisted.

Secret chats (end-to-end encryption)

Normal "cloud chats" are encrypted in transit and at rest but the server can read them (needed for multi-device sync). Secret chats are end-to-end encrypted and bound to two devices: keys are derived with a Diffie-Hellman exchange, and the server only relays opaque ciphertext — it cannot read content and cannot sync the secret chat to other devices.

Storage & technology choices

Which datastore for which job is most of the design:

  • API gateway (Envoy / NGINX): auth, rate limiting, and routing for the REST/login surface, in front of the WebSocket gateways.
  • Connection gateways: stateful WebSocket servers; the device→gateway session registry is in Redis (TTL refreshed by heartbeats).
  • Ordering authority: a per-chat sequencer assigns the monotonic seq — a single partition owner per chat_id, or a log partitioned by chat_id (Kafka/Pulsar) with one consumer per partition, or a conditional counter row (LWT). This is the piece that makes ordering correct under concurrent sends; the message store does not allocate the order.
  • Messages: a wide-column store (Cassandra / ScyllaDB) partitioned by chat_id, clustered by seq — it stores messages in the order the sequencer already assigned: cheap appends, efficient "fetch since seq" range reads, horizontally scalable. This is the workhorse store, not the sequencer.
  • Account / contacts / settings: a relational DB (PostgreSQL) — modest size, relational, transactional.
  • Fanout / update stream: Kafka carries post-and-fanout events to gateways and the push service.
  • Media (photos, video, files): blob/object storage (S3-like) + CDN; the message only stores a reference, never the bytes.
  • Push to offline devices: APNs / FCM via a push service.

Why these: messages are append-heavy, per-chat ordered, and enormous in aggregate → a wide-column store beats a single relational DB; the presence/session map is hot + ephemeral → Redis; media is large + immutable → object storage + CDN; account data is small + relational → SQL. Secret-chat ciphertext is just opaque bytes the server relays and stores without keys.

Consistency & guarantees

  • Per-chat total order, not global: a per-chat sequencer (single owner per chat) allocates the monotonic seq after deduping the client message id, so every device renders the same order within a chat. The wide-column store keeps that order; it does not create it. There is no cross-chat ordering guarantee, and that's fine.
  • At-least-once delivery + idempotent apply: a message may be delivered more than once (retries, reconnect), so clients dedup by (chat_id, seq) / message id. Senders attach a client-generated id so a resend doesn't create a duplicate.
  • Durability before ack: a message is persisted (and replicated) before the sender gets "sent" — an acknowledged message is never lost, even if the recipient is offline for days (it's pulled by seq on reconnect).
  • Read-your-writes via sync cursor: each device tracks its last-applied seq; on reconnect it pulls everything after it, so multi-device stays consistent (read receipts and deletes propagate the same way).
  • E2E secret chats trade features for privacy: end-to-end encryption means no server-side fanout, search, or multi-device cloud history — the server only routes ciphertext between two specific devices.

When (not) to use this design

  • Fits: consumer/team messaging needing low latency, multi-device, history, and a mix of 1:1, groups, and large channels.
  • Simplify when: you only need 1:1 ephemeral chat (e.g. in-app support) — a single push channel without the wide-column log and channel/pull machinery may be enough.
  • Different design when: the product is really live broadcast to millions (use a feed/log + CDN), or it's an event bus between services (use Kafka directly) — chat semantics (per-recipient read state, presence) add cost you don't need there.

Scaling and pitfalls

  • Connection scaling: millions of persistent connections — shard across many stateless gateways; keep per-connection memory small.
  • Hot group / channel: a channel with millions of members must use the shared-log model and read fanout, not write fanout.
  • Ordering under retries: the client message id dedups; the per-chat sequence number gives a single source of truth for order.
  • Thundering herd on reconnect: after a network blip, many devices call getUpdates at once — bound the replay window and rate-limit.
  • Media: never push bytes through the message path — upload to blob storage / CDN and send a reference.

Key takeaways

  • Stateless gateways + a shared session registry decouple "who is connected where" from delivery.
  • A client message id (idempotency) plus a per-chat sequence number give dedup and a single ordering authority.
  • A per-account update sequence (pts) is the backbone of multi-device sync.
  • Large groups use a shared log + read fanout; small chats can fan out on write.
  • Secret chats trade multi-device sync for true end-to-end encryption.
