An AI coding agent platform (Cursor / Devin style) runs autonomous agents that edit code, run tests, and open pull requests — often many in parallel, in the background. The hard infrastructure problems are isolated sandboxes, durable agent runs, and safe Git operations at scale. It builds on the agentic platform and the LLM inference platform.

The distinguishing constraint versus a generic agent platform: the agent executes arbitrary, untrusted code (the repo's tests, build scripts, and whatever the model decides to run) against private source and credentials. So the design is dominated by two tensions — strong isolation (a hostile or buggy run must not escape the sandbox, exfiltrate secrets, or touch another tenant's repo) versus fast spin-up and cost (thousands of short-lived environments). Almost every choice (microVMs, warm pools, copy-on-write repos, egress proxy, secret broker) is a point on that trade-off.

Clarifying questions (scope it first)

  • Trust boundary? Does agent code run arbitrary commands and tests? (Yes → hard isolation: microVM, no ambient network, brokered secrets.)
  • Interactive or background? A user waiting in an editor cares about sub-second spin-up; background fleets optimize throughput and cost.
  • What side effects are allowed? Open a PR only, or also push, deploy, call external APIs? Each needs scoped tokens and audit.
  • Repo scale and language? Monorepo vs small repos changes clone/snapshot strategy and build-cache design.
  • Multi-tenant? Per-tenant isolation of sandboxes, secrets, caches, and egress is a security requirement, not an optimization.

Requirements

Functional

  • Submit a coding task against a repo; the agent edits code in a sandbox, runs tests, streams progress.
  • Produce a diff / open a pull request; resume an interrupted run.
  • Run many background agents concurrently.

Non-functional

  • Isolation / security — agent code must not escape its sandbox or leak secrets.
  • Fast sandbox spin-up; reliability; high concurrency; cost control.

Back-of-the-envelope estimation

  • Concurrency: thousands of concurrent runs, each owning a sandbox — pool and recycle environments, do not spin one per request cold.
  • Spin-up: a cold container is seconds; a microVM with a warm pool is sub-second — matters because users wait at the start.
  • Run length: minutes to tens of minutes, mostly waiting on the LLM and on tests — async orchestration, not held threads.
  • Repo size: snapshots/clones of large repos are heavy → cache base images and use copy-on-write workspaces.

Worked example. Suppose 5,000 concurrent runs, each needing a 2 GB repo + toolchain environment. Cloning a 2 GB repo fresh per run is ~10 TB of I/O and tens of seconds of latency each — untenable. With copy-on-write from a cached base snapshot, each run only stores its diff (tens of MB), so 5,000 runs cost ~hundreds of GB, not 10 TB, and start in well under a second. Spin-up math: a cold container/VM boot is ~2-10s; if users wait at the start, a warm pool of pre-booted sandboxes turns that into queue-pop latency (ms). Sizing the pool is a classic utilization trade — too small and users queue, too large and idle microVMs burn money — so the pool is autoscaled on demand with a small warm buffer. The scarce resources are sandbox memory/CPU and LLM tokens, not orchestrator throughput.

Core APIs

  • POST /tasks — {repo, branch, instruction} → {run_id} (async, background).
  • GET /runs/{id} → status, streamed logs, diff.
  • POST /runs/{id}/resume; POST /runs/{id}/pr — open a pull request.

High-level architecture

An orchestrator (durable, like the agentic platform) drives each run; a sandbox provisioner hands it an isolated environment from a warm pool; a repo service clones/snapshots code; the tool layer runs edits/shell/tests inside the sandbox; results stream out and an artifact service opens the PR.

Sandbox provisioning

Each run needs a clean, isolated environment where untrusted, model-driven commands can run. microVMs (or hardened containers) give strong isolation; a warm pool of pre-booted sandboxes with a cached base image makes start-up sub-second. The repo is materialized via copy-on-write so cloning a large repo is cheap.

Run lifecycle

The orchestrator runs the agent loop (plan-act-observe) where the tools are edit file, run shell, and run tests. Each step is checkpointed so a run survives restarts and can pause for review. Logs stream to the client throughout.

Tool execution and Git

Tools are scoped to the sandbox filesystem and a restricted shell; network and secrets are locked down. When the agent is done, the repo service turns the working changes into a branch + commit and opens a pull request through the Git provider — the agent never pushes directly with broad credentials; a scoped token does it.

Separate local sandbox side effects (file edits, test runs — cheap to redo) from external side effects (Git PR, package publish, network calls). External actions go through the artifact/approval service with a recorded idempotency key, so a crash-then-replay does not open two PRs or publish twice. A control plane wraps the sandbox: a secret broker injects scoped short-lived tokens only when approved, an egress proxy/allowlist restricts network, and an artifact scanner + audit log cover the output.

Storage & technology choices

  • API gateway: auth, per-tenant concurrency quotas, routing to the run orchestrator.
  • Orchestrator: a durable workflow engine (Temporal-style) so a background run survives restarts and resumes.
  • Sandboxes: a warm pool of Firecracker microVMs (or gVisor/Kata) — strong isolation, sub-second start; the repo is materialized via a copy-on-write overlay filesystem over a cached base image.
  • Run state & artifacts: PostgreSQL for run/step state; blob storage (S3-like) for diffs, logs, and build artifacts; Redis for warm-pool bookkeeping and live log fan-out.
  • Repo / Git: the Git provider (GitHub/GitLab API) for clone + PR; commits go through a secret broker (Vault)-issued scoped token; an egress proxy/allowlist gates network.
  • LLM: the LLM/agent gateway for model calls.
  • Audit trail (durable sink): because the actor is autonomous, every command/tool/external action must land in an append-only audit store designed to be audit-grade — an append-only Postgres table or an immutable object-storage log partitioned by run/date (optionally hash-chained), with retention/WORM and access control. Kafka is the fanout from the audit write to consumers, not the system of record by itself.

Why these: isolation is the whole game → microVMs + egress proxy + Vault, not a shared host; run state is small/structured → SQL; diffs/logs are large/append → object storage; the warm pool and streaming are hot/ephemeral → Redis. There is no big relational DB on the critical path — the scarce resources are sandbox slots and LLM tokens.

Consistency & guarantees

  • Resumable runs, idempotent external effects: in-sandbox work (edits, test runs) is cheap to redo on resume, but external actions — git push, opening/updating a PR, calling a deploy API — must be idempotent (e.g. push to a deterministic branch, upsert the PR) so a retry after a crash does not create duplicates.
  • Sandbox isolation is a hard guarantee: a run cannot reach the network except through the egress allowlist, cannot read another tenant's repo or secrets, and is destroyed after the run (no state leaks between runs).
  • Secrets are brokered, never resident: the sandbox gets short-lived, scoped tokens from the broker on demand; long-lived credentials never enter agent-controlled space, so a compromised run has a small, time-boxed blast radius.
  • Eventually-consistent with the Git provider: the PR/commit state is owned by GitHub/GitLab; the platform reconciles its view with webhooks/polling rather than assuming its local state is authoritative.
  • Auditability: every command, tool call, and external action is durably recorded in an append-only, audit-grade store (immutable, retained, access-controlled) — not merely emitted to a stream — because the actor is an autonomous agent and the audit trail must withstand disputes/security review.

When (not) to use this design

  • Use it when: you run untrusted/agent-generated code at scale, need per-run isolation and auditable Git side effects, and want background parallelism (many agents at once).
  • Overkill when: code is fully trusted and runs rarely — a plain CI runner or a single container is enough; you don't need microVMs and a warm pool.
  • Be careful when: agents can push/deploy to production — gate those behind human approval and scoped tokens; the failure mode (a wrong autonomous deploy) is far more expensive than a wrong suggestion.

Pitfalls and talking points

  • Sandbox escape is the top risk — strong isolation (microVM), no host access, locked-down network.
  • Cold start hurts UX — warm pools + cached base images + copy-on-write repos.
  • Secret leakage: never expose raw long-lived credentials inside the sandbox; use short-lived scoped tokens.
  • Runaway runs: step/time/cost limits; detect no-progress loops.
  • Concurrency limits: cap sandboxes per tenant; recycle aggressively.

Key takeaways

  • The platform pairs a durable run with an isolated sandbox from a warm pool.
  • Tools (edit/shell/test) run inside the sandbox; never on the host.
  • Copy-on-write repos + warm pools make start-up fast.
  • Commits go through a scoped token; a PR gates human review.
