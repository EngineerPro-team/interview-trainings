A Content Delivery Network (CDN) serves content from servers close to the user, cutting latency and offloading the origin. It is the building block behind streaming, large downloads, and fast web assets. The core problems are request routing, a cache hierarchy, and invalidation.

The whole value proposition is a single number — the edge cache hit ratio — because everything else (latency, origin load, cost) follows from it. So a strong design is really an argument about how to keep that ratio high (routing, hierarchy, cache-key hygiene) and how to stay correct when content changes (invalidation) without tanking it.

Clarifying questions (scope it first)

  • Static, dynamic, or both? Static assets cache for hours/days; dynamic/personalized content needs micro-TTL, edge compute, or must bypass cache — very different answers.
  • Public or private content? Private content forces signed URLs/cookies and access-aware cache keys so one user's response is never served to another.
  • How fresh must updates be? "Eventually (minutes)" → TTL; "instantly" → active purge or versioned URLs.
  • Object size profile? Many small web assets vs few huge video segments change eviction, tiering, and range-request handling.

Requirements

Functional

  • Cache and serve static (and some dynamic) content from edge locations.
  • Invalidate / purge content; origin shielding; TLS termination.
  • Signed URLs for access control.

Non-functional

  • Low global latency; high availability.
  • High cache hit ratio (protect the origin); huge egress bandwidth.

Back-of-the-envelope estimation

  • Hit ratio economics: a 95% edge hit ratio means the origin sees only 5% of traffic — the difference between one origin and a meltdown.
  • PoP count: hundreds of edge PoPs worldwide so most users are within tens of ms.
  • Object mix: a small set of hot objects serves most requests (cache them everywhere); a long tail is pulled on demand.
  • Egress: CDNs serve the majority of internet bytes — capacity is bandwidth at the edge, not compute.

Worked example — why hit ratio dominates. Say total demand is 10 Tbps. At a 95% edge hit ratio the origin only needs to serve ~5% = ~500 Gbps; push the ratio to 99% and the origin drops to ~100 Gbps — a 5× reduction in origin/transit cost from a 4-point ratio change. That is why a few percent of hit ratio is worth large engineering effort (better cache keys, shielding, pre-positioning), and why a cache-busting mistake (e.g. a per-user query param in the cache key) is catastrophic: it can collapse the ratio toward 0 and melt the origin.

Core APIs

  • GET /{asset} — served by the nearest edge (transparent to the client).
  • POST /purge — {url | tag} invalidate cached content.
  • Origin pull config: cache-control TTLs, cache keys, signed-URL rules.

High-level architecture

A client request is routed to a nearby edge PoP; on a miss the edge fetches from a regional shield, which in turn fetches from the origin — so the origin sees very little traffic. A control plane pushes config and purges across the network.

Request routing

Getting a user to a nearby healthy edge is the first job. Two common techniques:

  • Anycast: many PoPs announce the same IP; the network routes the user to the topologically nearest one. Simple, fast failover, less precise control.
  • GeoDNS: DNS returns a different edge IP based on the resolver's location / latency / health. More control, but DNS caching slows changes.

Cache hierarchy

A single tier would stampede the origin on misses. A hierarchy — edge then regional shield then origin — means many edges share a shield, so the origin sees one fetch per object per region, not per edge. Each tier applies cache keys, TTLs, and LRU eviction.

Private content and signed URLs

Not everything is public. For private content the edge verifies a signed URL or signed cookie (HMAC with an expiry) before serving, and the response is marked private/no-store or cached under an access-aware cache key — so a private object is never served to another user from cache. The cache key must include only access-safe dimensions; user-specific headers stay out unless the response is private.

Cache miss flow

Invalidation and purge

When content changes, stale cached copies must go. Options: TTL expiry (simple, eventual), or active purge that the control plane propagates to all PoPs (fast, more work). A purge goes to the control plane, fans out to every PoP, and is eventually consistent with acks/retries and a version/tag — so a global purge has latency and can partially fail, which is why versioned URLs (a content hash in the path) are preferred: a new version is a new URL, so caches never serve stale bytes and no purge is needed.

On a miss, the edge applies request coalescing (single-flight): many concurrent misses for the same object collapse into one upstream fetch, preventing a cache stampede on the shield/origin.

Storage & technology choices

A common confusion: "where does a CDN actually store data?" A CDN has no single database — it is a tiered cache in front of someone else's durable store. The data lives in several distinct layers, each chosen for its access pattern:

  • Edge cache (the data plane's storage): each PoP keeps cached objects in a tiered local store — hot objects in RAM, the larger warm set on SSD/NVMe — managed by the cache engine (Varnish / NGINX / Apache Traffic Server) with an LRU/LFU eviction policy. This is ephemeral and rebuildable: losing a PoP loses no data, just cache warmth.
  • Origin (the source of truth): the durable copy lives in blob/object storage (S3-like / GCS) for media and large files, or the application's own origin servers/DB for dynamic responses. The CDN never owns durability — it caches what the origin owns.
  • Cache index/metadata: an in-memory structure per edge mapping cache key → object location + TTL + ETag; this is the "do I have it and is it fresh?" lookup, not a persisted DB.
  • Config & routing state: cache rules, origin mappings, and PoP health are distributed to edges via a config store / control plane (etcd/Consul-style or a proprietary push system); GeoDNS/Anycast config drives routing.
  • TLS certificates: per-domain certs stored at the edge (and a secret store at the control plane) so PoPs can terminate HTTPS.
  • Logs & analytics: access logs stream off the edge into Kafka → a data warehouse / time-series store for hit-ratio, billing, and traffic analytics — kept off the request hot path.

The rest of the landscape: most teams buy a managed CDN (Cloudflare, Fastly, Akamai, AWS CloudFront, Google Cloud CDN) rather than build; self-hosting means running Varnish/NGINX/ATS at each PoP. For dynamic/personalized content, edge compute (Cloudflare Workers, Lambda@Edge, Fastly Compute) runs logic at the PoP. The origin/app sets Cache-Control and emits versioned URLs to control all of the above.

Consistency & guarantees

A CDN is fundamentally an eventually-consistent cache, and being explicit about that is the depth interviewers want:

  • Freshness is best-effort: until a TTL expires or a purge lands, an edge can serve a stale copy. If you need strict freshness, the answer is versioned URLs (new content = new URL), not faster purges.
  • Purge is eventually consistent: a global purge fans out with acks/retries and can partially fail; design for "most PoPs within seconds, a tail later", not instant global truth.
  • Read-your-writes does not hold across edges by default — a user who just uploaded may hit a different PoP with the old object; bind such reads to a versioned URL or bypass cache.
  • Routing is approximate: Anycast follows BGP (can land on a non-ideal PoP under network policy); GeoDNS depends on resolver location and is slowed by DNS caching. Neither guarantees the truly nearest PoP.

Tradeoffs & when not to use a CDN

  • Great for: static assets, media segments, large downloads, software updates, cacheable API responses — anything read far more than written.
  • Marginal for: highly personalized or rapidly-changing content (low hit ratio) — use micro-TTL + stale-while-revalidate or edge compute, or accept origin serving.
  • Wrong for: write paths and strongly-consistent reads — those go to the origin/DB, not a cache.

Pitfalls and talking points

  • Cache stampede / thundering herd: many misses for the same object hit the origin at once — use request coalescing at the edge.
  • Hot vs long tail: push hot objects everywhere; pull the tail on demand.
  • Cache key design: include only meaningful dimensions; a bad key (e.g. query order) fragments the cache.
  • Invalidation is hard: prefer versioned URLs to global purges where possible.
  • Dynamic content: cache micro-TTL or use edge compute; not everything is cacheable.

Key takeaways

  • Routing (Anycast / GeoDNS) gets users to a near, healthy edge.
  • A cache hierarchy (edge to shield to origin) protects the origin and raises hit ratio.
  • Invalidation via TTL, purge, or — best — versioned URLs.
  • Capacity is edge bandwidth and hit ratio, not origin compute — a few points of hit ratio move origin cost multiplicatively.
  • A CDN is an eventually-consistent cache: freshness is best-effort, purge is eventual — prefer versioned URLs for correctness.
  • Cache-key hygiene is the make-or-break detail: a per-user dimension in the key destroys the hit ratio.
