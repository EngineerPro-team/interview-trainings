Google Docs-style collaborative editing lets many people edit one document at once and always converge to the same result. The crux is conflict resolution for concurrent edits — Operational Transformation (OT) or CRDTs — plus per-document ordering, persistence, and presence.

The entire problem reduces to one guarantee: convergence — given the same set of edits in any delivery order, every client must end up with byte-identical document state. Concurrent edits to the same region are the hard case: if Alice inserts at position 5 while Bob deletes position 3, naive application diverges. OT and CRDTs are two answers to "how do we make concurrent ops commute." The good news is the scale is gentle (a doc has a handful of editors), so this is a correctness problem, not a throughput one — and the design centers on a per-document authority that orders and transforms ops.

Clarifying questions (scope it first)

  • How many concurrent editors per doc? A handful (typical docs) lets you funnel ops through one per-doc server; hundreds (a live shared whiteboard) needs more care.
  • OT or CRDT? OT (central server transforms) is simpler server-side and battle-tested for text; CRDTs enable serverless/P2P and offline merge at the cost of metadata — clarify if offline/P2P is required.
  • Offline editing? If clients edit offline and reconnect, you need to rebase a queue of local ops against the server — a major requirement, not a nicety.
  • Rich content? Plain text vs styled text, tables, images, comments — richer models complicate the op set and transforms.
  • History/audit? Full revision history and named versions change the persistence model (keep the op log + periodic snapshots).

Requirements

Functional

  • Multiple users edit the same document concurrently; everyone converges.
  • See others' cursors / presence; comments.
  • Version history; offline edits that sync on reconnect.
  • Sharing and permissions.

Non-functional

  • Low-latency convergence (edits appear in well under a second).
  • Consistency: all clients reach the same document state.
  • Scale per-document concurrency and total documents.

Back-of-the-envelope estimation

  • Edit rate: active typing is a few keystrokes/s per user; a 10-editor doc is tens of ops/s — small per doc, but there are millions of docs.
  • Op size: an op (insert char at position) is tiny (tens of bytes); the op log grows fast but compacts into snapshots.
  • Fan-out: each op broadcasts to the other N-1 editors of that doc — bounded by editors-per-doc, not global users.
  • Storage: snapshot + recent op log per doc; old ops compacted away after a snapshot.

Worked example. The numbers explain why the architecture is "one owner per doc, sharded by doc." Ten people typing is ~5 keystrokes/s each ≈ 50 ops/s on that document — nothing for a single server thread. So you can afford to route all ops for one doc to one authoritative server (or one partition), which assigns a monotonic revision number and transforms each incoming op against any it didn't yet know about. That serialization is what guarantees convergence, and it's cheap because per-doc traffic is tiny. Scale comes from sharding documents across servers (doc_id → owner), not from making one doc faster — a million active docs × 50 ops/s is 50M ops/s in aggregate, but each server only handles the docs it owns. Storage: at ~30 bytes/op and 50 ops/s, an hour of heavy editing is ~5 MB of ops; you snapshot periodically (e.g. every N ops) and compact, so open = load latest snapshot + replay the short op tail, keeping open latency bounded regardless of document age.

Core APIs

  • WebSocket session: open(doc_id) → snapshot + current revision.
  • submitOps(doc_id, base_revision, ops[]) → {applied_revision}.
  • Server pushes: remote_ops, cursor, presence.
  • GET /docs/{id}/history → revisions / snapshots.

High-level architecture

Each open document is owned by a single collaboration server (sharded by doc_id) that serializes all edits for that doc. Clients connect over WebSocket; the server transforms/merges ops, assigns a revision number, persists to an op log, and broadcasts.

Permissions: every open, submitOps, comment, and history request is authorized against the document ACL (view / comment / edit) before the collaboration server applies it — a viewer cannot submit edits even if it forges ops.

The concurrency problem

If A inserts "X" at position 2 while B deletes position 1 at the same time, naively applying both gives different results on each client. Two families of solutions guarantee convergence:

  • Operational Transformation (OT): transform an incoming op against concurrent ops so it applies correctly at its new position. Needs a central server to order ops; conceptually simple text model, tricky to implement correctly.
  • CRDT: give each character a unique, totally-ordered id so concurrent inserts/deletes commute — order of application no longer matters. More metadata per character, but converges without a central transformer (good for offline/peer-to-peer).

Per-document ordering

The simplest correct design: shard documents so one server owns each doc and applies edits in a single order, assigning a monotonically increasing revision. Clients submit ops against the revision they last saw; the server transforms against any ops it accepted in between, applies, and acks with the new revision.

Persistence: op log plus snapshots

The document state is the snapshot plus the ops applied after it. Persisting every op gives full history and crash recovery; periodically the server writes a snapshot and compacts older ops. On open, a client loads the latest snapshot then replays the tail of the op log.

Presence and offline

Cursors and selections are ephemeral presence events broadcast to co-editors (not persisted). Offline editing buffers ops locally; on reconnect the client submits them against its last known revision and the server transforms them in — the same mechanism as online edits, which is exactly why OT/CRDT matters.

Storage & technology choices

  • API gateway + WebSocket gateway: REST for open/share/history, a persistent WebSocket for the live edit stream.
  • Op log: the source of truth is a durable append-only op table / event store per document with permanent retention and snapshot compaction (replay by doc + revision, keep history). Kafka may mirror ops as a live change stream for fanout, but it is not the long-term source of truth (retention/replay are bounded).
  • Snapshots: periodic compacted document state in blob/object storage (S3-like), so open = load snapshot + replay tail.
  • Document metadata + permissions/ACL: a relational DB (PostgreSQL) — structured, transactional, the authority for sharing.
  • Presence/cursors: ephemeral → Redis (pub/sub + TTL), never persisted.
  • Comments / version history: a store keyed by doc + range/revision (Postgres or a wide-column store for very active docs).

Why these: the live document is hot in-memory on its owning collaboration server; durability is the append-only op log + periodic snapshots (logs are perfect for an ordered edit stream, blob for big snapshots); permissions are small + relational → SQL; cursors are throwaway → Redis. The single-owner-per-doc shard makes the "where is this doc's state" routing trivial.

Consistency & guarantees

  • Strong eventual consistency (convergence): the core guarantee — all clients that have received the same ops are byte-identical, regardless of order. OT/CRDT makes concurrent ops commute so there is exactly one converged state.
  • Per-document total order: the owning server assigns a monotonic revision per doc; clients transform local ops against the server's order before applying — there is one authoritative sequence per document.
  • Optimistic local apply + rebase: a client applies its own edit immediately (responsive UX) and later rebases it against the server revision; on offline reconnect, the queued local ops are transformed against everything that happened while away.
  • Durable, replayable history: an accepted op is appended to the durable op log before it is broadcast as committed, so the document can always be reconstructed (snapshot + op tail) and old versions restored.
  • Permissions are strongly enforced: the ACL is the authority — a client without edit rights cannot commit ops, checked server-side, not in the client.

When (not) to use this design

  • OT + central server when: real-time collaborative text with a handful-to-dozens of editors and a server you control — the proven, simpler path (Docs, most editors).
  • CRDTs when: you need offline-first, peer-to-peer, or serverless merge (local-first apps) and can afford the per-element metadata.
  • Overkill when: documents are edited by one person at a time — last-writer-wins with locking/check-out is far simpler than OT/CRDT.
  • Different design when: the "collaboration" is really high-frequency shared state (a game world, a cursor-heavy whiteboard with hundreds of users) — that may need a different replication/interest-management model than document OT.

Pitfalls and talking points

  • OT correctness is famously subtle — many edge cases; CRDTs trade that for per-char metadata.
  • Single-owner hotspot: a doc with thousands of editors stresses one server — cap editors or partition large docs.
  • Snapshot cadence: too rare means long replays; too frequent wastes storage.
  • Offline divergence: long offline edits produce big transform sets — bound and reconcile.
  • Undo must be per-user and transform-aware, not a naive global revert.

Key takeaways

  • Convergence needs OT (server-ordered transform) or CRDT (commutative ops).
  • A single owner per document gives a clean ordering and revision numbers.
  • Op log + periodic snapshot give history, recovery, and fast open.
  • Offline edits reuse the same transform path on reconnect.
