An agentic AI platform runs autonomous agents that plan, call tools, observe results, and iterate until a task is done. Unlike a single LLM call, an agent run is a long, stateful, multi-step workflow — so the design borrows from durable workflow engines: checkpointing, idempotent steps, tool sandboxing, memory, and guardrails. It sits on top of the LLM inference platform.

The framing that wins the interview: stop thinking "LLM call" and start thinking "durable distributed workflow whose steps happen to be non-deterministic and can have side effects in the real world." That reframing is what forces the hard requirements — every step must be checkpointed so a crash can resume, every tool call must be idempotent or guarded so a retry doesn't double-charge a customer, and every action must be sandboxed and policy-gated because the model is untrusted input deciding what to do.

Clarifying questions (scope it first)

  • What can tools actually do? Read-only (search, fetch) is low-risk; side-effecting (send email, move money, deploy) demands idempotency keys, approvals, and audit.
  • How autonomous? Fully autonomous, or human-in-the-loop approval gates before risky actions? That decides whether you need an approval/pause-resume state.
  • Run duration and resumability? Seconds vs hours-long runs decide whether state lives in memory or in a durable workflow store.
  • Multi-tenant isolation? Shared platform across tenants needs per-tenant memory, secrets, sandboxes, and quotas — a security boundary, not just config.
  • Cost/loop bounds? What stops an agent looping forever or burning unbounded tokens — step limits, token budgets, a supervisor?

Requirements

Functional

  • Define an agent with a set of tools; run a multi-step task (plan to act to observe).
  • Tool calling; short- and long-term memory.
  • Resume interrupted runs; human-in-the-loop approval; full trace.

Non-functional

  • Reliability: steps are idempotent and the run is resumable.
  • Cost control: token budgets and loop limits.
  • Safety: sandboxed tools, guardrails. Scale to many concurrent runs.

Back-of-the-envelope estimation

  • Run length: an agent run can be 10-100+ LLM calls over minutes to hours — far longer than one request, so state must be durable, not in memory.
  • Cost: each step sends the growing context to the LLM; a 50-step run with a 10k-token context can burn ~500k+ tokens — context management and budgets are essential.
  • Concurrency: thousands of concurrent runs, mostly waiting on LLM or tool I/O → an async, queue-driven orchestrator, not a thread per run.
  • Memory store: per-agent vector + key-value memory; reads on most steps.

Worked example. Suppose a run averages 30 steps and each step resends a context that grows from 2k to ~15k tokens; the integral is roughly 30 × ~8k ≈ 240k input tokens plus output — one run alone. At 10k concurrent runs that is millions of tokens/s of demand on the inference platform, which is why context management (summarize/trim old turns, keep tool results out of the prompt when possible) is not optional — it directly controls cost and the per-step latency (bigger context = slower prefill). Concurrency math: 10k runs each blocked ~5s on an LLM/tool call means the orchestrator is mostly waiting, so a thread-per-run model would need 10k threads; an async, event-driven orchestrator backed by a durable queue handles the same load on a handful of workers. The scarce resource is the LLM/GPU and external tool rate limits, not orchestrator CPU.

Core APIs

  • POST /agents — {name, system_prompt, tools[]} → {agent_id}.
  • POST /agents/{id}/runs — {task, budget} → {run_id} (async).
  • GET /runs/{id} → state, steps, trace; POST /runs/{id}/resume.
  • POST /runs/{id}/approve — human-in-the-loop gate.

High-level architecture

An orchestrator drives each run as a durable state machine: it calls the LLM gateway to decide the next action, executes tools in sandboxes, reads/writes memory, manages context, and records every step to a trace. Long-running runs live on a queue, not a held connection.

The agent loop

The core is a loop: the LLM plans the next action, the platform acts (calls a tool), feeds back the observation, and repeats until the goal is met or a limit is hit. Each iteration is one durable step.

Tool calling and sandboxing

Tools are how an agent affects the world (search, code execution, API calls). They must run in an isolated sandbox with resource limits and no access to secrets it should not have — a tool is untrusted code driven by a model. The orchestrator validates the model's tool request, runs it, and returns a structured observation.

Durable runs: checkpoint and resume

Because a run spans minutes/hours and many fallible calls, treat it like a durable workflow (Temporal-style). After each step, persist the run state (step index, context pointers, memory deltas). On crash, restart, or a human-approval pause, the orchestrator resumes from the last checkpoint.

Tool side-effect safety is the subtle part. A tool can create an external side effect (an API call, a payment, a PR) and then crash before the checkpoint is written — a naive replay would call it twice. So a tool step is itself a small state machine: Planned → ToolRequested (idempotency_key recorded) → ToolResultRecorded → Checkpointed. The orchestrator records the request before calling the tool, the tool is invoked with the idempotency key (or the orchestrator looks up an existing result), and only a recorded result advances the run. The trace/state store redacts secrets and is tenant-isolated; persist summarized context + pointers rather than raw prompts.

Memory and context management

The LLM context window is finite, but a long run accumulates history. The context manager keeps the prompt within budget: summarize old steps, and retrieve only relevant long-term memory (a vector store) for the current step. Short-term memory is the recent step history; long-term memory persists across runs.

Storage & technology choices

  • API gateway: auth, per-tenant quotas/token budgets, routing to the orchestrator.
  • Orchestrator: a durable workflow engine (Temporal / a custom state machine) so a multi-step run survives crashes and resumes from a checkpoint.
  • Run state & trace: step state in PostgreSQL (small, transactional, queryable); large step artifacts (tool outputs, logs) in blob storage; traces in the observability stack.
  • Memory: long-term in a vector store (Milvus / pgvector / Pinecone), short-term/working memory in Redis, both per-tenant namespaced.
  • Tools: executed in a sandbox (Firecracker microVM / gVisor / containers); a secret broker (Vault) injects scoped short-lived credentials.
  • Queue + LLM: Kafka / SQS for long-running run scheduling; the LLM gateway (the inference platform) for model calls; SSE/WebSocket for progress streaming.

Why these: the run is long and fallible → a durable workflow engine, not a request thread; structured run state → SQL, big artifacts → object storage; semantic memory → a vector store, hot working state → Redis; untrusted tool code → a sandbox + Vault-brokered secrets. The split mirrors the data shapes, not one database for everything.

Consistency & guarantees

  • Exactly-once intent, at-least-once execution: the workflow engine guarantees a step is not lost (it retries from the last checkpoint), so a side-effecting tool call must be idempotent (idempotency key) or guarded by a step state machine, otherwise a retry repeats the action.
  • Durable, resumable runs: after every step the run state is committed; a worker crash resumes from the last checkpoint, not from the start — the LLM call output is recorded so it is not re-sampled on resume.
  • Policy is a hard gate, model output is not trusted: the model proposes actions; an authorization/approval layer decides if they execute. Guardrails (allowlist, scopes, human approval) are enforced outside the model.
  • Non-deterministic steps, deterministic orchestration: the LLM is non-deterministic, but the orchestration (which step ran, its result, retries) is a deterministic, replayable log — that is what makes debugging and auditing possible.
  • Isolation: per-tenant memory, secrets, and sandboxes are isolated; one run cannot read another's state or credentials.

When (not) to use an agentic platform

  • Use it when: the task genuinely needs multi-step reasoning with tools (research, coding, ops automation), runs are long/resumable, and actions have real side effects that need audit and approval.
  • Overkill when: a single LLM call (or a fixed prompt chain) solves it — don't build a workflow engine for a one-shot classification or summarization.
  • Dangerous when: tools have irreversible side effects and you cannot make them idempotent or gate them with approvals — the cost of a wrong autonomous action outweighs the benefit. Start read-only, add write tools behind approvals.

Pitfalls and talking points

  • Infinite loops / runaway cost: enforce step limits and token budgets; detect repeated no-progress actions.
  • Tool safety: sandbox everything; never give a model raw credentials or unbounded access.
  • Context overflow: summarize + retrieve; do not dump the whole history each step.
  • Non-determinism: traces and idempotent steps make runs debuggable and resumable.
  • Multi-agent: an orchestrator-worker pattern (a planner delegating to sub-agents) scales complex tasks but multiplies cost.

Key takeaways

  • An agent run is a durable, multi-step workflow, not a single call.
  • The plan-act-observe loop with budgets and limits is the core.
  • Sandbox tools; the model is driving untrusted actions.
  • Checkpoint/resume + idempotent steps make long runs reliable.
  • Context management + memory keep prompts bounded and grounded.
