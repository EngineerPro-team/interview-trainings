A distributed search engine (web search / large-scale full-text search) answers keyword queries over billions of documents with ranked results in milliseconds. The core data structure is the inverted index; the core scaling pattern is sharding + scatter-gather; the core quality lever is ranking.

Search has a split personality: an offline indexing path (throughput-bound, can be eventually consistent) and an online query path (latency-bound, tail-sensitive). Keeping those two concerns separate — and being honest that search results are an approximate, ranked, eventually-fresh view, not a precise database query — is what makes the design coherent.

Clarifying questions (scope it first)

  • Web search or app/site search? Web scale means billions of docs + crawl; product/log search is smaller, more structured, and may need filters/facets.
  • Freshness requirement? "Seconds" (near-real-time, e.g. tweets) is very different from "hours" (web crawl) and changes the segment/refresh design.
  • Relevance bar? Simple BM25 keyword match vs ML learning-to-rank with behavioral features — the latter adds a feature/training pipeline.
  • Query shape? Pure keyword, boolean filters, faceting, typo-tolerance, autocomplete — each adds index structures.

Requirements

Functional

  • Ingest / crawl documents and index them.
  • Query by keywords; return ranked results; paginate.
  • Keep results reasonably fresh.

Non-functional

  • Low query latency (tens of ms) with good relevance.
  • Scale to billions of documents and high QPS.

Back-of-the-envelope estimation

  • Corpus: 10B documents; the inverted index is large (posting lists per term) — must be sharded across many machines.
  • Query: a query touches a few terms; with document sharding, every shard is queried and results merged → latency bounded by the slowest shard (tail).
  • QPS: tens of thousands of queries/s → replicate shards for read throughput; cache hot queries.
  • Index size vs RAM: keep hot posting lists in memory; compress posting lists aggressively.

Worked example — why tail latency is the enemy. With document sharding, a query fans out to every shard and waits for the last reply. If each shard answers in ~10 ms at p50 but ~80 ms at p99, then a 50-shard scatter-gather sees a p99 on some shard almost every request — so the overall latency tracks the slow tail, not the median. Mitigations stack: replicate each shard and send to the least-loaded replica, issue hedged requests (fire a backup to a second replica if the first is slow), and cap per-shard work (top-k only). This is why "just add shards" can make latency worse if you ignore the tail.

Core APIs

  • GET /search?q=&cursor= → {results[], next_cursor} (cursor / search_after on a stable sort, not offset page= — deep offset pagination is expensive and unstable across shards).
  • POST /index — {doc_id, text, metadata} (ingest).

High-level architecture

An indexing pipeline turns documents into an inverted index spread over shards (each replicated). A query service does scatter-gather: send the query to all shards, each returns its top candidates, then merge and rank.

The inverted index

An inverted index maps each term to a posting list of documents containing it (with positions and stats for ranking). A query intersects/unions the posting lists of its terms. Posting lists are compressed and, for hot terms, kept in memory.

Indexing pipeline

Ingestion tokenizes text (lowercase, stem, drop stopwords), then appends each token to its term's posting list in the right shard. Indexes are built as immutable segments that are periodically merged; new documents become searchable in near-real-time once their segment is published. Because segments are immutable, a delete or update does not rewrite them: the doc id is added to a tombstone / delete bitmap and filtered out of results; an update is a delete + a new version in a fresh segment. Background merge physically drops tombstoned docs and reclaims space.

Query: scatter-gather and ranking

With document sharding, each shard holds a slice of the corpus, so a query must hit every shard. Each shard returns its local top-k by a cheap score (e.g. BM25); the query service merges them and applies a heavier ranking (learning-to-rank using more features). Latency is bounded by the slowest shard, so tail latency control matters.

Storage & technology choices

The storage decision is which state is the durable index versus a derived/rebuildable structure, and how writes become visible:

  • Lucene segment files (the index, on SSD): the inverted index lives as immutable segments on local SSD per shard — writes create new segments, never mutate old ones, which is what makes reads lock-free and merges safe.
  • Translog + commit/refresh: a write-ahead translog makes a new doc durable before it's in a committed segment; a periodic refresh makes it searchable (near-real-time), and commit fsyncs segments — this is the freshness/durability knob.
  • Replicas per shard: each shard has replicas for availability and read scale; the primary orders writes, replicas follow.
  • Raw documents (source of truth): the original docs live in a blob/object store or source DB — the index is a derived, rebuildable structure, not the system of record.
  • Deletes/updates: a delete bitmap / tombstones mark docs gone; a background segment merge policy reclaims them and consolidates segments.
  • Query cache: hot query results cached before scatter; rebuildable.
  • Implementations: Lucene (library), Elasticsearch/OpenSearch (distributed), Solr, Vespa (search + ML + vectors), Typesense/Meilisearch (lightweight); pair with a vector index for hybrid semantic + keyword search (see RAG).

Consistency, freshness & guarantees

  • Eventually fresh: a newly indexed doc becomes searchable only after its segment is published and replicated — expect seconds (NRT) to minutes, not instant. State your target.
  • Ranked, not exact: results are a relevance-ordered approximation; with ANN/learning-to-rank there is no single "correct" result set, unlike a SQL query.
  • Pagination stability: use search_after on a stable sort key (e.g. score + doc id) so concurrent indexing does not shift pages; deep offset is both slow and unstable.
  • Best-effort completeness: under a shard failure you may return partial results (with a "degraded" flag) rather than fail the whole query — an availability/accuracy trade-off to call out.

Tradeoffs & when not to use it

  • Great for: full-text search, relevance ranking, faceted/typo-tolerant search over large corpora.
  • Wrong for: exact transactional lookups (use a database), strong consistency / read-your-writes, or analytics aggregations over huge ranges (use an OLAP store).
  • Cost lever: replicas for QPS/tail, compression + tiering for index size; relevance quality is a separate, ongoing investment (eval + LTR).

Pitfalls and talking points

  • Document vs term sharding: document sharding (every shard queried) is the common choice; term sharding concentrates hot terms — usually worse.
  • Tail latency: scatter-gather waits for the slowest shard — replicate, hedge requests, and cap per-shard work.
  • Index freshness: immutable segments + background merge give near-real-time without rewriting the whole index.
  • Hot queries: the query cache is checked before scatter and updated after merge; a small fraction of queries are most traffic.
  • Deletes/updates: immutable segments require a tombstone/delete bitmap + background merge — never rewrite a segment in place.
  • Pagination: use cursor / search_after on a stable sort, not deep offset.
  • Posting-list size: compress; keep hot lists in memory.

Key takeaways

  • The inverted index (term to posting list) is the core structure.
  • Document sharding + scatter-gather scales the corpus; tail latency is the enemy.
  • Immutable segments + merge give near-real-time indexing.
  • Cheap per-shard scoring then heavier ranking on the merged set.
  • Tame the tail: replicate shards, hedge requests, cap per-shard work — scatter-gather latency = the slowest shard.
  • Results are ranked + eventually fresh, not exact — say so, and use search_after for stable pagination.
