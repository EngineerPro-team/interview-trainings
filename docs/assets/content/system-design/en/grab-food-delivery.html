A food-delivery platform like Grab Food is a three-sided marketplace — eaters, merchants, and drivers — glued together by geospatial search, an order lifecycle, and real-time driver dispatch. This chapter designs it from first principles.

What makes this more than a CRUD app is the collision of two very different workloads: a correctness-critical order state machine (money, no double orders, no lost orders) sitting next to a high-volume, ephemeral location stream (hundreds of thousands of driver pings/s that are worthless a few seconds later). A strong answer keeps these on separate paths — durable, transactional storage for orders; in-memory geo indexes for location — and treats dispatch (assigning one driver to one order, exactly once) as the hard concurrency problem at the center.

Clarifying questions (scope it first)

  • Optimize for what? Fastest delivery, lowest cost, or driver utilization? The matching objective changes the dispatch algorithm.
  • Batching / pooled deliveries? Can one driver carry multiple orders? That turns dispatch into a routing/optimization problem, not 1:1.
  • Geographic scope? City-by-city (shard by region) vs one global system — delivery is inherently local, which simplifies sharding.
  • Who can be assigned an order? Drivers near the merchant (not the eater), available, and headed the right way — clarify the matching constraints.
  • Payment timing? Authorize at order, capture on delivery? This shapes the order saga and refund/compensation paths.

Requirements

Functional

  • Browse nearby restaurants; place an order.
  • Merchant accepts and prepares; a driver is assigned.
  • Live tracking of the driver; payment; ratings.

Non-functional

  • Low-latency nearby search and matching.
  • Reliable order state — no lost or double orders.
  • Real-time location updates; regional high availability.

Back-of-the-envelope estimation

  • Orders: 10M orders/day ≈ ~115 orders/s average, ~5x peak at meal times ≈ ~600/s.
  • Driver pings: 1M active drivers sending location every 4s → ~250k location writes/s — the heaviest stream; keep it in memory.
  • Search: nearby query must scan only a few geo cells, not the whole city — index by H3/geohash.
  • Storage: orders are small (~1 KB) and bounded; location is hot-but-ephemeral (TTL in a geo cache).

Worked example. The two workloads size completely differently. Orders: 10M/day ≈ 115/s average, ~600/s peak — tiny; this is the part that needs ACID transactions, a saga, and idempotency keys, and a sharded SQL store handles it comfortably. Location: 1M active drivers pinging every 4s = ~250k writes/s, each tiny and obsolete within seconds. Writing 250k/s into a durable DB would be absurd and pointless — so location lives in an in-memory geo index (e.g. Redis with H3/geohash cells), last-write-wins, with a TTL; you never replicate it for durability because a lost ping is replaced in 4 seconds. Search: a "restaurants near me" query reads only the viewer's H3 cell + neighbors (a handful of cells), so it scans dozens of candidates, not the city. The lesson the example teaches: match storage to the data's value and lifetime — durability where money is, throughput-and-forget where location is.

Core APIs

  • GET /restaurants?lat=&lng=&radius= → nearby restaurants.
  • POST /orders — {eater_id, restaurant_id, items[], payment} → {order_id, state}.
  • POST /orders/{id}/accept (merchant), POST /orders/{id}/assign (dispatch).
  • GET /orders/{id}/track → live driver location + ETA.
  • Driver stream: POST /drivers/{id}/location (high-frequency).

High-level architecture

Geospatial index

"Restaurants near me" and "drivers near this restaurant" both need fast radius queries. Indexing raw lat/lng is slow; instead map the globe into hierarchical cells (H3 hexagons or geohash). A point maps to a cell id; a radius query reads its cell plus neighboring cells. Drivers are bucketed into cells in an in-memory store keyed by cell id.

Order lifecycle (state machine)

An order is a state machine: each transition is validated and persisted, and external steps (payment, merchant accept) are wrapped so a failure cannot leave the order inconsistent. Idempotency keys on transitions make retries safe.

Dispatch and matching

When an order is ready to assign, dispatch queries the location service for nearby available drivers, scores them (distance, ETA, current load, direction), and offers the order. Matching is often batched over a short window so it can optimize globally (assign the set of orders to drivers that minimizes total wait) rather than greedily.

Live tracking

The driver app streams location to the location service; the eater app subscribes (WebSocket / long-poll) to the assigned driver's positions to draw the moving pin and recompute ETA. Raw pings stay in a hot geo cache with a TTL; only sparse waypoints are persisted for history.

Storage & technology choices

  • API gateway: auth, rate limiting, routing across eater/merchant/driver apps.
  • Restaurant search: Elasticsearch for text + filters, with an H3/geohash geo index for "near me".
  • Driver locations: Redis (geo commands / in-memory cell buckets) — the 250k pings/s hot, ephemeral stream; persist only sparse waypoints to a wide-column store.
  • Orders: the order state machine is a consistency boundary, so prefer PostgreSQL / sharded SQL (transactional, the booking saga + idempotency keys live here). A wide-column DB (Cassandra) works only if you make transitions safe explicitly — conditional writes/LWT, one writer per order, or event-sourced state — and is otherwise better kept for append-only trip/order history.
  • Events / dispatch: Kafka for order and location events; a stream processor (Flink) for real-time supply/demand and surge.
  • Payments: a dedicated payment service / PSP; blob storage for receipts/invoices.

Why these: driver location is a firehose that must never hit a disk DB → Redis geo; orders need ACID-ish state transitions → a transactional DB; search needs text + geo → Elasticsearch + H3; the analytics/surge layer is a stream → Kafka + Flink. The split is by access pattern: hot-ephemeral vs transactional vs search vs streaming.

Consistency & guarantees

  • Order state is strongly consistent: transitions (placed → accepted → assigned → picked up → delivered) go through one authoritative store with transactional/conditional updates, so an order is never in two states or processed twice.
  • Exactly-one driver per order: dispatch assigns a driver with an atomic conditional write (claim only if still unassigned) — the same single-winner pattern as a distributed lock — so two drivers can't both "win" the same order.
  • Idempotent payments via saga: the order/payment flow is a saga with idempotency keys and compensations; a retry after a timeout never double-charges, and a failed step rolls back (refund/void).
  • Best-effort, eventually-consistent location: driver positions are last-write-wins with TTL; a missed ping is simply replaced — there is no durability or ordering guarantee on location, by design.
  • At-least-once events: order/location events on Kafka are at-least-once; consumers (surge, analytics, tracking) must be idempotent.

When (not) to use this design

  • Fits: real-time, location-based marketplaces (food, groceries, courier) with a three-sided match and a money-carrying order lifecycle.
  • Simplify when: scheduled (non-real-time) delivery or a single region with low volume — you may not need an in-memory geo firehose or stream processors; a relational DB + periodic batch matching can suffice.
  • Different design when: there's no live location/dispatch (e.g. mail-order e-commerce) — that's a catalog + checkout + fulfillment problem, without the geospatial real-time core.

Pitfalls and talking points

  • Location write storm: 250k pings/s must not hit a database — in-memory geo cache, persist sparsely.
  • Hot zones: downtown at lunch is a hotspot cell — shard cells and cap per-cell work.
  • Order consistency: wrap payment + accept in a saga with idempotency keys; never double-charge.
  • Greedy vs batched matching: batching a short window yields better global assignments than first-come.
  • Boundary effects: a driver just across a cell edge — always search neighbor cells.

Key takeaways

  • A three-sided marketplace = search + order state machine + dispatch.
  • Hierarchical geo cells turn radius queries into key lookups.
  • The order is a validated state machine with saga-style compensations.
  • Driver location is hot and ephemeral — memory + TTL, persist sparsely.
  • Batched matching beats greedy assignment.
