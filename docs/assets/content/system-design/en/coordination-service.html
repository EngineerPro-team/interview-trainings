A coordination service (ZooKeeper / etcd style) is the building block other distributed systems lean on for leader election, distributed locks, configuration, and service discovery. Its whole value is being strongly consistent (and as available as a CP system can be) — which it achieves with a consensus algorithm like Raft.

The key mental model: this is the one place in your architecture that is allowed to be small, slow, and absolutely correct, so everything else can be large, fast, and loose. You deliberately trade throughput for linearizability and a single source of truth — which is why "don't put your data here, put your decisions here" is the framing that impresses.

Clarifying questions (scope it first)

  • What is it coordinating? Leader election, locks, config, service discovery, membership — each leans on the same primitives (CAS, watches, ephemeral keys + leases) but with different access patterns.
  • Read or write heavy? Reads can be scaled/relaxed (follower reads, read-index); writes are bounded by consensus and should stay rare.
  • Linearizable reads required? If stale reads are acceptable, follower reads are far cheaper; if not, reads must go through the leader / read-index.
  • Failure model? How many simultaneous node failures must it survive — this sets the cluster size (3/5/7) and the quorum.

Requirements

Functional

  • A small key-value store with watches (notify on change).
  • Distributed lock and leader election.
  • Ephemeral entries tied to a session (auto-removed on disconnect).

Non-functional

  • Strong consistency (linearizable reads/writes).
  • Availability under the CAP CP tradeoff — survives a minority of node failures, but on a partition the minority side is unavailable (it favors consistency over availability). Not "always available".
  • Durability; modest but predictable latency.

Back-of-the-envelope estimation

  • Cluster size: 3, 5, or 7 nodes — odd, to form a majority quorum; tolerates floor(N/2) failures.
  • Write throughput: every write goes through consensus (replicated + majority ack), so it is modest (thousands/s), not millions — this is a coordination store, not a data store.
  • Read: can be served from the leader (linearizable) or replicas (faster, possibly stale) depending on guarantee.
  • Data size: small — config, locks, membership — keep it in memory with a replicated log on disk.

Worked example — why writes are bounded. Every write must be appended to the leader's log, replicated, and acked by a majority before commit. On a 5-node cluster that is at least one fsync + a network round-trip to 2 more nodes per write, so a single Raft group realistically commits on the order of a few thousand writes/s — fine for "elect a leader" or "update this config", catastrophic if you treat it as a database and write per user request. If you genuinely need more write throughput, you shard into multiple independent Raft groups (etcd/ZooKeeper are not meant to be sharded data stores) — which is the cue that you are using the wrong tool.

Core APIs

  • put(key, value), get(key), delete(key).
  • watch(key) → events on change.
  • lock(key) / unlock(key) with a lease.
  • create_ephemeral(key) — removed when the session ends.

High-level architecture

A small cluster of nodes runs a consensus protocol. One node is the leader; clients send writes to it, the leader replicates them through a replicated log to followers, and a write commits once a majority has it. The committed log is applied to an in-memory state machine (the key-value tree).

Consensus and leader election

Raft makes the cluster agree on an ordered log despite failures. Nodes elect a leader by majority vote for a term; the leader handles all writes and replicates them. If the leader dies, followers time out and elect a new one. Because entries commit only with a majority, a split network cannot produce two committing leaders (no split-brain).

Log replication

Distributed lock with lease and fencing

A lock is just a key that one client holds. Crucially it carries a lease (so a crashed holder's lock auto-expires) and a fencing token — a monotonically increasing number handed out with the lock. Downstream systems reject operations carrying an old token, so a paused-then-resumed old holder cannot corrupt state. Locks without fencing are unsafe.

Watches and sessions

Clients watch keys to be notified of changes (e.g. config update, new leader) instead of polling. Watches carry a revision so a client can resume "from revision X" after a reconnect and not miss events; if a watched history was compacted away, the server signals a re-sync. Ephemeral keys are tied to a client session kept alive by heartbeats; when the session ends, its ephemeral keys vanish — the mechanism behind presence and leader election (the leader holds an ephemeral key). The API also offers compare-and-swap / versioned writes and lease grant + keepalive.

Storage & technology choices

The storage decision here is about what is authoritative and how it is made durable — a coordination service stores small, critical decisions, not bulk data:

  • Replicated consensus log (source of truth): the durable, replicated Raft/ZAB log of state changes is the authority; every write is committed by a quorum before ack. Periodic snapshots compact it so recovery isn't a full replay.
  • In-memory KV state (MVCC projection): the current key space is held in memory (a tree/MVCC store), rebuilt from log + snapshot on restart — fast reads, but derived from the log, not a separate source of truth.
  • Leases / session table: client sessions and lease expiries are tracked so locks auto-release on client death (TTL + heartbeat); this is what makes locks safe.
  • Watch / revision history: a monotonic global revision per change lets clients watch and resume from a revision; old revisions are compacted.
  • Local disk with fsync: each node fsyncs the log to local disk; values are deliberately small (KB), not a blob store — large values do not belong here.
  • Implementations: etcd (Raft, behind Kubernetes), ZooKeeper (ZAB; Kafka/Hadoop/HBase), Consul (KV + discovery + health), Google Chubby (the original). Almost every system here uses one for leader election, config, and locks.

When (not) to use a coordination service

  • Great for: leader election, distributed locks with fencing, dynamic config, service discovery/membership, small amounts of critical metadata — low write volume, high correctness.
  • Wrong for: a general database or high-throughput store (writes are consensus-bound), large blobs, or anything where availability must beat consistency on a partition.
  • A cheaper alternative for plain best-effort locking is a Redis lease with a fencing token — but it is not linearizable, so use the coordination service when correctness under partition actually matters.

Pitfalls and talking points

  • Not a data store: writes go through consensus — keep it small and low-throughput.
  • Locks need fencing: a lease alone is unsafe under GC pauses / network delays.
  • Cluster size: odd numbers (3/5/7); more nodes means more durable but slower writes.
  • Linearizable reads cost: reading from the leader (or via read-index) is correct; replica reads can be stale.
  • Watch storms: one change can notify many watchers — debounce / batch.

Key takeaways

  • A coordination service trades throughput for strong consistency via consensus (Raft).
  • Leader election + log replication with a majority quorum avoids split-brain.
  • Locks need a lease and a fencing token to be safe.
  • Watches + ephemeral sessions power discovery, config, and presence.
  • Put decisions here, not data: it is intentionally small/slow/correct so the rest of the system can be large/fast/loose — wrong tool for a high-throughput store.
