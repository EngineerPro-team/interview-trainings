A flight-booking system has a read-heavy search problem (millions browsing) wrapped around a strict-consistency booking problem (a seat must never be sold twice). This chapter designs search caching, the seat hold, and a booking saga across inventory and payment.

The defining shape is two systems with opposite needs glued together: a massively read-heavy search (cacheable, eventually consistent, optimize for QPS) and a tiny but strict booking core (a seat is a unique resource sold at most once, spanning inventory + payment, must be idempotent). The bridge between "I saw this price" and "I bought it" is the seat hold with a TTL — a temporary reservation that turns a race into a two-phase "reserve, then pay" so the user isn't charged for a seat someone else grabbed. Getting the hold and the booking saga right is the whole game.

Clarifying questions (scope it first)

  • Single airline or aggregator (GDS)? Owning inventory is a consistency problem you control; aggregating third-party inventory adds external availability calls and stale-price handling.
  • Hold semantics? How long is a seat held during checkout, and what happens on expiry? This defines the TTL and the release path.
  • Multi-leg / multi-passenger? Booking several seats/legs atomically (all-or-nothing) is harder than one seat — clarify atomicity scope.
  • Payment timing? Authorize then capture (the clean flow given a hold) vs charge upfront — shapes the saga and compensation.
  • Search freshness? Can results be cached for seconds/minutes, or must price/availability be live at search time?

Requirements

Functional

  • Search flights (incl. multi-leg) by route and date.
  • Hold a seat while the user pays; then confirm the booking.
  • Cancel / refund; look up a booking by reference (PNR).

Non-functional

  • Consistency: a seat is sold at most once (no double-booking).
  • Read scalability: search QPS dwarfs booking QPS.
  • Idempotent booking under retries; high availability.

Back-of-the-envelope estimation

  • Read:write skew: ~1000 searches per booking — optimize the read path hard (cache, read replicas).
  • Search QPS: 100M searches/day ≈ ~1.2k/s average, large peaks; results are cacheable for seconds.
  • Inventory contention: a popular flight has limited seats; holds + conditional updates serialize the few writes that matter.
  • Storage: bookings are small and durable; search data is derived and cacheable.

Worked example. The ~1000:1 read:write skew is the design driver. 100M searches/day ≈ 1.2k/s (with large peaks), but only ~100k bookings/day ≈ ~1/s of actual writes. So you pour effort into the read path — cache fare/availability results for a few seconds, serve from read replicas, precompute popular routes — because that's where the volume is, and slightly stale search results are acceptable (the hold step re-validates). The write path is tiny but must be exactly right: a popular flight has, say, 180 seats, and at peak dozens of users may try to book the last few at once. You don't lock the whole flight; you do a conditional decrement ("reserve seat only if available count > 0") or a per-seat conditional claim, which serializes just the contended seats. The hold gives the user a TTL window (e.g. 10 minutes) to pay; if the seat count is decremented at hold time, an expired/abandoned hold must release the seat back — otherwise inventory silently leaks. The numbers justify the architecture: optimize reads broadly, guard the rare writes strictly.

Core APIs

  • GET /search?from=&to=&date= → {itineraries[]} (cacheable).
  • POST /holds — {flight_id, seat_class, user_id} → {hold_id, expires_at}.
  • POST /bookings — {hold_id, passenger, payment, idempotency_key} → {pnr, status}.
  • GET /bookings/{pnr}, POST /bookings/{pnr}/cancel.

High-level architecture

Search path

Search is read-heavy and tolerant of slight staleness. Serve it from a cache (route+date keyed, short TTL) backed by read replicas; precompute popular routes. Availability shown in search is a hint — the authoritative check happens at hold time.

Seat hold with TTL

To avoid two users paying for the same seat, the user first holds it: a conditional update marks the seat reserved with an expiry. If they pay in time, the hold becomes a booking; if not, the hold auto-expires and the seat returns to inventory. The hold is the consistency boundary.

Booking saga

Confirming a booking touches two systems that can each fail: inventory (convert hold to sold) and payment. Because a hold already exists, the clean flow is authorize the payment (reserve funds), commit the seat, then capture — so the common path never charges then refunds. A saga sequences them with an idempotency key so retries are safe; a void/refund is only the fallback compensation if commit fails after authorization.

Booking lifecycle

Storage & technology choices

  • API gateway: auth, rate limiting, routing for search vs booking.
  • Search: a Redis cache (route+date keyed, short TTL) in front of read replicas of the fare/schedule DB; popular routes precomputed.
  • Inventory: a transactional DB (PostgreSQL) holding seats with a conditional hold + TTL; a background sweeper releases expired holds.
  • Booking: a saga orchestrator (workflow engine) coordinating inventory + payment with an idempotency key; the PNR record in a relational store.
  • Events: Kafka for booking/cancellation events → notifications, analytics, downstream GDS sync.
  • Payments: a PSP integration; emails/itineraries to a notification service.

Why these: search is read-heavy and tolerates staleness → cache + replicas; the seat hold is the consistency boundary and must be strongly consistent → a transactional DB with conditional writes; the cross-system booking is a saga → a workflow engine + idempotency keys. The read path and the write path deliberately use different consistency models.

Consistency & guarantees

  • A seat is sold at most once: the conditional hold/booking on the inventory DB is the single source of truth — search availability is only a hint, and a booking is rejected if the conditional reserve fails.
  • Hold = bounded, auto-releasing reservation: a hold has a TTL; if the user doesn't pay in time, a sweeper releases the seat, so abandoned checkouts can't permanently leak inventory.
  • Idempotent booking via saga: the booking is keyed by an idempotency key so a client retry returns the same result, not a second booking; the authorize → commit → capture saga has compensations (void/refund) for partial failure.
  • Eventually-consistent search: cached fares/availability may be seconds stale — explicitly acceptable because the hold step re-validates against the authoritative inventory.
  • Durable confirmation: once a PNR is issued, it is durable and authoritative; downstream systems (GDS, notifications) sync from booking events, eventually consistent.

When (not) to use this design

  • Fits: any reserve-limited-inventory-then-pay flow — flights, hotels, event tickets, car rental — where overselling is unacceptable and search dwarfs booking.
  • Simplify when: inventory is effectively unlimited (digital goods) — you don't need holds or conditional reserves, just an idempotent purchase.
  • Different design when: demand massively exceeds a tiny supply at an instant (a flash ticket drop) — you may add a virtual waiting room / queue in front so the booking core isn't stampeded, on top of this hold model.

Pitfalls and talking points

  • Double-book: never trust search availability — the conditional hold is the single source of truth.
  • Orphaned holds: always set a TTL and have a sweeper release expired holds.
  • Idempotency: a retried POST /bookings with the same key must return the original result, not charge twice.
  • Multi-leg / multi-airline: a saga spanning several inventories — partial holds need compensation.
  • Cache staleness: fine for search; never for the hold/booking step.

Key takeaways

  • Separate the read-heavy search (cache + replicas) from the strict booking path.
  • The seat hold with TTL is the consistency boundary that prevents double-booking.
  • Booking is a saga with compensations and an idempotency key.
  • Availability in search is a hint; the conditional hold is authoritative.
