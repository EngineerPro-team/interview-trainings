Blob (object) storage like Amazon S3 stores arbitrary bytes under a bucket/key name with extreme durability at exabyte scale. This building-block design covers the write/read path, replication vs erasure coding, metadata sharding, multipart upload, and garbage collection.

The defining insight is to separate metadata from data and treat them as two different problems: metadata is small, numerous, and needs fast indexed lookup; data is huge, immutable, and needs cheap durable bytes. Almost every design decision (sharding, durability scheme, consistency) follows from that split, so a strong answer keeps the two planes distinct throughout.

Clarifying questions (scope it first)

  • Object size profile? Mostly small objects (KB) stresses metadata and per-object overhead; large media (GB-TB) stresses the data path and needs multipart + chunking.
  • Read/write/delete mix and hot vs cold? Hot read-heavy data wants replication; cold archival data wants erasure coding for cost.
  • Consistency expectation? Read-after-write for new objects is standard; what about overwrites and list-after-write (often weaker)?
  • Durability/availability target? "11 nines" durability and the regional/AZ failure model drive the replication/EC and placement choices.

Requirements

Functional

  • PUT / GET / DELETE an object; LIST a bucket.
  • Multipart upload for large objects; versioning; presigned URLs.

Non-functional

  • Durability ~11 nines; high availability.
  • Scale to exabytes and trillions of objects.
  • Read-after-write consistency for new objects.

Back-of-the-envelope estimation

  • Durability math: with a ~0.8% annual disk failure rate, 3 replicas give ~6 nines; erasure coding (e.g. 8+4) reaches ~11 nines — the reason EC is preferred for cold data.
  • Storage overhead: 3x replication = 200% overhead; 8+4 erasure coding = 50% overhead — big cost difference at exabyte scale.
  • Metadata: trillions of objects × ~1 KB metadata = petabytes of metadata alone — it must be sharded.
  • Object size spread: from tiny (KB) to huge (TB) — pack small objects into larger files; split big ones into chunks.

Worked example — replication vs erasure coding cost. To store 1 EB of usable data: 3× replication needs ~3 EB of raw disk (200% overhead) but any single copy serves a read with low latency. 8+4 erasure coding needs ~1.5 EB raw (50% overhead) — that is half the hardware at exabyte scale, i.e. enormous savings — but a read may have to fetch and decode k=8 shards (more IO + CPU + tail latency), and a single lost shard triggers a reconstruction read across 8 nodes. The rule of thumb that falls out: replication for hot/latency-sensitive data, erasure coding for cold/cost-sensitive data, and re-encode replicated objects to EC as they cool.

Core APIs

  • PUT /{bucket}/{key} — body is the object → {etag, version_id}.
  • GET /{bucket}/{key} → object bytes.
  • DELETE /{bucket}/{key}; GET /{bucket}?list&prefix= → keys.
  • Multipart: POST .../uploads (init), PUT part, POST complete.

High-level architecture

Separate metadata from data so each scales independently: a stateless API tier, a sharded metadata service (key to location), and data nodes that store the actual bytes as append-only chunks.

Write path

On PUT, the API picks a placement group, writes the bytes to several data nodes, waits for a write quorum to acknowledge durably, then commits the metadata entry. Read-after-write holds because metadata is committed only after data is durable.

Replication vs erasure coding

Two ways to survive disk failures:

  • Replication: keep N full copies. Simple, fast recovery, low read latency — but high storage cost (3x = 200% overhead).
  • Erasure coding: split an object into k data shards plus m parity shards (e.g. 8+4); any k of the k+m can reconstruct it. Much cheaper (50% overhead for 8+4) and more durable — but reconstruction reads several shards, adding latency.

Rule of thumb: replication for hot/latency-sensitive data, erasure coding for cold/cost-sensitive data.

Metadata sharding and listing

Metadata (key to location, size, version) is itself huge, so it is sharded — commonly by a hash of bucket+key. That makes point lookups O(1) but makes LIST prefix hard (keys are scattered). A common fix: keep a separate, range-partitioned index ordered by key for listing, accepting that listing is eventually consistent and slower than a GET.

Multipart upload

Uploading a 5 TB object in one request is fragile. Multipart upload splits it into parts uploaded independently (and in parallel); on complete, the service stitches the parts into one logical object. A failed part is retried alone, not the whole upload.

Garbage collection and lifecycle

Deletes and overwrites leave orphaned chunks; a garbage collector reclaims space not referenced by any live metadata entry (mark-and-sweep). A lifecycle manager tiers cold objects to cheaper storage (e.g. Glacier) and can re-encode replicated data to erasure coding as it cools.

Storage & technology choices

  • Managed: AWS S3, Google Cloud Storage, Azure Blob, Cloudflare R2 — the default for most teams.
  • Self-hosted: MinIO (S3-compatible), Ceph, SeaweedFS; Facebook's Haystack/f4 are the classic in-house designs.
  • Metadata layer: often a sharded relational/KV store (e.g. FoundationDB, DynamoDB, or sharded Postgres) — separate from the data nodes.
  • Pairs with: a CDN in front for read-heavy media, and lifecycle tiering to a cold class (Glacier) for archives.

Consistency & guarantees

  • Read-after-write for new objects: achieved by committing metadata only after the data write quorum is durable — a GET after a 200 always resolves. (Modern S3 made this strong for all operations; older systems were eventual.)
  • Overwrites / deletes are trickier: with versioning, a PUT creates a new version and the metadata pointer flips atomically; without it, concurrent overwrites need last-writer-wins or conditional writes (If-Match on etag).
  • Listing is often weaker than point reads: the key-ordered index is updated asynchronously, so a just-written key may appear in LIST slightly later.
  • Durability is independent of availability: 11 nines durability (you won't lose bytes) does not mean 11 nines availability (you might briefly not be able to read them during a failure) — state both targets separately.

Tradeoffs & when not to use object storage

  • Great for: large immutable blobs — media, backups, logs, ML datasets, static assets (often fronted by a CDN).
  • Wrong for: small mutable records with low latency (use a database/KV), append-in-place or partial in-place edits (objects are immutable — you rewrite), or strong cross-object transactions.
  • Cost lever: lifecycle-tier cold objects to cheaper classes and re-encode to EC; most cost is storage-months, not requests.

Pitfalls and talking points

  • Metadata is the bottleneck at object scale — shard it; it is petabytes on its own.
  • Listing is expensive with hash sharding — keep a separate ordered index.
  • Small-object overhead: pack many small objects into large append-only files to avoid per-object cost.
  • EC reconstruction cost: reading cold data may touch several shards — fine for cold, not for hot.
  • Read-after-write: commit metadata only after a durable write quorum.

Key takeaways

  • Separate metadata from data; shard both.
  • Replication for hot data, erasure coding for cold — durability vs cost.
  • Commit metadata after a write quorum for read-after-write.
  • Multipart upload + GC + lifecycle tiering handle scale and cost.
  • State the guarantees: read-after-write for new objects (metadata committed after a durable data quorum); listing is often weaker; durability ≠ availability.
  • Objects are immutable — model updates as new versions/overwrites, not in-place edits.
