Retrieval-Augmented Generation (RAG) grounds an LLM in your own data: retrieve the most relevant passages for a question, then have the model answer using them (with citations). The design is two pipelines — an offline ingestion/indexing path and an online retrieval + generation path — plus a vector index for similarity search.

The core insight for an interview: RAG turns "the model doesn't know my data / hallucinates" into a retrieval problem. Answer quality is bounded by what you retrieve — if the right passage isn't in the top-k, no prompt engineering saves the answer. So most of the design effort goes into recall, ranking, freshness, and access control, not the generation call itself.

Clarifying questions (scope it first)

  • What corpus and how fresh? Static docs (re-index nightly) vs constantly changing data (incremental, near-real-time indexing) change the ingestion design completely.
  • Private/multi-tenant data? If answers must respect per-user permissions, ACL filtering belongs inside retrieval — a correctness and security requirement, not an add-on.
  • Latency vs quality budget? Can you afford a reranker and/or multi-step retrieval, or is this a tight sub-200ms path?
  • Citations / groundedness required? If the answer must be auditable, every chunk needs stable source metadata and the answer must cite it.
  • Corpus scale? Millions vs billions of chunks decides flat vs sharded ANN and whether you quantize.

Requirements

Functional

  • Ingest documents (chunk, embed, index).
  • Answer a query with grounded text and citations.
  • Incremental updates as documents change.

Non-functional

  • Low retrieval latency; good recall and precision.
  • Freshness of the index; scale to billions of vectors.

Back-of-the-envelope estimation

  • Corpus: 10M documents × ~10 chunks each = 100M chunks → 100M embedding vectors.
  • Vector size: 100M × 768 dims × 4 bytes ≈ ~300 GB of raw vectors → shard across nodes; compress with quantization (PQ).
  • Query latency: exact nearest-neighbor over 100M vectors is too slow → approximate (ANN) index returns top-k in milliseconds.
  • Ingestion cost: embedding 100M chunks is a big one-time GPU job; re-embedding on model change is the expensive part.

Worked example. 100M chunks at 768-dim FP32 is ~300 GB of vectors. An HNSW graph adds roughly the same order of magnitude in graph links, so plan for memory on the order of hundreds of GB — which forces either sharding across nodes or quantization. Product quantization (PQ) can compress each 768-dim vector from ~3 KB to ~100-200 bytes (~15-30x), bringing 300 GB down to ~10-20 GB at the cost of some recall — the classic recall/memory trade. On the write side, embedding 100M chunks at, say, ~1k chunks/s on a GPU pool is ~28 hours of one-time compute; the painful part is that changing the embedding model re-embeds the entire corpus, so model version is a first-class part of the index (you version and rebuild, you don't mix embedding spaces).

Core APIs

  • POST /ingest — {doc_id, content} → chunked, embedded, indexed.
  • POST /query — {question, top_k} → {answer, citations[]}.
  • POST /search — {query, top_k} → raw retrieved chunks (no generation).

High-level architecture

The ingestion pipeline turns documents into indexed vectors; the query path retrieves, reranks, builds a prompt, and calls the LLM gateway. A vector store plus a keyword index back retrieval.

Ingestion pipeline

Documents are chunked (split into passages sized for retrieval and the context window), each chunk is turned into an embedding by an embedding model, and the vectors are written to the index with their source metadata (for citations). Chunking strategy matters: too big dilutes relevance, too small loses context.

The vector index (ANN)

Exact nearest-neighbor over 100M+ vectors is too slow, so RAG uses approximate nearest neighbor (ANN). Two common families:

  • HNSW (graph): builds a navigable small-world graph; excellent recall and latency, higher memory.
  • IVF-PQ (inverted file + product quantization): clusters vectors and compresses them; lower memory, tunable recall/latency.

The trade-off is the classic recall vs latency vs memory triangle; pick per corpus size and SLA.

Query path: hybrid retrieval and rerank

Vector search captures meaning; keyword search (BM25) captures exact terms (names, codes). Hybrid retrieval runs both and merges, then a reranker (a cross-encoder) reorders the merged candidates by true relevance to the query. The top passages become the LLM's context.

Access control

RAG over private data must respect permissions: each chunk carries tenant + ACL labels (and a source_uri) from ingestion, and the ACL is pushed into the retrieval query itself — a metadata filter on the vector/keyword search (or over-fetch then filter before merge) — not applied after top-k. Filtering after a global top-k is both a security risk (forbidden chunks reach the app layer) and a recall bug (the top-k can be entirely chunks the user cannot see, leaving nothing after the filter). Filtering inside the query keeps recall correct and the model never sees forbidden context.

Freshness and evaluation

Documents change, so ingestion is incremental and versioned: an indexing job writes a new document version, atomically swaps the active version, tombstones stale chunks, and a background compaction reclaims them. Each chunk keeps a stable chunk_id, doc_version, and embedding_model_version so re-embeds and deletes propagate cleanly. Citations carry doc_id, chunk_id, source_uri, title, span, and version. Quality is measured with an eval loop — retrieval recall and answer groundedness (is the answer supported by the citations, not hallucinated?) over a golden set plus online feedback.

Storage & technology choices

  • API gateway: auth + rate limiting in front of the query and ingest endpoints.
  • Vector store: a purpose-built ANN store — FAISS (library), Milvus / Qdrant / Weaviate (services), pgvector (Postgres extension), or Pinecone (managed). HNSW or IVF-PQ under the hood.
  • Keyword index: Elasticsearch / OpenSearch (BM25) for the lexical half of hybrid retrieval.
  • Raw documents + chunks: originals in blob/object storage (S3-like); chunk text + metadata + ACL labels in a relational/KV store (PostgreSQL / DynamoDB).
  • Ingestion pipeline: Kafka for the document-change stream, a batch/stream processor (Spark / Flink) to chunk + embed at scale, and an embedding model served on GPUs (Triton / vLLM).
  • Reranker: a cross-encoder model service; LLM gateway for generation; Redis to cache hot query results / embeddings.

Why these: the storage choice follows the access pattern — semantic similarity → a vector index (not a B-tree); exact-term match → an inverted index; large immutable source files → object storage; small structured metadata + permissions → a relational/KV store; the high-volume ingest/reindex job → Kafka + a batch engine. No single database does all four well, so RAG is deliberately polyglot.

Consistency & guarantees

  • Eventually fresh, not transactional: there is a lag between a document changing and the index reflecting it (re-chunk → re-embed → publish). State the freshness SLA; don't promise read-after-write on the corpus.
  • Best-effort recall, not exact: ANN returns approximate top-k — tune recall vs latency, and use hybrid (vector + keyword) so exact-term matches aren't missed by the embedding.
  • ACL is a hard guarantee: the permission filter is enforced inside retrieval, so a user can never be shown (or cited) a chunk they cannot access — even at the cost of recall.
  • Groundedness, not truth: RAG guarantees the answer is built from retrieved passages with citations; it does not guarantee the source is correct. Surface citations so a human can verify.
  • Versioned index: within one query, retrieval reads a consistent index version; an embedding-model change triggers a full rebuild into a new version, swapped atomically (tombstones for deletes in between).

When (not) to use RAG

  • Great for: question-answering over private/changing knowledge, reducing hallucination, and any answer that must cite sources — without retraining the model.
  • Overkill for: small, static knowledge that simply fits in the prompt (just put it in context), or pure reasoning/transform tasks that don't need external facts.
  • Wrong tool for: questions needing aggregation/joins over structured data (use SQL/analytics, optionally as a tool the model calls), or when the source of truth changes faster than you can index and strict freshness is required.

Pitfalls and talking points

  • Chunking is underrated: bad chunk boundaries wreck recall — tune size and overlap.
  • Vector-only misses exact terms: add keyword/hybrid retrieval and a reranker.
  • Stale index: support incremental upsert/delete; full re-embed only on model change.
  • Permission leakage: filter by ACL/tenant before rerank and generation; never let a forbidden chunk reach the model or a citation.
  • Vector storage overhead: raw vectors undercount real memory — HNSW graph links, metadata, chunk text, tombstones/versions, and replicas multiply it; IVF-PQ compresses at a recall cost.
  • Hallucination: instruct the model to answer only from context and cite; evaluate groundedness.
  • Cost of re-embedding the whole corpus on an embedding-model upgrade — plan migrations.

Key takeaways

  • RAG = offline chunk-embed-index + online retrieve-rerank-generate.
  • ANN (HNSW / IVF-PQ) makes similarity search fast at scale; tune recall vs latency vs memory.
  • Hybrid retrieval + reranking beats pure vector search.
  • Support incremental indexing and measure groundedness.
