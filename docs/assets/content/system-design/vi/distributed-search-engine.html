Một distributed search engine (web search / full-text search quy mô lớn) trả lời keyword query trên hàng tỷ document với ranked result trong millisecond. Cấu trúc dữ liệu cốt lõi là inverted index; pattern scale cốt lõi là sharding + scatter-gather; đòn bẩy chất lượng cốt lõi là ranking.

Search có hai tính cách: một path indexing offline (throughput-bound, có thể eventually consistent) và một path query online (latency-bound, nhạy tail). Giữ hai mối quan tâm đó tách biệt — và thành thật rằng kết quả search là một view xấp xỉ, đã rank, eventually-fresh, không phải một query database chính xác — là điều làm thiết kế mạch lạc.

Clarifying questions (chốt scope trước)

  • Web search hay app/site search? Web scale nghĩa hàng tỷ doc + crawl; product/log search nhỏ hơn, có cấu trúc hơn, và có thể cần filter/facet.
  • Yêu cầu freshness? "Giây" (near-real-time, vd tweet) rất khác "giờ" (web crawl) và đổi thiết kế segment/refresh.
  • Bar relevance? BM25 keyword đơn giản vs ML learning-to-rank với behavioral feature — cái sau thêm feature/training pipeline.
  • Query shape? Keyword thuần, boolean filter, faceting, typo-tolerance, autocomplete — mỗi cái thêm index structure.

Requirements

Functional

  • Ingest / crawl document và index chúng.
  • Query theo keyword; trả về ranked result; paginate.
  • Giữ result đủ fresh.

Non-functional

  • Query latency thấp (vài chục ms) với relevance tốt.
  • Scale tới hàng tỷ document và QPS cao.

Back-of-the-envelope estimation

  • Corpus: 10B document; inverted index lớn (posting list mỗi term) — phải shard ra nhiều máy.
  • Query: một query đụng vài term; với document sharding, mọi shard bị query và result merge → latency bị chặn bởi shard chậm nhất (tail).
  • QPS: hàng chục nghìn query/s → replicate shard cho read throughput; cache hot query.
  • Index size vs RAM: giữ hot posting list trong memory; nén posting list quyết liệt.

Ví dụ có số — vì sao tail latency là kẻ thù. Với document sharding, một query fanout tới mọi shard và chờ reply cuối cùng. Nếu mỗi shard trả ~10 ms ở p50 nhưng ~80 ms ở p99, thì một scatter-gather 50 shard gặp p99 ở một shard nào đó gần như mỗi request — nên latency tổng bám theo tail chậm, không phải median. Mitigation chồng lên: replicate mỗi shard và gửi tới replica ít tải nhất, dùng hedged request (bắn backup tới replica thứ hai nếu cái đầu chậm), và cap công việc per-shard (chỉ top-k). Đó là lý do "cứ thêm shard" có thể làm latency tệ hơn nếu bỏ qua tail.

Core APIs

  • GET /search?q=&cursor= → {results[], next_cursor} (cursor / search_after trên một stable sort, không offset page= — deep offset pagination đắt và không ổn định giữa các shard).
  • POST /index — {doc_id, text, metadata} (ingest).

High-level architecture

Một indexing pipeline biến document thành một inverted index trải trên các shard (mỗi cái replicated). Query service làm scatter-gather: gửi query tới mọi shard, mỗi shard trả top candidate của nó, rồi merge và rank.

Inverted index

Một inverted index map mỗi term tới một posting list các document chứa nó (kèm position và stat cho ranking). Một query intersect/union posting list của các term. Posting list được nén và, với hot term, giữ trong memory.

Indexing pipeline

Ingestion tokenize text (lowercase, stem, bỏ stopword), rồi append mỗi token vào posting list của term nó trong shard đúng. Index được dựng dưới dạng segment bất biến được merge định kỳ; document mới searchable near-real-time một khi segment của nó được publish. Vì segment bất biến, một delete hoặc update không rewrite chúng: doc id được thêm vào một tombstone / delete bitmap và bị filter khỏi result; một update là delete + một version mới trong segment mới. Background merge xoá vật lý doc đã tombstone và thu hồi không gian.

Query: scatter-gather và ranking

Với document sharding, mỗi shard giữ một lát của corpus, nên một query phải đụng mọi shard. Mỗi shard trả local top-k bằng một score rẻ (vd BM25); query service merge chúng và áp một ranking nặng hơn (learning-to-rank dùng nhiều feature hơn). Latency bị chặn bởi shard chậm nhất, nên kiểm soát tail latency quan trọng.

Storage & technology choices

Quyết định storage là state nào là durable index so với structure derived/rebuild được, và write hiển thị thế nào:

  • Lucene segment files (index, trên SSD): inverted index nằm dưới dạng segment bất biến trên local SSD mỗi shard — write tạo segment mới, không bao giờ sửa cái cũ, đó là cái làm read lock-free và merge an toàn.
  • Translog + commit/refresh: một translog write-ahead làm một doc mới durable trước khi nó vào committed segment; một refresh định kỳ làm nó searchable (near-real-time), và commit fsync segment — đây là núm freshness/durability.
  • Replica mỗi shard: mỗi shard có replica cho availability và read scale; primary order write, replica follow.
  • Raw documents (source of truth): doc gốc nằm trong một blob/object store hoặc source DB — index là một structure derived, rebuild được, không phải system of record.
  • Delete/update: một delete bitmap / tombstone đánh dấu doc bị xoá; một segment merge ở background reclaim chúng và gộp segment.
  • Query cache: kết quả query hot cache trước scatter; rebuild được.
  • Implementations: Lucene (library), Elasticsearch/OpenSearch (phân tán), Solr, Vespa (search + ML + vector), Typesense/Meilisearch (nhẹ); pair với một vector index cho hybrid semantic + keyword search (xem RAG).

Consistency, freshness & guarantees

  • Eventually fresh: doc mới index chỉ searchable sau khi segment của nó publish và replicate — kỳ vọng giây (NRT) tới phút, không tức thì. Nêu rõ target.
  • Ranked, không exact: result là xấp xỉ sắp theo relevance; với ANN/learning-to-rank không có một "result set đúng" duy nhất, khác query SQL.
  • Pagination ổn định: dùng search_after trên một stable sort key (vd score + doc id) để indexing đồng thời không dịch page; deep offset vừa chậm vừa không ổn.
  • Best-effort completeness: khi một shard fail có thể trả partial result (kèm cờ "degraded") thay vì fail cả query — một trade-off availability/accuracy cần nêu.

Tradeoffs & khi nào không dùng

  • Tốt cho: full-text search, relevance ranking, faceted/typo-tolerant search trên corpus lớn.
  • Sai cho: lookup transactional chính xác (dùng database), strong consistency / read-your-writes, hoặc analytics aggregation trên range khổng lồ (dùng OLAP store).
  • Cost lever: replica cho QPS/tail, compression + tiering cho index size; chất lượng relevance là một đầu tư riêng, liên tục (eval + LTR).

Pitfalls và điểm cần bàn

  • Document vs term sharding: document sharding (mọi shard bị query) là lựa chọn phổ biến; term sharding dồn hot term — thường tệ hơn.
  • Tail latency: scatter-gather chờ shard chậm nhất — replicate, hedge request, và cap công việc mỗi shard.
  • Index freshness: segment bất biến + background merge cho near-real-time mà không phải rewrite cả index.
  • Hot query: query cache được check trước scatter và update sau merge; một phần nhỏ query chiếm phần lớn traffic.
  • Delete/update: segment bất biến cần tombstone/delete bitmap + background merge — không bao giờ rewrite segment tại chỗ.
  • Pagination: dùng cursor / search_after trên stable sort, không deep offset.
  • Posting-list size: nén; giữ hot list trong memory.

Key takeaways

  • Inverted index (term tới posting list) là cấu trúc cốt lõi.
  • Document sharding + scatter-gather scale corpus; tail latency là kẻ thù.
  • Segment bất biến + merge cho near-real-time indexing.
  • Score per-shard rẻ rồi ranking nặng hơn trên tập đã merge.
  • Trị tail: replicate shard, hedge request, cap công việc per-shard — latency scatter-gather = shard chậm nhất.
  • Result là ranked + eventually fresh, không exact — nói rõ, và dùng search_after cho pagination ổn định.
