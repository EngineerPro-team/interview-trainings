Retrieval-Augmented Generation (RAG) grounds một LLM trên dữ liệu của bạn: retrieve các passage liên quan nhất cho một câu hỏi, rồi cho model trả lời dùng chúng (kèm citation). Thiết kế là hai pipeline — một ingestion/indexing offline và một retrieval + generation online — cộng một vector index cho similarity search.

Insight cốt lõi cho phỏng vấn: RAG biến "model không biết dữ liệu của tôi / hallucinate" thành một bài toán retrieval. Chất lượng answer bị chặn bởi cái bạn retrieve — nếu passage đúng không nằm trong top-k, không prompt engineering nào cứu được answer. Nên phần lớn công sức thiết kế đổ vào recall, ranking, freshness, và access control, không phải lời gọi generation.

Clarifying questions (scope trước)

  • Corpus gì và fresh tới đâu? Doc tĩnh (re-index hàng đêm) vs dữ liệu thay đổi liên tục (incremental, near-real-time indexing) đổi hoàn toàn thiết kế ingestion.
  • Dữ liệu private/multi-tenant? Nếu answer phải tôn trọng permission per-user, ACL filter thuộc bên trong retrieval — một yêu cầu correctness và security, không phải add-on.
  • Budget latency vs quality? Có cho phép một reranker và/hoặc multi-step retrieval không, hay đây là path chặt dưới 200ms?
  • Cần citation / groundedness? Nếu answer phải audit được, mỗi chunk cần source metadata ổn định và answer phải cite nó.
  • Scale corpus? Triệu vs tỷ chunk quyết định flat vs sharded ANN và có quantize hay không.

Requirements

Functional

  • Ingest document (chunk, embed, index).
  • Trả lời một query với text grounded và citation.
  • Incremental update khi document thay đổi.

Non-functional

  • Retrieval latency thấp; recall và precision tốt.
  • Freshness của index; scale tới hàng tỷ vector.

Back-of-the-envelope estimation

  • Corpus: 10M document × ~10 chunk mỗi cái = 100M chunk → 100M embedding vector.
  • Vector size: 100M × 768 dims × 4 bytes ≈ ~300 GB vector thô → shard ra nhiều node; nén bằng quantization (PQ).
  • Query latency: exact nearest-neighbor trên 100M vector quá chậm → ANN index trả top-k trong millisecond.
  • Ingestion cost: embed 100M chunk là một GPU job one-time lớn; re-embed khi đổi model mới là phần đắt.

Worked example. 100M chunk ở 768-dim FP32 là ~300 GB vector. Một HNSW graph thêm cỡ cùng order về graph link, nên dự trù memory cỡ hàng trăm GB — buộc phải sharding qua nhiều node hoặc quantization. Product quantization (PQ) có thể nén mỗi vector 768-dim từ ~3 KB xuống ~100-200 byte (~15-30x), đưa 300 GB còn ~10-20 GB đổi lấy mất chút recall — trade-off recall/memory kinh điển. Phía write, embed 100M chunk ở ~1k chunk/s trên pool GPU là ~28 giờ compute one-time; phần đau là đổi embedding model phải re-embed toàn bộ corpus, nên model version là first-class của index (bạn version và rebuild, không trộn embedding space).

Core APIs

  • POST /ingest — {doc_id, content} → chunked, embedded, indexed.
  • POST /query — {question, top_k} → {answer, citations[]}.
  • POST /search — {query, top_k} → raw chunk retrieved (không generation).

High-level architecture

Ingestion pipeline biến document thành vector đã index; query path retrieve, rerank, dựng prompt, và gọi LLM gateway. Một vector store cộng một keyword index hậu thuẫn retrieval.

Ingestion pipeline

Document được chunk (chia thành passage có size hợp với retrieval và context window), mỗi chunk được biến thành một embedding bởi embedding model, và vector được ghi vào index kèm source metadata (để citation). Chunking strategy quan trọng: quá lớn làm loãng relevance, quá nhỏ mất context.

Vector index (ANN)

Exact nearest-neighbor trên 100M+ vector quá chậm, nên RAG dùng approximate nearest neighbor (ANN). Hai họ phổ biến:

  • HNSW (graph): dựng một navigable small-world graph; recall và latency tuyệt, memory cao hơn.
  • IVF-PQ (inverted file + product quantization): cluster vector và nén chúng; memory thấp hơn, recall/latency tune được.

Đánh đổi là tam giác kinh điển recall vs latency vs memory; chọn theo corpus size và SLA.

Query path: hybrid retrieval và rerank

Vector search bắt nghĩa; keyword search (BM25) bắt term chính xác (tên, mã). Hybrid retrieval chạy cả hai và merge, rồi một reranker (cross-encoder) sắp lại candidate đã merge theo relevance thật với query. Các passage top thành context của LLM.

Access control

RAG trên dữ liệu private phải tôn trọng permission: mỗi chunk mang tenant + ACL label (và một source_uri) từ ingestion, và ACL được đẩy vào chính retrieval query — một metadata filter trên vector/keyword search (hoặc over-fetch rồi filter trước merge) — không áp sau top-k. Filter sau một global top-k vừa là security risk (forbidden chunk tới app layer) vừa là recall bug (top-k có thể toàn chunk user không được xem, sau filter còn rỗng). Filter bên trong query giữ recall đúng và model không bao giờ thấy context cấm.

Freshness và evaluation

Document thay đổi, nên ingestion là incremental và versioned: một indexing job ghi một doc version mới, atomically swap active version, tombstone chunk cũ, và background compaction thu hồi chúng. Mỗi chunk giữ chunk_id ổn định, doc_version, và embedding_model_version để re-embed và delete propagate sạch. Citation mang doc_id, chunk_id, source_uri, title, span, và version. Chất lượng đo bằng một vòng eval — retrieval recall và groundedness của answer (có được citation hỗ trợ không, có hallucinate không?) trên một golden set cộng online feedback.

Storage & technology choices

  • API gateway: auth + rate limiting đứng trước query và ingest endpoint.
  • Vector store: một ANN store chuyên dụng — FAISS (library), Milvus / Qdrant / Weaviate (service), pgvector (extension Postgres), hoặc Pinecone (managed). HNSW hoặc IVF-PQ bên dưới.
  • Keyword index: Elasticsearch / OpenSearch (BM25) cho nửa lexical của hybrid retrieval.
  • Raw document + chunk: bản gốc trong blob/object storage (S3-like); chunk text + metadata + ACL label trong relational/KV store (PostgreSQL / DynamoDB).
  • Ingestion pipeline: Kafka cho document-change stream, một batch/stream processor (Spark / Flink) để chunk + embed ở scale, và một embedding model serve trên GPU (Triton / vLLM).
  • Reranker: một cross-encoder model service; LLM gateway cho generation; Redis để cache hot query result / embedding.

Vì sao chọn vậy: lựa chọn storage theo access pattern — semantic similarity → vector index (không phải B-tree); exact-term match → inverted index; source file lớn bất biến → object storage; metadata + permission nhỏ có cấu trúc → relational/KV store; job ingest/reindex throughput cao → Kafka + batch engine. Không một database nào làm tốt cả bốn, nên RAG cố ý polyglot.

Consistency & guarantees

  • Eventually fresh, không transactional: có độ trễ giữa lúc document đổi và lúc index phản ánh (re-chunk → re-embed → publish). Nói rõ freshness SLA; đừng hứa read-after-write trên corpus.
  • Best-effort recall, không exact: ANN trả top-k xấp xỉ — tune recall vs latency, và dùng hybrid (vector + keyword) để exact-term match không bị embedding bỏ sót.
  • ACL là guarantee cứng: permission filter enforce bên trong retrieval, nên user không bao giờ bị hiển thị (hoặc cite) một chunk họ không được truy cập — kể cả khi mất recall.
  • Groundedness, không phải truth: RAG bảo đảm answer được dựng từ passage retrieved kèm citation; nó không bảo đảm source đúng. Hiện citation để người kiểm chứng.
  • Versioned index: trong một query, retrieval đọc một index version nhất quán; đổi embedding model trigger full rebuild sang version mới, swap atomically (tombstone cho delete ở giữa).

Khi nào (không) nên dùng RAG

  • Tuyệt cho: question-answering trên knowledge private/thay đổi, giảm hallucination, và bất kỳ answer nào phải cite source — mà không cần retrain model.
  • Thừa khi: knowledge nhỏ, tĩnh vừa prompt (cứ bỏ vào context), hoặc task reasoning/transform thuần không cần fact ngoài.
  • Sai công cụ khi: câu hỏi cần aggregation/join trên structured data (dùng SQL/analytics, tùy chọn như một tool model gọi), hoặc khi source of truth đổi nhanh hơn tốc độ index được và cần freshness nghiêm ngặt.

Pitfalls và điểm cần bàn

  • Chunking bị đánh giá thấp: ranh giới chunk tệ phá recall — tune size và overlap.
  • Vector-only miss term chính xác: thêm keyword/hybrid retrieval và một reranker.
  • Index cũ: hỗ trợ incremental upsert/delete; full re-embed chỉ khi đổi model.
  • Permission leakage: filter theo ACL/tenant trước rerank và generation; không bao giờ để một chunk cấm tới model hay citation.
  • Vector storage overhead: vector thô tính thiếu memory thật — HNSW graph link, metadata, chunk text, tombstone/version, và replica nhân lên; IVF-PQ nén nhưng đánh đổi recall.
  • Hallucination: chỉ dẫn model trả lời chỉ từ context và cite; eval groundedness.
  • Cost re-embed cả corpus khi nâng cấp embedding-model — lên kế hoạch migration.

Key takeaways

  • RAG = offline chunk-embed-index + online retrieve-rerank-generate.
  • ANN (HNSW / IVF-PQ) làm similarity search nhanh ở scale; tune recall vs latency vs memory.
  • Hybrid retrieval + reranking thắng vector search thuần.
  • Hỗ trợ incremental indexing và đo groundedness.
