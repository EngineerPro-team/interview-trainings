Một AI coding agent platform (kiểu Cursor / Devin) chạy các agent tự động edit code, chạy test, và mở pull request — thường nhiều cái song song, chạy nền. Các bài infra khó là sandbox cô lập, durable agent run, và Git operation an toàn ở scale. Nó xây trên agentic platform và LLM inference platform.

Ràng buộc phân biệt so với một agentic platform chung chung: agent execute code tùy ý, untrusted (test của repo, build script, và bất cứ gì model quyết định chạy) trên source và credential private. Nên thiết kế bị chi phối bởi hai căng thẳng — isolation mạnh (một run thù địch hoặc lỗi không được thoát sandbox, exfiltrate secret, hay đụng repo của tenant khác) versus spin-up nhanh và cost (hàng nghìn environment ngắn hạn). Gần như mọi lựa chọn (microVM, warm pool, copy-on-write repo, egress proxy, secret broker) là một điểm trên trade-off đó.

Clarifying questions (scope trước)

  • Trust boundary? Code agent có chạy lệnh và test tùy ý không? (Có → isolation cứng: microVM, không network mặc định, secret brokered.)
  • Interactive hay background? User chờ trong editor quan tâm spin-up dưới giây; fleet background tối ưu throughput và cost.
  • Side effect nào được phép? Chỉ mở PR, hay cả push, deploy, gọi API ngoài? Mỗi cái cần scoped token và audit.
  • Scale repo và ngôn ngữ? Monorepo vs repo nhỏ đổi chiến lược clone/snapshot và thiết kế build-cache.
  • Multi-tenant? Isolation per-tenant của sandbox, secret, cache, và egress là một yêu cầu security, không phải tối ưu.

Requirements

Functional

  • Submit một coding task lên một repo; agent edit code trong sandbox, chạy test, stream progress.
  • Tạo diff / mở pull request; resume run bị gián đoạn.
  • Chạy nhiều background agent đồng thời.

Non-functional

  • Isolation / security — code agent không được thoát sandbox hay rò rỉ secret.
  • Sandbox spin-up nhanh; reliability; concurrency cao; cost control.

Back-of-the-envelope estimation

  • Concurrency: hàng nghìn run đồng thời, mỗi cái sở hữu một sandbox — pool và recycle environment, đừng spin một cái cold mỗi request.
  • Spin-up: một container cold mất vài giây; một microVM với warm pool dưới một giây — quan trọng vì user chờ ở lúc bắt đầu.
  • Run length: vài phút tới vài chục phút, đa số chờ LLM và test — async orchestration, không phải thread giữ mãi.
  • Repo size: snapshot/clone repo lớn thì nặng → cache base image và dùng copy-on-write workspace.

Worked example. Giả sử 5.000 run đồng thời, mỗi cái cần environment 2 GB repo + toolchain. Clone repo 2 GB mới mỗi run là ~10 TB I/O và hàng chục giây latency mỗi cái — không khả thi. Với copy-on-write từ một base snapshot cache sẵn, mỗi run chỉ lưu diff của nó (vài chục MB), nên 5.000 run tốn ~vài trăm GB, không phải 10 TB, và start dưới một giây nhiều. Toán spin-up: boot container/VM cold ~2-10s; nếu user chờ lúc đầu, một warm pool các sandbox đã boot biến nó thành latency pop-queue (ms). Size pool là một trade-off utilization kinh điển — nhỏ quá thì user queue, lớn quá thì microVM nằm không đốt tiền — nên pool được autoscale theo demand với một buffer warm nhỏ. Tài nguyên khan hiếm là memory/CPU sandbox và token LLM, không phải throughput orchestrator.

Core APIs

  • POST /tasks — {repo, branch, instruction} → {run_id} (async, background).
  • GET /runs/{id} → status, log stream, diff.
  • POST /runs/{id}/resume; POST /runs/{id}/pr — mở pull request.

High-level architecture

Một orchestrator (durable, như agentic platform) điều khiển mỗi run; một sandbox provisioner đưa nó một environment cô lập từ warm pool; một repo service clone/snapshot code; tool layer chạy edit/shell/test bên trong sandbox; kết quả stream ra và một artifact service mở PR.

Sandbox provisioning

Mỗi run cần một environment sạch, cô lập nơi các lệnh untrusted do model điều khiển có thể chạy. microVM (hoặc container được hardened) cho isolation mạnh; một warm pool các sandbox đã boot sẵn với base image cached làm start-up dưới một giây. Repo được materialize qua copy-on-write nên clone repo lớn rẻ.

Run lifecycle

Orchestrator chạy agent loop (plan-act-observe) nơi tool là edit file, run shell, và run tests. Mỗi step được checkpoint nên một run sống sót qua restart và có thể pause để review. Log stream tới client suốt quá trình.

Tool execution và Git

Tool được scope vào filesystem của sandbox và một shell hạn chế; network và secret bị khoá. Khi agent xong, repo service biến working change thành một branch + commit và mở pull request qua Git provider — agent không bao giờ push trực tiếp với credential rộng; một scoped token làm việc đó.

Tách side effect local trong sandbox (edit file, chạy test — redo rẻ) khỏi side effect bên ngoài (Git PR, package publish, network call). Action bên ngoài đi qua artifact/approval service với một idempotency key đã ghi, nên crash-rồi-replay không mở hai PR hay publish hai lần. Một control plane bọc sandbox: một secret broker inject scoped short-lived token chỉ khi approved, một egress proxy/allowlist hạn chế network, và một artifact scanner + audit log phủ output.

Storage & technology choices

  • API gateway: auth, quota concurrency theo tenant, route tới run orchestrator.
  • Orchestrator: một durable workflow engine (kiểu Temporal) để background run sống sót qua restart và resume.
  • Sandbox: một warm pool Firecracker microVM (hoặc gVisor/Kata) — isolation mạnh, start dưới giây; repo materialize qua một copy-on-write overlay filesystem trên base image cached.
  • Run state & artifact: PostgreSQL cho run/step state; blob storage (S3-like) cho diff, log, build artifact; Redis cho warm-pool bookkeeping và live log fan-out.
  • Repo / Git: Git provider (GitHub/GitLab API) cho clone + PR; commit đi qua scoped token do secret broker (Vault) cấp; một egress proxy/allowlist gate network.
  • LLM: LLM/agent gateway cho model call.
  • Audit trail (durable sink): vì actor tự động, mọi command/tool/action ngoài phải đáp vào một append-only audit store thiết kế đạt mức audit-grade — một append-only Postgres table hoặc một immutable object-storage log partition theo run/date (tùy chọn hash-chained), kèm retention/WORM và access control. Kafka là fanout từ lần ghi audit tới consumer, không phải system of record tự thân.

Vì sao chọn vậy: isolation là toàn bộ cuộc chơi → microVM + egress proxy + Vault, không phải host chung; run state nhỏ/có cấu trúc → SQL; diff/log lớn/append → object storage; warm pool và streaming hot/ephemeral → Redis. Không có DB quan hệ lớn trên critical path — tài nguyên khan hiếm là sandbox slot và LLM token.

Consistency & guarantees

  • Run resumable, external effect idempotent: việc trong sandbox (edit, chạy test) rẻ để làm lại khi resume, nhưng action ngoài — git push, mở/update PR, gọi deploy API — phải idempotent (vd push lên một branch deterministic, upsert PR) để retry sau crash không tạo bản trùng.
  • Sandbox isolation là guarantee cứng: một run không ra được network trừ qua egress allowlist, không đọc được repo hay secret của tenant khác, và bị hủy sau run (không rò state giữa các run).
  • Secret được broker, không bao giờ resident: sandbox nhận token short-lived, scoped từ broker theo nhu cầu; credential long-lived không bao giờ vào không gian agent kiểm soát, nên một run bị compromise có blast radius nhỏ, giới hạn thời gian.
  • Eventually-consistent với Git provider: state PR/commit thuộc GitHub/GitLab; platform reconcile view của nó bằng webhook/polling thay vì giả định state local là authoritative.
  • Auditability: mọi lệnh, tool call, và action ngoài được ghi durable vào một store append-only đạt audit-grade (immutable, có retention, access-controlled) — không chỉ emit ra một stream — vì actor là một agent tự động và audit trail phải trụ được trước tranh chấp/security review.

Khi nào (không) nên dùng thiết kế này

  • Dùng khi: bạn chạy code untrusted/agent-generated ở scale, cần isolation per-run và Git side effect audit được, và muốn parallelism nền (nhiều agent cùng lúc).
  • Thừa khi: code hoàn toàn trusted và chạy hiếm — một CI runner thường hoặc một container đơn là đủ; không cần microVM và warm pool.
  • Cẩn thận khi: agent có thể push/deploy lên production — gate sau human approval và scoped token; failure mode (một deploy tự động sai) đắt hơn nhiều một suggestion sai.

Pitfalls và điểm cần bàn

  • Sandbox escape là rủi ro hàng đầu — isolation mạnh (microVM), không host access, network bị khoá.
  • Cold start hại UX — warm pool + base image cached + repo copy-on-write.
  • Secret leakage: không bao giờ expose credential long-lived thô trong sandbox; dùng scoped token short-lived.
  • Runaway run: step/time/cost limit; phát hiện vòng lặp no-progress.
  • Concurrency limit: cap sandbox mỗi tenant; recycle quyết liệt.

Key takeaways

  • Platform ghép một durable run với một sandbox cô lập từ warm pool.
  • Tool (edit/shell/test) chạy bên trong sandbox; không bao giờ trên host.
  • Repo copy-on-write + warm pool làm start-up nhanh.
  • Commit đi qua một scoped token; một PR gate human review.
