Một agentic AI platform chạy các agent tự động: plan, gọi tool, observe kết quả, và lặp tới khi task xong. Khác một LLM call đơn lẻ, một agent run là một workflow dài, stateful, nhiều bước — nên thiết kế mượn từ durable workflow engine: checkpointing, idempotent step, tool sandboxing, memory, và guardrails. Nó nằm trên LLM inference platform.

Khung tư duy ăn điểm phỏng vấn: ngừng nghĩ "LLM call" và bắt đầu nghĩ "workflow phân tán durable mà các step tình cờ non-deterministic và có thể gây side effect ngoài đời thực." Reframe đó buộc ra các requirement khó — mỗi step phải checkpoint để crash resume được, mỗi tool call phải idempotent hoặc có guard để retry không charge khách hai lần, và mỗi action phải sandboxed và policy-gated vì model là untrusted input đang quyết định làm gì.

Clarifying questions (scope trước)

  • Tool thực sự làm được gì? Read-only (search, fetch) rủi ro thấp; side-effecting (gửi email, chuyển tiền, deploy) đòi idempotency key, approval, và audit.
  • Tự động tới mức nào? Hoàn toàn tự động, hay có approval gate human-in-the-loop trước action rủi ro? Điều đó quyết định có cần state approval/pause-resume không.
  • Thời lượng run và resumability? Giây vs run hàng giờ quyết định state nằm in-memory hay trong một durable workflow store.
  • Isolation multi-tenant? Platform dùng chung qua nhiều tenant cần memory, secret, sandbox, và quota per-tenant — một security boundary, không chỉ config.
  • Giới hạn cost/loop? Cái gì chặn agent loop mãi hoặc đốt token vô hạn — step limit, token budget, một supervisor?

Requirements

Functional

  • Định nghĩa agent với một bộ tool; chạy task nhiều bước (plan tới act tới observe).
  • Tool calling; memory ngắn hạn và dài hạn.
  • Resume run bị gián đoạn; human-in-the-loop approval; full trace.

Non-functional

  • Reliability: step idempotent và run resumable.
  • Cost control: token budget và loop limit.
  • Safety: tool sandboxed, guardrails. Scale nhiều run đồng thời.

Back-of-the-envelope estimation

  • Run length: một agent run có thể là 10-100+ LLM call qua vài phút tới vài giờ — dài hơn một request rất nhiều, nên state phải durable, không phải in-memory.
  • Cost: mỗi step gửi context đang lớn dần tới LLM; một run 50 step với context 10k token có thể đốt ~500k+ token — context management và budget là thiết yếu.
  • Concurrency: hàng nghìn run đồng thời, đa số đang chờ LLM hoặc tool I/O → một orchestrator async, queue-driven, không phải một thread mỗi run.
  • Memory store: vector + key-value memory theo từng agent; read ở hầu hết step.

Worked example. Giả sử một run trung bình 30 step và mỗi step gửi lại một context lớn dần từ 2k tới ~15k token; tích phân cỡ 30 × ~8k ≈ 240k input token cộng output — chỉ một run. Ở 10k run đồng thời, đó là hàng triệu token/s nhu cầu lên inference platform, nên context management (summarize/trim turn cũ, giữ tool result ngoài prompt khi có thể) không phải tùy chọn — nó trực tiếp điều khiển cost và latency mỗi step (context lớn = prefill chậm hơn). Toán concurrency: 10k run mỗi run block ~5s trên một LLM/tool call nghĩa là orchestrator chủ yếu đang chờ, nên model thread-per-run cần 10k thread; một orchestrator async, event-driven dựa trên một durable queue xử lý cùng tải trên vài worker. Tài nguyên khan hiếm là LLM/GPU và rate limit của tool ngoài, không phải CPU orchestrator.

Core APIs

  • POST /agents — {name, system_prompt, tools[]} → {agent_id}.
  • POST /agents/{id}/runs — {task, budget} → {run_id} (async).
  • GET /runs/{id} → state, step, trace; POST /runs/{id}/resume.
  • POST /runs/{id}/approve — cổng human-in-the-loop.

High-level architecture

Một orchestrator điều khiển mỗi run như một durable state machine: nó gọi LLM gateway để quyết định action kế tiếp, execute tool trong sandbox, read/write memory, quản context, và ghi mọi step vào trace. Run dài sống trên một queue, không phải một connection giữ mãi.

Agent loop

Cốt lõi là một vòng lặp: LLM plan action kế tiếp, platform act (gọi tool), feed lại observation, và lặp tới khi đạt goal hoặc chạm limit. Mỗi iteration là một durable step.

Tool calling và sandboxing

Tool là cách agent tác động lên thế giới (search, code execution, API call). Chúng phải chạy trong một sandbox cô lập với resource limit và không truy cập secret mà nó không nên có — một tool là code untrusted được điều khiển bởi model. Orchestrator validate tool request của model, chạy nó, và trả về một observation có cấu trúc.

Durable runs: checkpoint và resume

Vì một run trải vài phút/giờ và nhiều call có thể fail, coi nó như một durable workflow (kiểu Temporal). Sau mỗi step, persist run state (step index, context pointer, memory delta). Khi crash, restart, hay pause chờ human-approval, orchestrator resume từ checkpoint cuối.

An toàn side-effect của tool là phần tinh tế. Một tool có thể tạo side effect bên ngoài (API call, payment, PR) rồi crash trước khi checkpoint được ghi — replay ngây thơ sẽ gọi nó hai lần. Nên một tool step bản thân là một state machine nhỏ: Planned → ToolRequested (ghi idempotency_key) → ToolResultRecorded → Checkpointed. Orchestrator ghi request trước khi gọi tool, tool được gọi kèm idempotency key (hoặc orchestrator lookup result đã có), và chỉ một result đã ghi mới đẩy run tiến. Trace/state store redact secret và tenant-isolated; persist context summarize + pointer thay vì prompt thô.

Memory và context management

Context window của LLM hữu hạn, nhưng một run dài tích luỹ history. Context manager giữ prompt trong budget: summarize step cũ, và chỉ retrieve memory dài hạn liên quan (một vector store) cho step hiện tại. Short-term memory là history step gần đây; long-term memory persist xuyên các run.

Storage & technology choices

  • API gateway: auth, quota/token budget theo tenant, route tới orchestrator.
  • Orchestrator: một durable workflow engine (Temporal / state machine tuỳ chỉnh) để một run nhiều bước sống sót qua crash và resume từ checkpoint.
  • Run state & trace: step state trong PostgreSQL (nhỏ, transactional, queryable); artifact step lớn (tool output, log) trong blob storage; trace trong observability stack.
  • Memory: long-term trong một vector store (Milvus / pgvector / Pinecone), short-term/working memory trong Redis, cả hai namespaced theo tenant.
  • Tools: execute trong một sandbox (Firecracker microVM / gVisor / container); một secret broker (Vault) inject scoped short-lived credential.
  • Queue + LLM: Kafka / SQS cho scheduling run dài; LLM gateway (inference platform) cho model call; SSE/WebSocket cho progress streaming.

Vì sao chọn vậy: run dài và dễ fail → một durable workflow engine, không phải request thread; run state có cấu trúc → SQL, artifact lớn → object storage; semantic memory → vector store, hot working state → Redis; tool code untrusted → sandbox + secret broker Vault. Split phản ánh hình dạng data, không phải một database cho tất cả.

Consistency & guarantees

  • Exactly-once intent, at-least-once execution: workflow engine bảo đảm một step không bị mất (retry từ checkpoint gần nhất), nên một tool call có side-effect phải idempotent (idempotency key) hoặc được guard bởi một step state machine, nếu không retry lặp lại action.
  • Run durable, resumable: sau mỗi step run state được commit; worker crash thì resume từ checkpoint gần nhất, không phải từ đầu — output LLM call được ghi lại nên không bị re-sample khi resume.
  • Policy là gate cứng, model output không được tin: model đề xuất action; một lớp authorization/approval quyết định chúng có execute không. Guardrails (allowlist, scope, human approval) enforce bên ngoài model.
  • Step non-deterministic, orchestration deterministic: LLM non-deterministic, nhưng orchestration (step nào chạy, kết quả, retry) là một log deterministic, replay được — đó là cái làm debug và audit khả thi.
  • Isolation: memory, secret, và sandbox per-tenant được cô lập; một run không đọc được state hay credential của run khác.

Khi nào (không) nên dùng một agentic platform

  • Dùng khi: task thực sự cần reasoning nhiều bước với tool (research, coding, ops automation), run dài/resumable, và action có side effect thật cần audit và approval.
  • Thừa khi: một LLM call đơn (hoặc một prompt chain cố định) giải được — đừng xây workflow engine cho một classification hay summarization một phát.
  • Nguy hiểm khi: tool có side effect không đảo ngược được và bạn không thể làm idempotent hay gate bằng approval — chi phí một action tự động sai lớn hơn lợi ích. Bắt đầu read-only, thêm write tool sau approval.

Pitfalls và điểm cần bàn

  • Vòng lặp vô hạn / cost vượt kiểm soát: enforce step limit và token budget; phát hiện action lặp không tiến triển.
  • Tool safety: sandbox mọi thứ; không bao giờ đưa model credential thô hay quyền truy cập không giới hạn.
  • Context overflow: summarize + retrieve; đừng dump cả history mỗi step.
  • Non-determinism: trace và idempotent step làm run debug được và resume được.
  • Multi-agent: pattern orchestrator-worker (một planner uỷ thác cho sub-agent) scale task phức tạp nhưng nhân chi phí.

Key takeaways

  • Một agent run là một durable, multi-step workflow, không phải một call.
  • Vòng plan-act-observe với budget và limit là cốt lõi.
  • Sandbox tool; model đang điều khiển action untrusted.
  • Checkpoint/resume + idempotent step làm run dài tin cậy.
  • Context management + memory giữ prompt có giới hạn và grounded.
