An online auction (eBay-style, or live real-time bidding) is a concurrency-and-consistency problem: many bidders race on the same item, the highest valid bid must always win, and the auction must close correctly at a precise time. This chapter focuses on bid concurrency, correct close/settlement, and anti-sniping.

Unlike most "scale" questions, an auction is a correctness-first design where the load is highly concentrated: 99% of items are quiet, but a hot item in its final seconds is a thundering race where the wrong answer (a lost bid, two winners, a double charge) is unacceptable. The central idea is to serialize all writes for a single item (so bids on one item have a single, total order) while letting the far larger read/watch traffic scale out separately. Money makes durability and exactly-once settlement non-negotiable — you cannot trade them for latency.

Clarifying questions (scope it first)

  • Auction style? Ascending (eBay), proxy/max-bid auto-bidding, or sealed-bid? Proxy bidding changes the "accept" logic (resolve against the other party's max).
  • Hard close or anti-snipe? Does a last-second bid extend the end time? That changes the close scheduler and fairness model.
  • How hot can one item get? Tens vs thousands of bids/s in the final seconds decides whether one writer per item suffices or needs extra care.
  • Consistency vs availability on bids? Bids must be strongly consistent and durable (it's money) — confirm we favor correctness over raw throughput.
  • Settlement? Charge the winner exactly once, handle payment failure / second-chance offers — defines the settlement saga.

Requirements

Functional

  • Create an auction with a start/end time and starting price.
  • Place a bid; see the current highest bid in real time.
  • Proxy / max bid (auto-bid up to a limit).
  • Auto-close at end time; notify winner; settle payment.

Non-functional

  • Strong consistency for bids — no lost or out-of-order accepted bids.
  • Low latency bid acknowledgement and live price updates.
  • Handle bid spikes at auction close.
  • Exactly-once settlement.

Back-of-the-envelope estimation

  • Items: 10M active auctions; most get few bids, a few get thousands.
  • Bid spike: a hot item in its final 10 seconds can take hundreds of bids/s on one item — the per-item write path must be serialized and fast.
  • Reads: watchers vastly outnumber bidders — current price is a fan-out read, cache and push it.
  • Close events: 10M auctions closing across a day, clustered at round hours — the close scheduler must handle bursts.

Worked example. Picture one hot item in its final 10 seconds taking ~500 bids/s. If you used a plain "read price, compare, write" with row locks, the contention on that one row serializes everyone anyway but with lock waits and retries — and an optimistic compare-and-set would make hundreds of bidders retry in a tight loop. The clean model is a single writer per item: route every bid for item X to one owner (an in-memory actor / partition) that processes them in arrival order, so 500 bids/s is just 500 sequential compares — trivial for one core — and the order is unambiguous. The subtlety the example forces: that writer must durably commit each accepted bid before acking (group-commit to a WAL or a conditional DB write), because a crash after acking a winning bid but before persisting would lose money. Meanwhile the close burst is a separate problem: 10M auctions clustered at round hours means the close scheduler faces a thundering herd of expirations — spread them with jitter and use a partitioned timer/queue, not one global timer.

Core APIs

  • POST /auctions — {item, start_price, ends_at} → {auction_id}.
  • POST /auctions/{id}/bids — {user_id, amount, idempotency_key} → {accepted, current_high}.
  • GET /auctions/{id} → current high bid + time left (cacheable, pushed via WebSocket).
  • POST /auctions/{id}/proxy — {user_id, max_amount}.

High-level architecture

Bid concurrency

The core race: two bids for the same item arrive at once. We must accept only bids that beat the current high, and never lose one. Two robust approaches:

  • Optimistic concurrency: a conditional update — UPDATE ... SET high = new WHERE id = ? AND high < new. If the row changed under us, the update affects 0 rows and the bid is rejected/retried. The conditional row update is the arbiter for the current high-bid projection; the accepted bid event must still be durably recorded in the BidLog (the source of truth) before ack — ideally in the same local transaction.
  • Single-writer per item: route all bids for an item to one partition/actor (e.g. by hashing auction_id) and process them in a queue — serialized, no contention.

Closing and settlement

At the end time, the auction must atomically freeze the winner and settle. A scheduler (durable timer) fires a close job; settlement is idempotent (keyed by auction_id) so a retried or duplicated close cannot double-charge. The auction is a state machine.

Anti-sniping

A "snipe" is a bid in the final instant that leaves no time to respond. The common rule: if a bid lands within the final window (e.g. last 10s), extend the end time by that window. This keeps the close fair and spreads the spike out.

Scaling a hot item

Most items are cold; a few are extremely hot at close. Because correctness requires serializing writes per item, a single hot item is bounded by one writer's throughput — still thousands/s when the writer keeps the high bid in memory but durably commits each accepted bid — appending to the append-only BidLog and updating the high-bid projection in one step (group-commit to a replicated log) — before acking. Durability is not skipped for speed; it is batched. Watchers (reads) scale separately: the current price is cached and pushed, never recomputed per viewer.

Storage & technology choices

  • API gateway: auth, rate limiting (bid spikes), routing.
  • BidLog (source of truth): an append-only log of accepted/rejected bid events keyed by auction_id, ordered by bid_seq — this is what makes replay, audit, dispute resolution, proxy-bid reasoning, and outbid-notification reconstruction possible.
  • AuctionState (projection): a row holding the current high bid + state-machine status with a version, a fast projection of the BidLog (not a substitute). To avoid a cross-system atomic write, keep BidLog and AuctionState in the same transactional store/partition (e.g. the same PostgreSQL DB, or one single-writer-per-item partition) so the bid event append and the high-bid update commit in one local transaction — a conditional update is the arbiter. (Alternatively, make BidLog the only source of truth and derive/reconcile AuctionState from it, so the ack depends only on the durable BidLog append.)
  • Live price push: Redis (pub/sub + cached current high) fanned out to watchers over WebSocket.
  • Events: Kafka carries bid/outbid/settlement events to notifications and analytics — a fanout transport, not the authoritative bid log (unless you explicitly design its retention/replay/compaction/audit to be audit-grade).
  • Close scheduling: a durable scheduler/timer (a delay queue or a workflow engine) fires the close job at the end time.
  • Settlement / ledger: a transactional ledger (PostgreSQL) with idempotent settlement keyed by auction_id; payment via a PSP.

Why these: bids demand correctness under contention → a transactional DB with conditional writes (the one place you must not use an eventually-consistent cache as the source of truth); the read-heavy watcher path is cache + push → Redis; close is a scheduled job → a durable timer; money → a transactional ledger. Reads and writes use different stores on purpose.

Consistency & guarantees

  • Strongly consistent, durable bids: accepted bids are totally ordered per item and committed to the append-only BidLog (with the high-bid projection updated in the same step) before the ack — the highest valid bid always wins, an acknowledged bid is never lost, and the full history is auditable/replayable on crash.
  • Single-winner per item: either a single writer per item or a conditional/compare-and-set update arbitrates, so concurrent bids can never both "win" or skip the current high.
  • Exactly-once settlement: close-and-charge is idempotent keyed by auction_id, so a retried close or duplicate event charges the winner once; payment failure triggers a defined fallback (second-chance offer), not a silent loss.
  • Eventually-consistent watcher view: the live price shown to watchers is a cached, pushed value that may lag the authoritative high by milliseconds — fine for display, never used as the bid arbiter.
  • Deterministic close: the auction closes against the durable BidLog at the end time; anti-snipe extensions are part of that authoritative timeline, not a client-side guess. The winner is reconstructable from the log, not just from the current high-bid projection.

When (not) to use this design

  • Fits: any "highest/first valid action wins on a contended item" problem — auctions, limited-stock flash sales, seat/ticket grabs, ad real-time bidding.
  • Simplify when: bids are rare and items never get hot — a single conditional update on a row is enough; you don't need per-item single writers or a close-scheduler fleet.
  • Different design when: the matching is two-sided continuous (buyers and sellers with a live order book) — that's a matching engine (see the stock exchange), not a one-sided ascending auction.

Pitfalls and talking points

  • Lost bid: never read-then-write without a version/condition — use conditional update or a per-item single writer.
  • Double settlement: close + charge must be idempotent (key on auction_id).
  • Clock at close: use a durable scheduler; do not rely on a single in-process timer.
  • Snipe spike: anti-snipe extension both improves fairness and flattens the burst.
  • Proxy bids: resolve auto-bids server-side atomically so two proxies do not ratchet incorrectly.

Key takeaways

  • Bids need serialized, conditional writes — DB row arbiter or per-item single writer.
  • Close is a durable scheduled job driving idempotent settlement.
  • Anti-snipe extension keeps closes fair and spreads load.
  • Reads (watchers) scale independently via cache + push.
