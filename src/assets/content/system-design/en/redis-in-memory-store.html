Redis is an in-memory data-structure store used as a cache, database, and message broker. In an interview, "design Redis" is a building-block question: instead of assembling existing services, you design the internals of one. This chapter builds a Redis-like store from first principles — the data model, the single-threaded execution engine, persistence, replication, failover, horizontal scaling, and the consistency guarantees that fall out of those choices.

The reason this question is popular is that it forces you to reason about memory layout, the CPU/IO boundary, and the durability–availability–latency trade space directly, without hiding behind a managed service. A strong answer is not "Redis has these features" — it is "here is why each design decision is made and what it costs."

Clarifying questions (scope it first)

Before designing, pin down the use case — the answer changes a lot depending on it:

  • Cache or system of record? A pure cache can lose data on crash (cheap, fast); a primary datastore needs real durability and changes the persistence/replication answer.
  • Read-heavy or write-heavy? Read-heavy favors replicas and client-side caching; write-heavy stresses the single thread and persistence I/O.
  • One dataset bigger than one machine's RAM? If yes, you need Cluster (sharding); if no, a single primary + replicas is simpler.
  • Latency target and consistency tolerance? Sub-ms p99 and "stale reads OK" point to async replicas; "read-your-writes" points to the primary or WAIT.

Requirements

Functional

  • GET / SET / DEL with optional TTL (per-key expiry).
  • Rich data structures: string, hash, list, set, sorted set (zset), plus streams.
  • Atomic operations (e.g. INCR, LPUSH) and multi-command transactions / Lua scripts.
  • Pub/Sub messaging.
  • Optional persistence so data survives a restart.

Non-functional

  • Sub-millisecond latency for point operations; very high throughput (100k+ ops/s per node).
  • High availability — survive a node failure with automatic failover.
  • Horizontal scalability beyond a single machine's RAM.
  • Tunable durability — from "pure cache, lose-on-crash" to "fsync every write".

Back-of-the-envelope estimation

Sizing a cache cluster for a busy web backend:

  • Working set: 100M keys, avg value ~1 KB → ~100 GB of data; with ~20% overhead ~120 GB.
  • Memory per node: on 64 GB nodes, shard across ~3-4 primaries (~30-40 GB each), each with 1-2 replicas → ~8-10 nodes total.
  • Throughput: one node sustains ~100k-200k ops/s; a 1M ops/s peak needs ~6-10 shards.
  • Network: 1M ops/s × ~1 KB ≈ 1 GB/s — plan for 10 GbE and use pipelining to amortize round-trips.
  • Persistence I/O: AOF everysec writes ~ write-QPS × value size to disk; budget disk space and IOPS for the rewrite spike.

Worked example. Say each value is ~1 KB and we hold 100M keys: that is ~100 GB of payload. Redis per-key overhead (the dictionary entry, the object header, the expiry entry) is roughly tens of bytes per key, so 100M keys adds a few GB of bookkeeping on top — never size memory at exactly the payload size, always leave 20-30% headroom for overhead, fragmentation, and the fork copy-on-write spike during snapshots. At 1M ops/s with ~1 KB values the wire traffic is ~1 GB/s each way, so the NIC (10 GbE ≈ 1.25 GB/s) becomes the limit before the CPU does — which is exactly why pipelining (batching many commands per round-trip) and client-side caching matter more than raw command speed.

Core APIs

Redis exposes commands over RESP (TCP), not REST. The surface a client relies on:

  • Strings / counters: SET key val [EX ttl], GET key, DEL key, INCR key, EXPIRE key ttl
  • Hash: HSET key field val, HGET key field — store objects.
  • List: LPUSH key val, RPOP key — queues.
  • Sorted set: ZADD key score member, ZRANGE key a b, ZREVRANK key member — leaderboards.
  • Pub/Sub: SUBSCRIBE ch, PUBLISH ch msg.
  • Cluster / durability: CLUSTER SLOTS, WAIT numreplicas timeout (block until replicated).

High-level architecture

A single Redis node is conceptually simple: clients speak a compact wire protocol (RESP) over TCP to a server whose heart is a single-threaded command processor operating on an in-memory keyspace. Around that core sit the persistence engine, the replication stream, and (in a cluster) the slot-routing layer.

The single-threaded event loop

The defining design choice: command execution is single-threaded. Redis multiplexes thousands of connections with an event loop (epoll/kqueue) and executes one command at a time. This sounds counter-intuitive but is the source of much of Redis's simplicity and speed:

  • No locks, no race conditions on the keyspace — every command is atomic by construction.
  • RAM access is so fast that the bottleneck is the network and syscalls, not CPU. I/O multiplexing keeps the single core busy.
  • Avoids context-switch and lock-contention overhead that would dominate at this latency scale.

Where threads are used: modern Redis offloads slow side-tasks to background threads — closing large keys (UNLINK / lazy-free), fsync of the AOF, and optional I/O threads for reading/writing sockets. The command logic itself stays single-threaded.

Pipelining vs the round-trip tax. Because the bottleneck is network round-trips, not CPU, the single biggest client-side win is pipelining: send N commands without waiting for each reply, so N requests cost one round-trip instead of N. A loop of 10k individual SETs over a 1 ms RTT link takes ~10 s of pure waiting; pipelined, it is a few ms. This is also why MGET/MSET and Lua scripts (which run server-side, atomically) are preferred over chatty per-key calls.

What this buys and what it costs. The single thread gives you atomicity for free — a Lua script or MULTI/EXEC transaction runs to completion with no other command interleaving — but it also means one slow command stalls everyone. A single KEYS * on 100M keys, a 1M-element ZRANGE, or a heavy Lua script blocks the whole server for its entire duration. The design rule that follows: keep every command O(small), and push large scans to SCAN/cursor-based iteration.

Data structures & memory

Redis is "data structures as a service". Each value type is backed by a specialized internal encoding that switches as data grows, trading memory for speed:

TypeUsed forNotable encodings
stringcache values, countersint, embstr, raw
hashobjects / fieldslistpack then hashtable
listqueues, timelinesquicklist (linked listpacks)
setunique membershipintset / listpack / hashtable
zsetleaderboards, rate limitslistpack then skiplist + hashtable

The sorted set is worth a closer look because it powers leaderboards and time-ranged queries. It keeps two structures in sync: a hashtable (member to score, O(1) lookup) and a skip list (ordered by score, O(log n) range queries).

Why the encodings matter. A small hash or zset is stored as a compact listpack (a flat, cache-friendly array) and only "upgrades" to a hashtable/skiplist once it crosses a size threshold. This is a deliberate memory/speed trade: tiny collections stay tiny in RAM; large ones pay for the index. It is also a footgun — a key that slowly grows past the threshold suddenly costs more memory, and a single huge collection becomes a "big key" that blocks the thread on access or delete.

Two worked uses:

  • Sliding-window rate limiter (zset): store request timestamps as scores in rl:user:42; on each request ZADD now, ZREMRANGEBYSCORE to drop entries older than the window, then ZCARD to count — all O(log n), atomic in one Lua script.
  • Object cache (hash): store a user as fields in user:42 so you can read/update one field without serializing the whole object, and set a TTL on the key for expiry.

Persistence: RDB vs AOF

Pure in-memory data is lost on restart. Redis offers two complementary persistence modes:

  • RDB (snapshot): periodically fork() the process and dump a point-in-time binary image of the dataset. Compact, fast to load, great for backups — but you can lose the writes since the last snapshot.
  • AOF (append-only file): log every write command to a file; replay it on startup. More durable (configurable fsync policy: always / everysec / no), but the file grows and must be periodically rewritten (compacted).

Production setups often run both: AOF for durability, RDB for fast restart and backups.

The fork trick: snapshotting and AOF rewrite use fork() + copy-on-write. The child writes a consistent view to disk while the parent keeps serving traffic; only pages modified during the dump are duplicated. The cost is a memory spike (a write-heavy workload during the dump can nearly double RSS) and a brief fork pause on very large datasets — a real production gotcha on big instances.

The AOF fsync policy is the core durability vs throughput knob:

fsync policyDurability on crashThroughput cost
alwayslose ~0 (every write flushed)high — an fsync per write
everyseclose up to ~1 s of writeslow — the usual balance
nolose whatever the OS hasn't flushedlowest — OS decides

Even with always, "durable" means written to the local disk of one node — surviving a whole-node loss is the job of replication, not persistence. The two are complementary: persistence protects against restart, replication against node death.

Replication & failover

For read scaling and availability, a primary asynchronously replicates to one or more replicas. A replica first does a full sync (the primary sends an RDB snapshot), then streams subsequent writes from a replication backlog buffer. Replication is asynchronous, so a replica can lag slightly behind — a deliberate latency/consistency trade-off.

To make failover automatic, Redis Sentinel processes monitor the primary; on agreement (quorum) that it is down, they elect a new primary from the replicas and reconfigure clients.

Full sync vs partial resync. The first time a replica connects it does a full sync (the primary forks an RDB and ships it, then streams the backlog). If a replica briefly disconnects, it can do a partial resync — it asks for everything after the last replication offset it saw, served from the primary's in-memory replication backlog buffer. Size that buffer for your worst expected blip; if the replica falls further behind than the buffer holds, it is forced into an expensive full sync again.

The failure mode that bites people: because replication is asynchronous, a primary can acknowledge a write to the client and then crash before that write reached any replica — on failover the new primary never had it, so the write is silently lost. Redis is therefore not a strongly-consistent store by default. Mitigations: WAIT numreplicas timeout blocks the write until N replicas confirm (turning it into a slower, quorum-ish write), and replicas should be in different failure domains so one rack/AZ loss does not take the primary and all replicas together.

Horizontal scaling: Redis Cluster

One node is bounded by a single machine's RAM and CPU. Redis Cluster shards the keyspace across nodes using 16384 hash slots: slot = CRC16(key) mod 16384. Each primary owns a contiguous range of slots (and has its own replicas). Clients cache the slot to node map and talk directly to the right node; if a key has moved, the node replies with a MOVED redirect.

Why fixed slots and not consistent hashing of nodes? Slots decouple the key space from the node count. Adding a node is "give it some slots"; the migration unit is a slot, and only keys in moved slots are affected — keeping resharding incremental and online.

Multi-key operations and hash tags. A command touching several keys (e.g. MGET a b c, a transaction, a Lua script) only works if all those keys live in the same slot — otherwise Redis rejects it with a cross-slot error. To force related keys together you use a hash tag: only the part in braces is hashed, so user:{42}:profile and user:{42}:sessions land in the same slot and can be operated on atomically. This is a real constraint to call out: Cluster trades away cross-shard transactions.

Online resharding (MOVED vs ASK). While a slot is migrating, some keys are on the old node and some on the new. A client hitting the old node for an already-moved key gets a MOVED (update your map permanently) or, for a key mid-migration, an ASK redirect (one-shot, do not cache). This is how Cluster reshards while still serving traffic — no global lock, no full rehash.

Eviction & expiry

As a cache, Redis must stay within a memory budget (maxmemory). Two mechanisms reclaim space:

  • Expiry: keys with a TTL are removed lazily (on access) and by a background sampler that probabilistically scans for expired keys.
  • Eviction: when at the memory limit, a policy decides what to drop — noeviction (reject writes), allkeys-lru, allkeys-lfu, volatile-ttl, etc. Redis uses approximate LRU/LFU (samples a handful of keys) to avoid the cost of exact bookkeeping.

Storage & technology choices

Redis is itself the building block, so the "tech choice" is when to reach for it and what to pair it with:

  • Redis vs Memcached: Memcached is a simpler multi-threaded string cache; pick Redis when you need data structures, persistence, replication, or pub/sub. (Dragonfly / KeyDB are multi-threaded, Redis-compatible alternatives.)
  • Cache-aside with a primary DB: the most common pattern — Redis caches in front of PostgreSQL / Cassandra; the app reads cache, falls back to the DB, and writes invalidate or update the cache.
  • As a component inside other designs: session/presence registry (chat, Zoom), feed cache (news feed), rate limiter, geo index of hot locations (Grab/Uber), leaderboard (gaming), prefix cache (LLM serving).
  • Streams vs Kafka: Redis Streams suit lightweight, in-process queues; reach for Kafka when you need high-throughput, durable, replayable logs across many consumers.

Consistency & guarantees

It is worth stating Redis's guarantees explicitly, because interviewers probe them:

  • Single-command atomicity: every command — and every Lua script / MULTI/EXEC block — executes atomically on the one thread. No partial updates, no interleaving.
  • No multi-key transactions across shards: in Cluster, atomicity is only within a slot (hence hash tags).
  • Asynchronous replication = possible data loss on failover (see above). With Sentinel/Cluster, Redis chooses availability on partition (AP-leaning), not strong consistency; WAIT tightens this but cannot make it fully linearizable.
  • At-most-once Pub/Sub: classic Pub/Sub is fire-and-forget — a disconnected subscriber misses messages. Use Streams (consumer groups, acks, replay) when you need at-least-once delivery.

When (not) to use Redis

  • Great for: caching, sessions, rate limiting, leaderboards, counters, ephemeral queues, real-time presence — anything that fits in RAM and benefits from sub-ms latency.
  • Be careful for: a primary system of record with strict durability (acknowledged-write loss on failover is real) — pair it with a durable database or accept the trade-off.
  • Wrong tool for: datasets far larger than RAM where most data is cold (use a disk-based store), complex multi-key/relational queries, or strong cross-shard transactions.

Pitfalls & talking points

  • Hot key: a single key serving millions of ops can saturate one node (and one slot cannot be split). Mitigate with client-side caching, read fan-out to replicas, or splitting the value across keys.
  • Big key: a huge value blocks the single thread when accessed or deleted — use UNLINK (lazy free) and avoid unbounded collections.
  • Blocking commands: KEYS *, large ZRANGE, or Lua scripts run on the one thread and stall everyone — prefer SCAN and bounded operations.
  • Persistence latency: fsync=always hurts throughput; everysec is the usual balance.
  • Replica lag: reads from a replica may be stale; route read-your-writes to the primary.
  • Cache stampede: when a hot key expires, many clients miss and hit the database at once — use a short lock / single-flight on recompute, or stagger TTLs.
  • Unbounded growth: a list/zset/stream with no trimming silently grows into a big key — cap it (LTRIM, XADD ... MAXLEN) and always set TTLs on cache keys.

Key takeaways

  • A single-threaded event loop over an in-memory keyspace gives atomicity for free and makes the network the bottleneck, not CPU.
  • Specialized data-structure encodings trade memory for speed and switch as data grows.
  • RDB + AOF are complementary durability knobs; both lean on fork() + copy-on-write.
  • Async replication + Sentinel give read scaling and automatic failover.
  • 16384 hash slots make Redis Cluster shard and reshard incrementally; cross-slot atomicity needs hash tags.
  • Know the guarantees: per-command atomicity, but async replication means an acknowledged write can be lost on failover — Redis leans AP, and WAIT only tightens it.
  • Pick the right job: cache/sessions/rate-limit/leaderboard yes; strict system-of-record durability and cross-shard transactions, think twice.
