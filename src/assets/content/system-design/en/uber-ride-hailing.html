Uber-style ride-hailing matches riders to nearby drivers in real time, tracks the trip, and prices it. It shares geospatial foundations with food delivery but centers on driver-rider matching, the trip lifecycle, and surge pricing.

The defining tension is the same hot-ephemeral-vs-transactional split as delivery, but the matching problem is sharper: a driver is a single physical resource that exactly one rider can claim, and a wrong claim means two riders think the same car is coming. So the core is a real-time geo index (millions of pings/s, in memory) feeding a matcher whose job is to atomically assign one driver to one trip — a distributed single-winner problem — while the trip itself is a durable state machine carrying money. Everything is also inherently regional: matching never needs a global view, which is what makes it scale.

Clarifying questions (scope it first)

  • Match objective? Lowest ETA, highest driver utilization, or pooled rides? That changes whether matching is greedy-nearest or batched optimization.
  • Pooled / shared rides? If one car carries multiple riders, matching becomes routing with detour constraints, not 1:1.
  • Surge model? Real-time supply/demand pricing per cell requires a streaming aggregation layer; flat pricing does not.
  • Region scope and HA? Per-city/region sharding (the norm) vs cross-region — and what happens to in-flight trips if a region fails.
  • Payment flow? Authorize at request, capture at completion, handle cancellation fees — defines the trip saga.

Requirements

Functional

  • Request a ride; match a nearby driver; live-track the trip.
  • Fare estimate and surge; payment; rating.

Non-functional

  • Low matching latency; real-time location.
  • Consistent trip state (one driver per trip).
  • Regional high availability.

Back-of-the-envelope estimation

  • Driver pings: 5M active drivers every 4s → ~1.25M location writes/s as a global peak target — the dominant stream; shard by region/cell (matching never queries globally), kept in an in-memory geo store.
  • Ride requests: 5M rides/day ≈ ~60/s average, peaks at rush hour and in dense zones.
  • Matching: a request scans only nearby geo cells — bounded work even though the global driver set is huge.
  • Hotspots: downtown / airport / events concentrate supply and demand — shard cells and rate-limit.

Worked example. Look at why matching scales despite a huge location firehose. 5M drivers pinging every 4s is ~1.25M writes/s globally — but it is never one global index: you shard the geo store by region/cell, so each shard holds a city's worth of drivers and a match query reads only the requester's H3 cell + ring of neighbors (a few cells, dozens of candidate drivers). So the per-request work is tiny and constant regardless of the 5M global total — the firehose is partitioned, the query is local. The hard part isn't volume, it's the claim: when the matcher offers a driver, it does an atomic conditional write ("set driver→trip only if driver is free") with a short TTL and a fencing token, so if two nearby requests target the same driver, exactly one wins and the other instantly retries the next candidate. Add a location staleness filter (ignore pings older than, say, 10s) so you never dispatch to a driver who has gone offline. That combination — partitioned hot geo index + atomic claim — is the whole matching design.

Core APIs

  • POST /rides — {rider_id, pickup, dropoff} → {ride_id, state, eta}.
  • POST /drivers/{id}/location — high-frequency ping.
  • GET /rides/{id} → trip state + driver location.
  • GET /fare/estimate?pickup=&dropoff= → fare + surge multiplier.

High-level architecture

Geo index and nearest driver

Driver positions update constantly, so they live in an in-memory geo store keyed by cell id (H3 / geohash / QuadTree). A ride request maps pickup to a cell and reads that cell plus neighbors to get candidate drivers — turning "nearest driver" into a few key lookups instead of a global scan.

Matching and dispatch

Matching scores nearby drivers (distance, ETA, direction, rating) and offers the ride. To avoid assigning one driver to two requests, the dispatch locks/claims a driver during the offer; a decline or timeout releases them. Batching requests over a short window enables better global assignments in dense areas.

The claim must be atomic: a conditional write on the driver's available state with a short TTL and a fencing token, so if the driver app disconnects or ignores the offer, the claim expires and the driver is re-offered — and a stale acceptance carrying an old token is rejected. Candidate drivers are also filtered by last_ping age, heading, and availability so stale pings do not cause bad matches.

Ride-specific concerns

Beyond the shared geo/dispatch core, ride-hailing has its own depth: pickup ETA and routing (turn-by-turn, re-route on traffic), cancellation / no-show handling and fees, pooled rides (matching multiple riders on one route), payment auth at request then capture at completion, driver repositioning / supply shaping toward demand, and airport/event queues (FIFO driver lines). These distinguish it from food delivery, where the route is merchant-to-eater and there is no shared trip.

Trip lifecycle

A trip is a state machine; transitions are persisted and idempotent so retries and reconnects are safe.

Surge pricing

When demand exceeds supply in a cell, a surge multiplier raises the price to balance the market (and attract drivers). Surge is computed per geo cell from the live supply/demand ratio and applied at fare-estimate time. It is intentionally local and time-windowed.

Storage & technology choices

  • API gateway: auth, rate limiting, routing across rider/driver apps.
  • Driver locations + claims: Redis (geo + conditional claim with TTL/fencing) — the ~1.25M pings/s hot, ephemeral store; an H3 index keys the cells.
  • Trips: the trip state machine is a consistency boundary → prefer PostgreSQL / sharded SQL for transitions and idempotency. Cassandra/Scylla is great for append-only trip history, and acceptable for the state machine only with conditional writes/LWT, a single writer per trip, or event-sourced state.
  • Events / pricing: Kafka for location and trip events; a stream processor (Flink) computes per-cell supply/demand for surge.
  • Routing / ETA: a routing service over a road graph (OSRM-style) + map tiles.
  • Payments: a payment service (auth at request, capture at completion); blob storage for receipts.

Why these: location is a firehose + needs atomic claim → Redis; trip state needs reliable transitions → a transactional DB; surge is a real-time aggregation → Kafka + Flink. Same access-pattern split as a delivery system — the difference is the ride-specific routing/ETA and trip lifecycle, not the storage shapes.

Consistency & guarantees

  • One driver per trip (single-winner): the claim is an atomic conditional write with a TTL and fencing token — exactly one rider can hold a given driver; a stale or late acceptance is rejected by the fencing token.
  • Strongly consistent trip state: trip transitions (requested → matched → en route → started → completed) go through one authoritative store; reconnecting a dropped client resumes the same trip rather than creating a new one.
  • Idempotent payments: authorize at request, capture at completion, with idempotency keys so retries and cancellations don't double-charge; cancellation fees are a defined compensation.
  • Best-effort, eventually-consistent location: driver positions are last-write-wins with TTL and a staleness filter; lost pings are simply replaced, never recovered.
  • Regional availability over global consistency: matching and trips are sharded per region, so one region's failure doesn't stop others; there is no need for a globally consistent driver view.

When (not) to use this design

  • Fits: real-time matching of mobile supply to demand — ride-hailing, courier, roadside assistance — anywhere "find the nearest available unit and assign it exactly once" is the core.
  • Simplify when: scheduled/pre-booked rides with no live matching — a reservation system + batch assignment is enough, no geo firehose.
  • Different design when: there's no physical location to match (any non-spatial marketplace) — you don't need H3/geo indexes; or when matching is many-to-many optimization (logistics fleet planning), which is an offline solver, not real-time nearest-claim.

Pitfalls and talking points

  • Ping write storm: 1M+ pings/s never hit a database — in-memory geo store, persist sparsely.
  • Double assignment: claim/lock a driver during an offer; release on decline/timeout.
  • Hotspots: airport/events overload a cell — shard and rate-limit.
  • Trip consistency: persist idempotent state transitions; reconnect resumes the trip.
  • Surge fairness: compute locally and transparently; avoid oscillation with smoothing.

Key takeaways

  • An in-memory geo cell store makes nearest-driver lookups cheap.
  • Matching claims a driver during the offer to prevent double assignment.
  • The trip is an idempotent state machine.
  • Surge is a per-cell, time-windowed supply/demand signal.
