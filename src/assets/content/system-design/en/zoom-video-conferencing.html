Designing a video-conferencing system like Zoom is a real-time media problem: move audio and video between many participants with sub-150ms latency. The interesting decisions are about the media transport topology (mesh vs MCU vs SFU), signaling, bandwidth adaptation, and scaling a single meeting to hundreds of participants.

The key mental shift: this is not a request/response or store-and-forward system. Media is real-time UDP that is useless if late — a video frame that arrives 400ms behind is worse than dropped. So the usual tools (durable queues, retries, strong consistency) are the wrong reflexes; the design optimizes latency, bandwidth, and graceful degradation under loss, and the central question is just "who relays the packets and how many copies." Everything else (signaling, recording, chat) is a normal control-plane bolted onto that media core.

Clarifying questions (scope it first)

  • Meeting size? 1:1 and small calls can be peer-to-peer/mesh; large meetings (50-1000) force an SFU and cascading — the size target drives the whole topology.
  • Latency class? Interactive conferencing needs sub-150ms (SFU, UDP); one-to-many webinar/broadcast can tolerate seconds and use HLS/CDN instead.
  • Recording / compliance? Cloud recording, transcription, and retention add a server-side media pipeline and storage that pure relaying doesn't need.
  • E2E encryption required? True end-to-end encryption limits what the SFU and recording can do (it only forwards opaque packets) — a real product trade-off.
  • Network conditions? Mobile/lossy links make simulcast, bandwidth adaptation, and FEC/retransmission first-class, not optional.

Requirements

Functional

  • 1:1 and group calls; join via a meeting link.
  • Screen share, in-call chat, mute / camera toggle.
  • Recording to cloud.

Non-functional

  • Low latency: mouth-to-ear under ~150 ms.
  • Scale: hundreds of participants per meeting; millions of concurrent meetings.
  • Resilience to packet loss and variable bandwidth; global reach.

Back-of-the-envelope estimation

  • Bitrate: ~1-2 Mbps per HD video stream; audio ~50 Kbps.
  • Mesh blow-up: in an N-person mesh each client sends and receives N-1 streams → upload scales with N. At N=10 that is ~9× upload — infeasible on consumer links beyond a handful of people.
  • SFU offload: with an SFU each client sends 1 stream up and receives N-1 down. A 50-person HD meeting pushes ~50-100 Mbps down per viewer — hence simulcast + selective forwarding.
  • Server fan-out: one SFU forwarding 50 participants at ~2 Mbps handles ~50×49×... — capacity-plan by egress Gbps per SFU and shard meetings across SFUs.

Worked example. Compare a 10-person HD call (~2 Mbps/stream). In a full mesh each person uploads 9 streams = ~18 Mbps up and downloads ~18 Mbps — most home uplinks (~5-10 Mbps) simply can't, which is why mesh dies past ~4-5 people. With an SFU each client uploads exactly 1 stream (~2 Mbps) and downloads N-1; the cost moves to the server. Now scale the server: a 1000-person town hall where 1000 people watch but only ~5 speak — naive forwarding is 1000×~10 active streams, but with simulcast + last-N active-speaker forwarding the SFU only relays the few speakers' streams (at a resolution matched to each viewer), so egress is ~1000 viewers × ~2 Mbps ≈ 2 Gbps, which you spread across cascaded SFUs (regional edges each fanning out locally). This is why the answer to "scale a big meeting" is always selective forwarding + cascading, not a bigger box.

Core APIs

  • POST /meetings → {meeting_id, join_token}.
  • POST /meetings/{id}/join — returns ICE servers + assigned SFU edge.
  • Signaling (WebSocket): offer, answer, ice_candidate, publish, subscribe, mute.
  • Media (WebRTC): SRTP over UDP, negotiated via the signaling channel.

High-level architecture

Clients exchange session metadata over a signaling WebSocket, then send media over WebRTC to a regional SFU (Selective Forwarding Unit). TURN relays traverse NATs/firewalls; a recording pipeline and a chat sidecar hang off the meeting.

Transport topology: mesh vs MCU vs SFU

  • Mesh: every client sends to every other. No server media cost, but client upload explodes with N. Good only for 2-3 people.
  • MCU: server decodes all streams, composites one mixed stream, re-encodes per client. Cheap client bandwidth, but huge server CPU and added latency.
  • SFU: server forwards streams without decoding. Each client uploads once; the SFU relays to subscribers. Best balance — the modern default.

Simulcast and bandwidth adaptation

A publisher sends several quality layers (simulcast: e.g. high/medium/low). The SFU forwards the layer that fits each subscriber's measured bandwidth, and drops to a lower layer on congestion — so one slow viewer does not degrade everyone. This is the core trick that makes large SFU meetings work.

Scaling large meetings: cascading SFUs

One SFU is bounded by egress bandwidth and CPU. For very large meetings (or globally spread participants), cascade SFUs: each region has a local SFU, and SFUs relay between each other. A participant only connects to their nearest SFU, cutting cross-region traffic to one inter-SFU link per stream.

Recording, presence, chat

Recording subscribes to the SFU like a silent participant, composites or stores per-stream, and writes to blob storage. Presence and chat ride the signaling channel (or a sidecar) — low-volume compared to media.

Storage & technology choices

Concretely, what runs where — and which datastore for which job:

  • API gateway (e.g. Envoy / NGINX / a managed gateway): TLS termination, auth, rate limiting, and routing the "create/join meeting" REST calls — separate from the realtime media path.
  • Signaling: a stateful WebSocket service; the "which gateway/SFU holds this user" map lives in Redis (in-memory, TTL, fast).
  • Media (SFU): dedicated media servers (the open-source landscape: mediasoup, Janus, Jitsi, LiveKit) — CPU/bandwidth machines, no database.
  • TURN relay: coturn-style relays for NAT traversal.
  • Meeting metadata (rooms, participants, settings): a relational DB like PostgreSQL — small, structured, transactional.
  • Events / analytics (join/leave, quality samples): produced to Kafka, optionally aggregated with a stream processor (Flink) for real-time quality dashboards.
  • Recordings: large immutable files → blob/object storage (S3-like), fronted by a CDN for playback; never in a database.
  • Chat / presence: low volume — ride the signaling channel; persist chat in a wide-column store (Cassandra) keyed by meeting if history is required.

Why these: meeting metadata is small + relational → SQL; the session/presence map is hot + ephemeral → Redis; recordings are big + write-once + read-rarely → object storage + CDN; the event firehose is high-throughput append-only → Kafka (+ Flink). Media itself is not stored — it is forwarded.

Consistency & guarantees

  • Best-effort, latency-first media: media uses UDP (RTP) — packets may be lost or reordered, and late packets are dropped, not retried. The guarantee is "the freshest frame possible," not "every frame." Loss is hidden with FEC, selective retransmission (NACK), and concealment, not by blocking.
  • Eventually-consistent control plane: the participant list, mute state, and presence converge quickly but aren't strongly consistent — two clients may briefly disagree on who's speaking; the signaling server is the tiebreaker.
  • Reliable, ordered signaling: signaling messages (join, offer/answer, ICE) do need reliable ordered delivery — that's why they run over WebSocket/TCP, separate from media.
  • Recording is asynchronous: the recording pipeline is decoupled from the live call; a recording may lag or be assembled after the meeting ends, and its durability is the object store's, not the SFU's.

When (not) to use this design

  • SFU when: interactive multi-party calls (3-1000) needing low latency — the standard answer for conferencing.
  • Mesh/P2P when: 1:1 or tiny calls where you want minimal server cost and lowest latency, and uplinks can handle it.
  • MCU when: clients are too weak to decode many streams (compose one mixed stream server-side) — at high CPU cost; rarely the default now.
  • Not this at all: one-to-many broadcast/webinar with no interactivity is better served by HLS/DASH over a CDN (seconds of latency, massive cheap fan-out) — don't pay SFU costs for a passive audience.

Pitfalls and talking points

  • Never use mesh beyond ~3 people — client upload is the wall.
  • NAT/firewall: a meaningful fraction of clients need TURN relay; budget relay capacity.
  • One slow viewer: without simulcast, the SFU is forced to a low common quality — simulcast isolates per-subscriber.
  • Region selection: assign the SFU by client latency, not just geography.
  • E2E encryption conflicts with server-side compositing/recording — a deliberate trade-off.

Key takeaways

  • The SFU (forward, don't decode) is the sweet spot between mesh and MCU.
  • Simulcast + selective forwarding adapt per-subscriber and keep big meetings smooth.
  • Cascading SFUs scale participants and geography.
  • Signaling, recording, presence, and chat are cheap sidecars around the media path.
