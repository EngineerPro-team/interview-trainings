Redis là một in-memory data-structure store, dùng làm cache, database và message broker. Trong phỏng vấn, "design Redis" là dạng building-block: thay vì ghép các service có sẵn, bạn thiết kế phần lõi bên trong của một hệ thống. Chương này dựng một store kiểu Redis từ first principles — data model, engine thực thi single-threaded, persistence, replication, failover, horizontal scaling, và các consistency guarantee rơi ra từ những lựa chọn đó.

Lý do câu hỏi này phổ biến: nó buộc bạn lý luận trực tiếp về memory layout, ranh giới CPU/IO, và trade space giữa durability–availability–latency, không núp sau một managed service. Một câu trả lời mạnh không phải "Redis có các tính năng này" — mà là "đây là vì sao mỗi quyết định thiết kế được đưa ra và nó tốn gì."

Clarifying questions (chốt scope trước)

Trước khi thiết kế, chốt use case — câu trả lời đổi nhiều tuỳ theo nó:

  • Cache hay system of record? Cache thuần có thể mất data khi crash (rẻ, nhanh); một primary datastore cần durability thật và đổi câu trả lời persistence/replication.
  • Read-heavy hay write-heavy? Read-heavy ưu tiên replica và client-side caching; write-heavy gây áp lực lên single thread và persistence I/O.
  • Một dataset lớn hơn RAM một máy? Nếu có, cần Cluster (sharding); nếu không, một primary + replica đơn giản hơn.
  • Latency target và mức chịu stale? Sub-ms p99 và "stale read OK" → async replica; "read-your-writes" → primary hoặc WAIT.

Requirements

Functional

  • GET / SET / DEL kèm TTL tuỳ chọn (expiry theo từng key).
  • Data structures phong phú: string, hash, list, set, sorted set (zset), và streams.
  • Thao tác atomic (vd INCR, LPUSH) và transaction nhiều lệnh / Lua script.
  • Messaging kiểu Pub/Sub.
  • Persistence tuỳ chọn để dữ liệu sống sót qua restart.

Non-functional

  • Latency dưới một millisecond cho point operation; throughput rất cao (100k+ ops/s mỗi node).
  • High availability — chịu được một node chết với automatic failover.
  • Horizontal scalability vượt giới hạn RAM của một máy.
  • Durability điều chỉnh được — từ "cache thuần, mất khi crash" tới "fsync mỗi write".

Back-of-the-envelope estimation

Ước lượng cho một cache cluster phục vụ web backend tải cao:

  • Working set: 100M key, value trung bình ~1 KB → ~100 GB dữ liệu; cộng ~20% overhead ~120 GB.
  • Memory mỗi node: với node 64 GB, shard ra ~3-4 primary (~30-40 GB mỗi cái), mỗi primary 1-2 replica → tổng ~8-10 node.
  • Throughput: một node chịu ~100k-200k ops/s; peak 1M ops/s cần ~6-10 shard.
  • Network: 1M ops/s × ~1 KB ≈ 1 GB/s — cần 10 GbE và dùng pipelining để khấu hao round-trip.
  • Persistence I/O: AOF everysec ghi ~ write-QPS × value size xuống disk; tính dung lượng disk và IOPS cho spike khi rewrite.

Ví dụ có số. Giả sử mỗi value ~1 KB và giữ 100M key: đó là ~100 GB payload. Overhead mỗi key của Redis (dictionary entry, object header, expiry entry) cỡ vài chục byte/key, nên 100M key thêm vài GB bookkeeping nữa — đừng bao giờ size memory đúng bằng payload, luôn chừa 20-30% headroom cho overhead, fragmentation, và spike copy-on-write khi snapshot. Ở 1M ops/s với value ~1 KB, traffic dây ~1 GB/s mỗi chiều, nên NIC (10 GbE ≈ 1.25 GB/s) thành giới hạn trước CPU — đúng lý do pipelining (batch nhiều lệnh mỗi round-trip) và client-side caching quan trọng hơn tốc độ lệnh thô.

Core APIs

Redis expose command qua RESP (TCP), không phải REST. Bề mặt mà client dựa vào:

  • String / counter: SET key val [EX ttl], GET key, DEL key, INCR key, EXPIRE key ttl
  • Hash: HSET key field val, HGET key field — lưu object.
  • List: LPUSH key val, RPOP key — queue.
  • Sorted set: ZADD key score member, ZRANGE key a b, ZREVRANK key member — leaderboard.
  • Pub/Sub: SUBSCRIBE ch, PUBLISH ch msg.
  • Cluster / durability: CLUSTER SLOTS, WAIT numreplicas timeout (chờ tới khi replicate xong).

High-level architecture

Một node Redis về ý tưởng khá đơn giản: client nói chuyện qua một wire protocol gọn (RESP) trên TCP tới server mà trái tim là một command processor single-threaded thao tác trên keyspace nằm trong bộ nhớ. Bao quanh lõi đó là persistence engine, replication stream, và (trong cluster) lớp routing theo slot.

Event loop single-threaded

Lựa chọn thiết kế đặc trưng: command execution là single-threaded. Redis multiplex hàng nghìn connection bằng event loop (epoll/kqueue) và chạy một lệnh tại một thời điểm. Nghe phản trực giác nhưng đây là nguồn gốc của sự đơn giản và tốc độ của Redis:

  • Không lock, không race condition trên keyspace — mọi lệnh atomic theo thiết kế.
  • Truy cập RAM nhanh tới mức bottleneck là network và syscall, không phải CPU. I/O multiplexing giữ cho single core luôn bận.
  • Tránh chi phí context-switch và lock-contention vốn sẽ chiếm ưu thế ở mức latency này.

Thread được dùng ở đâu: Redis hiện đại đẩy các side-task chậm sang background thread — đóng key lớn (UNLINK / lazy-free), fsync AOF, và optional I/O thread cho việc đọc/ghi socket. Bản thân command logic vẫn single-threaded.

Pipelining vs thuế round-trip. Vì bottleneck là round-trip mạng, không phải CPU, thắng lợi lớn nhất phía client là pipelining: gửi N lệnh mà không chờ từng reply, nên N request tốn một round-trip thay vì N. Một vòng 10k SET riêng lẻ trên link RTT 1 ms tốn ~10 s chờ thuần; pipelined thì còn vài ms. Đây cũng là lý do MGET/MSET và Lua script (chạy server-side, atomic) được ưu tiên hơn gọi từng key.

Được gì và mất gì. Single thread cho atomicity miễn phí — một Lua script hay transaction MULTI/EXEC chạy tới hết mà không lệnh nào xen vào — nhưng cũng nghĩa một lệnh chậm làm nghẽn tất cả. Một KEYS * trên 100M key, một ZRANGE 1M phần tử, hay một Lua script nặng chặn cả server suốt thời gian chạy. Quy tắc thiết kế kéo theo: giữ mọi lệnh O(nhỏ), và đẩy scan lớn sang SCAN/iteration theo cursor.

Data structures & memory

Redis là "data structures as a service". Mỗi value type được hậu thuẫn bởi một encoding nội bộ chuyên biệt, tự đổi khi dữ liệu lớn lên, đánh đổi memory lấy speed:

TypeDùng choEncoding tiêu biểu
stringcache value, counterint, embstr, raw
hashobject / fieldlistpack rồi hashtable
listqueue, timelinequicklist (linked listpacks)
setmembership duy nhấtintset / listpack / hashtable
zsetleaderboard, rate limitlistpack rồi skiplist + hashtable

Sorted set đáng xem kỹ vì nó là nền cho leaderboard và truy vấn theo range thời gian. Nó giữ hai cấu trúc đồng bộ: một hashtable (member tới score, lookup O(1)) và một skip list (sắp theo score, range query O(log n)).

Vì sao encoding quan trọng. Một hash/zset nhỏ được lưu dưới dạng listpack gọn (mảng phẳng, thân thiện cache) và chỉ "nâng cấp" lên hashtable/skiplist khi vượt một ngưỡng kích thước. Đây là một trade memory/speed có chủ đích: collection nhỏ ở RAM nhỏ; collection lớn trả giá cho index. Cũng là một footgun — một key lớn dần vượt ngưỡng đột nhiên tốn nhiều memory hơn, và một collection khổng lồ thành "big key" chặn thread khi truy cập hoặc xoá.

Hai use thực tế:

  • Sliding-window rate limiter (zset): lưu timestamp request làm score trong rl:user:42; mỗi request ZADD now, ZREMRANGEBYSCORE bỏ entry cũ hơn window, rồi ZCARD đếm — đều O(log n), atomic trong một Lua script.
  • Object cache (hash): lưu một user thành các field trong user:42 để đọc/cập nhật một field mà không serialize cả object, và set TTL trên key cho expiry.

Persistence: RDB vs AOF

Dữ liệu thuần in-memory mất khi restart. Redis cho hai chế độ persistence bổ trợ nhau:

  • RDB (snapshot): định kỳ fork() process và dump một binary image của dataset tại một thời điểm. Gọn, load nhanh, hợp cho backup — nhưng có thể mất các write kể từ snapshot gần nhất.
  • AOF (append-only file): log mọi write command ra file; replay lại khi khởi động. Durable hơn (chính sách fsync điều chỉnh được: always / everysec / no), nhưng file phình to và phải định kỳ rewrite (nén lại).

Production thường chạy cả hai: AOF cho durability, RDB cho restart nhanh và backup.

Mẹo fork: snapshot và AOF rewrite dùng fork() + copy-on-write. Child ghi một view nhất quán ra disk trong khi parent vẫn phục vụ traffic; chỉ các page bị sửa trong lúc dump mới bị nhân đôi. Cái giá là spike memory (workload write-heavy lúc dump có thể gần gấp đôi RSS) và một fork pause ngắn trên dataset rất lớn — một gotcha production thật trên instance lớn.

Chính sách fsync của AOF là nút durability vs throughput cốt lõi:

fsync policyDurability khi crashChi phí throughput
alwaysmất ~0 (mỗi write flush)cao — một fsync mỗi write
everysecmất tối đa ~1 s writethấp — điểm cân bằng thường dùng
nomất phần OS chưa flushthấp nhất — OS quyết định

Ngay cả với always, "durable" nghĩa là đã ghi xuống disk local của một node — sống sót khi mất cả node là việc của replication, không phải persistence. Hai cái bổ trợ: persistence chống restart, replication chống node chết.

Replication & failover

Để scale read và tăng availability, một primary replicate bất đồng bộ tới một hoặc nhiều replica. Replica đầu tiên làm full sync (primary gửi một RDB snapshot), sau đó stream các write tiếp theo từ replication backlog buffer. Replication là asynchronous, nên replica có thể lag nhẹ — một đánh đổi latency/consistency có chủ đích.

Để failover tự động, các process Redis Sentinel monitor primary; khi đồng thuận (quorum) rằng nó chết, chúng bầu một primary mới từ các replica và cấu hình lại client.

Full sync vs partial resync. Lần đầu replica connect nó làm full sync (primary fork một RDB và ship đi, rồi stream backlog). Nếu replica rớt ngắn, nó có thể partial resync — xin mọi thứ sau replication offset cuối nó thấy, phục vụ từ replication backlog buffer trong memory của primary. Size buffer đó cho cú rớt tệ nhất dự kiến; nếu replica tụt xa hơn buffer chứa, nó bị ép full sync đắt lại.

Failure mode hay cắn người ta: vì replication bất đồng bộ, primary có thể ack một write cho client rồi crash trước khi write đó tới bất kỳ replica nào — khi failover primary mới chưa từng có nó, nên write mất âm thầm. Do đó Redis không phải strongly-consistent store mặc định. Giảm thiểu: WAIT numreplicas timeout chặn write tới khi N replica xác nhận (biến nó thành write chậm hơn, kiểu quorum), và replica nên ở các failure domain khác nhau để mất một rack/AZ không kéo cả primary lẫn replica đi cùng.

Horizontal scaling: Redis Cluster

Một node bị giới hạn bởi RAM và CPU của một máy. Redis Cluster shard keyspace ra nhiều node bằng 16384 hash slot: slot = CRC16(key) mod 16384. Mỗi primary sở hữu một dải slot liên tục (và có replica riêng). Client cache bản đồ slot tới node và nói trực tiếp với node đúng; nếu key đã chuyển đi, node trả về một redirect MOVED.

Vì sao slot cố định thay vì consistent hashing trên node? Slot tách key space khỏi số lượng node. Thêm node là "giao cho nó vài slot"; đơn vị migration là một slot, và chỉ key trong slot bị chuyển mới bị ảnh hưởng — giữ cho resharding incremental và online.

Thao tác multi-key và hash tag. Một lệnh đụng nhiều key (vd MGET a b c, một transaction, một Lua script) chỉ chạy được nếu mọi key đó nằm cùng slot — nếu không Redis từ chối với cross-slot error. Để ép các key liên quan về cùng chỗ, dùng hash tag: chỉ phần trong ngoặc nhọn được hash, nên user:{42}:profile và user:{42}:sessions rơi cùng slot và thao tác atomic được. Đây là một ràng buộc thật cần nêu: Cluster đánh đổi mất cross-shard transaction.

Resharding online (MOVED vs ASK). Trong lúc một slot đang migrate, vài key ở node cũ và vài key ở node mới. Client đập node cũ cho một key đã chuyển nhận MOVED (cập nhật map vĩnh viễn) hoặc, cho một key đang giữa migration, một redirect ASK (một lần, đừng cache). Đây là cách Cluster reshard trong khi vẫn phục vụ traffic — không global lock, không full rehash.

Eviction & expiry

Là cache, Redis phải nằm trong ngân sách memory (maxmemory). Hai cơ chế thu hồi không gian:

  • Expiry: key có TTL bị xoá lazy (khi truy cập) và bởi một background sampler quét xác suất tìm key hết hạn.
  • Eviction: khi chạm giới hạn memory, một policy quyết định bỏ gì — noeviction (từ chối write), allkeys-lru, allkeys-lfu, volatile-ttl, v.v. Redis dùng LRU/LFU xấp xỉ (sample vài key) để tránh chi phí bookkeeping chính xác.

Storage & technology choices

Redis bản thân là building block, nên "tech choice" là khi nào dùng nó và pair với gì:

  • Redis vs Memcached: Memcached là string cache multi-threaded đơn giản hơn; chọn Redis khi cần data structure, persistence, replication, hoặc pub/sub. (Dragonfly / KeyDB là alternative multi-threaded, tương thích Redis.)
  • Cache-aside với một primary DB: pattern phổ biến nhất — Redis cache đứng trước PostgreSQL / Cassandra; app đọc cache, fallback DB, và write invalidate hoặc update cache.
  • Như một component trong các thiết kế khác: session/presence registry (chat, Zoom), feed cache (news feed), rate limiter, geo index location hot (Grab/Uber), leaderboard (gaming), prefix cache (LLM serving).
  • Streams vs Kafka: Redis Streams hợp queue nhẹ, in-process; dùng Kafka khi cần log throughput cao, durable, replayable qua nhiều consumer.

Consistency & guarantees

Nên nêu rõ guarantee của Redis, vì interviewer hay hỏi sâu:

  • Atomicity từng lệnh: mọi lệnh — và mọi Lua script / block MULTI/EXEC — chạy atomic trên một thread. Không partial update, không interleaving.
  • Không có multi-key transaction xuyên shard: trong Cluster, atomicity chỉ trong một slot (nên cần hash tag).
  • Async replication = có thể mất data khi failover (xem trên). Với Sentinel/Cluster, Redis chọn availability khi partition (thiên AP), không strong consistency; WAIT siết chặt nhưng không làm nó fully linearizable.
  • Pub/Sub at-most-once: Pub/Sub cổ điển là fire-and-forget — subscriber bị rớt sẽ miss message. Dùng Streams (consumer group, ack, replay) khi cần at-least-once.

Khi nào (không) dùng Redis

  • Tốt cho: caching, session, rate limiting, leaderboard, counter, queue ephemeral, real-time presence — thứ gì vừa RAM và hưởng lợi từ latency sub-ms.
  • Cẩn thận với: một primary system of record cần durability nghiêm ngặt (mất write đã ack khi failover là thật) — ghép với một database durable hoặc chấp nhận trade-off.
  • Sai công cụ cho: dataset lớn hơn RAM nhiều mà đa số cold (dùng disk-based store), query multi-key/relational phức tạp, hoặc strong cross-shard transaction.

Pitfalls & điểm cần bàn

  • Hot key: một key phục vụ hàng triệu ops có thể bão hoà một node (và một slot không tách được). Giảm thiểu bằng client-side caching, fan-out read qua replica, hoặc tách value ra nhiều key.
  • Big key: một value khổng lồ chặn single thread khi truy cập hoặc xoá — dùng UNLINK (lazy free) và tránh collection không giới hạn.
  • Blocking command: KEYS *, ZRANGE lớn, hay Lua script chạy trên một thread và làm nghẽn tất cả — ưu tiên SCAN và thao tác có giới hạn.
  • Persistence latency: fsync=always giảm throughput; everysec là điểm cân bằng thường dùng.
  • Replica lag: read từ replica có thể cũ; route read-your-writes về primary.
  • Cache stampede: khi một hot key hết hạn, nhiều client cùng miss và đập database — dùng lock ngắn / single-flight khi recompute, hoặc stagger TTL.
  • Tăng không giới hạn: một list/zset/stream không trim âm thầm thành big key — cap nó (LTRIM, XADD ... MAXLEN) và luôn set TTL trên cache key.

Key takeaways

  • Một event loop single-threaded trên in-memory keyspace cho atomicity miễn phí và khiến network là bottleneck, không phải CPU.
  • Encoding data-structure chuyên biệt đánh đổi memory lấy speed và tự đổi khi dữ liệu lớn lên.
  • RDB + AOF là hai nút điều chỉnh durability bổ trợ nhau; cả hai dựa vào fork() + copy-on-write.
  • Async replication + Sentinel cho read scaling và automatic failover.
  • 16384 hash slot giúp Redis Cluster shard và reshard incremental; atomicity xuyên slot cần hash tag.
  • Nắm guarantee: atomic từng lệnh, nhưng async replication nghĩa một write đã ack có thể mất khi failover — Redis thiên AP, và WAIT chỉ siết thêm.
  • Chọn đúng việc: cache/session/rate-limit/leaderboard thì có; durability system-of-record nghiêm ngặt và cross-shard transaction thì cân nhắc.
