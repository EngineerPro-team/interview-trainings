Một Content Delivery Network (CDN) serve content từ server gần user, cắt latency và offload origin. Nó là building block đằng sau streaming, download lớn, và web asset nhanh. Các bài cốt lõi là request routing, một cache hierarchy, và invalidation.

Toàn bộ giá trị gói trong một con số — edge cache hit ratio — vì mọi thứ khác (latency, tải origin, chi phí) đều suy ra từ nó. Nên một thiết kế mạnh thực ra là lập luận về cách giữ hit ratio cao (routing, hierarchy, cache-key hygiene) và cách giữ đúng đắn khi content đổi (invalidation) mà không làm tụt nó.

Clarifying questions (chốt scope trước)

  • Static, dynamic, hay cả hai? Static asset cache hàng giờ/ngày; dynamic/personalized cần micro-TTL, edge compute, hoặc bypass cache — câu trả lời rất khác.
  • Public hay private content? Private buộc signed URL/cookie và access-aware cache key để response của một user không bao giờ serve cho người khác.
  • Update phải fresh tới mức nào? "Eventually (vài phút)" → TTL; "tức thì" → active purge hoặc versioned URL.
  • Profile kích thước object? Nhiều web asset nhỏ vs vài video segment khổng lồ đổi cách eviction, tiering, và xử lý range request.

Requirements

Functional

  • Cache và serve content static (và một phần dynamic) từ edge location.
  • Invalidate / purge content; origin shielding; TLS termination.
  • Signed URL cho access control.

Non-functional

  • Latency toàn cầu thấp; high availability.
  • Cache hit ratio cao (bảo vệ origin); egress bandwidth khổng lồ.

Back-of-the-envelope estimation

  • Hit ratio economics: edge hit ratio 95% nghĩa origin chỉ thấy 5% traffic — khác biệt giữa một origin và một meltdown.
  • PoP count: hàng trăm edge PoP toàn cầu để đa số user trong tầm vài chục ms.
  • Object mix: một tập nhỏ object hot serve đa số request (cache khắp nơi); một long tail pull on demand.
  • Egress: CDN serve phần lớn bytes internet — capacity là bandwidth ở edge, không phải compute.

Ví dụ có số — vì sao hit ratio chi phối. Giả sử tổng demand 10 Tbps. Ở hit ratio 95%, origin chỉ cần serve ~5% = ~500 Gbps; đẩy lên 99% thì origin tụt còn ~100 Gbps — giảm 5× chi phí origin/transit chỉ từ 4 điểm hit ratio. Đó là lý do vài phần trăm hit ratio đáng để bỏ nhiều effort (cache key tốt hơn, shielding, pre-positioning), và vì sao một lỗi cache-busting (vd query param theo user trong cache key) là thảm hoạ: nó có thể kéo ratio về 0 và làm cháy origin.

Core APIs

  • GET /{asset} — serve bởi edge gần nhất (trong suốt với client).
  • POST /purge — {url | tag} invalidate content cached.
  • Origin pull config: cache-control TTL, cache key, signed-URL rule.

High-level architecture

Một request client được route tới một edge PoP gần; khi miss, edge fetch từ một regional shield, cái này lại fetch từ origin — nên origin thấy rất ít traffic. Một control plane push config và purge khắp network.

Request routing

Đưa user tới một edge gần và healthy là việc đầu tiên. Hai kỹ thuật phổ biến:

  • Anycast: nhiều PoP announce cùng một IP; network route user tới cái gần nhất về topology. Đơn giản, failover nhanh, ít kiểm soát chính xác.
  • GeoDNS: DNS trả một edge IP khác dựa trên location / latency / health của resolver. Kiểm soát nhiều hơn, nhưng DNS caching làm thay đổi chậm.

Cache hierarchy

Một tier duy nhất sẽ stampede origin khi miss. Một hierarchy — edge rồi regional shield rồi origin — nghĩa nhiều edge share một shield, nên origin thấy một fetch mỗi object mỗi region, không phải mỗi edge. Mỗi tier áp cache key, TTL, và LRU eviction.

Private content và signed URL

Không phải mọi thứ đều public. Với content private, edge verify một signed URL hoặc signed cookie (HMAC kèm expiry) trước khi serve, và response được đánh dấu private/no-store hoặc cache dưới một cache key access-aware — nên một object private không bao giờ được serve cho user khác từ cache. Cache key chỉ gồm dimension access-safe; header user-specific để ngoài trừ khi response là private.

Cache miss flow

Invalidation và purge

Khi content thay đổi, copy cached cũ phải đi. Lựa chọn: TTL expiry (đơn giản, eventual), hoặc active purge mà control plane propagate tới mọi PoP (nhanh, nhiều việc hơn). Một purge đi tới control plane, fanout tới mọi PoP, và eventually consistent với ack/retry và một version/tag — nên global purge có latency và có thể fail một phần, đó là lý do versioned URL (content hash trong path) được ưu tiên: version mới là URL mới, nên cache không bao giờ serve bytes cũ và không cần purge.

Khi miss, edge áp request coalescing (single-flight): nhiều miss đồng thời cho cùng object gom thành một upstream fetch, ngăn cache stampede lên shield/origin.

Storage & technology choices

Một nhầm lẫn thường gặp: "CDN thực ra lưu data ở đâu?" Một CDN không có một database duy nhất — nó là một tiered cache đứng trước durable store của người khác. Data nằm ở nhiều tầng riêng biệt, mỗi tầng chọn theo access pattern:

  • Edge cache (storage của data plane): mỗi PoP giữ object cached trong một tiered local store — object hot trong RAM, tập warm lớn hơn trên SSD/NVMe — quản bởi cache engine (Varnish / NGINX / Apache Traffic Server) với eviction policy LRU/LFU. Đây là ephemeral và rebuild được: mất một PoP không mất data, chỉ mất cache warmth.
  • Origin (source of truth): bản durable nằm trong blob/object storage (S3-like / GCS) cho media và file lớn, hoặc origin server/DB của chính ứng dụng cho response dynamic. CDN không bao giờ sở hữu durability — nó cache cái origin sở hữu.
  • Cache index/metadata: một structure in-memory mỗi edge map cache key → vị trí object + TTL + ETag; đây là lookup "tôi có nó không và còn fresh không?", không phải một DB persisted.
  • Config & routing state: cache rule, origin mapping, và PoP health được phân phối tới edge qua một config store / control plane (kiểu etcd/Consul hoặc một push system proprietary); config GeoDNS/Anycast lái routing.
  • TLS certificate: cert per-domain lưu ở edge (và một secret store ở control plane) để PoP terminate HTTPS.
  • Logs & analytics: access log stream khỏi edge vào Kafka → một data warehouse / time-series store cho hit-ratio, billing, và traffic analytics — giữ ngoài request hot path.

Phần còn lại của landscape: đa số team mua một managed CDN (Cloudflare, Fastly, Akamai, AWS CloudFront, Google Cloud CDN) thay vì build; self-host nghĩa là chạy Varnish/NGINX/ATS ở mỗi PoP. Cho content dynamic/personalized, edge compute (Cloudflare Workers, Lambda@Edge, Fastly Compute) chạy logic tại PoP. Origin/app set Cache-Control và phát versioned URL để điều khiển tất cả những thứ trên.

Consistency & guarantees

CDN về bản chất là một cache eventually-consistent, và nói rõ điều đó là chiều sâu interviewer muốn:

  • Freshness là best-effort: tới khi TTL hết hạn hoặc purge tới, một edge có thể serve copy cũ. Cần freshness nghiêm ngặt thì câu trả lời là versioned URL (content mới = URL mới), không phải purge nhanh hơn.
  • Purge eventually consistent: global purge fanout với ack/retry và có thể fail một phần; thiết kế cho "đa số PoP trong vài giây, đuôi muộn hơn", không phải global truth tức thì.
  • Read-your-writes không giữ xuyên edge mặc định — user vừa upload có thể đập một PoP khác với object cũ; bind read đó vào versioned URL hoặc bypass cache.
  • Routing là xấp xỉ: Anycast theo BGP (có thể rơi vào PoP không lý tưởng do network policy); GeoDNS phụ thuộc location resolver và bị DNS caching làm chậm. Không cái nào đảm bảo PoP gần nhất thật sự.

Tradeoffs & khi nào không dùng CDN

  • Tốt cho: static asset, media segment, download lớn, software update, API response cacheable — thứ gì read nhiều hơn write rất nhiều.
  • Biên cho: content cá nhân hoá cao hoặc đổi nhanh (hit ratio thấp) — dùng micro-TTL + stale-while-revalidate hoặc edge compute, hoặc chấp nhận origin serve.
  • Sai cho: write path và strongly-consistent read — chúng đi origin/DB, không phải cache.

Pitfalls và điểm cần bàn

  • Cache stampede / thundering herd: nhiều miss cho cùng object đập origin cùng lúc — dùng request coalescing ở edge.
  • Hot vs long tail: push object hot khắp nơi; pull tail on demand.
  • Cache key design: chỉ gồm dimension có ý nghĩa; một key tệ (vd thứ tự query) phân mảnh cache.
  • Invalidation khó: ưu tiên versioned URL hơn global purge khi có thể.
  • Dynamic content: cache micro-TTL hoặc dùng edge compute; không phải mọi thứ cacheable.

Key takeaways

  • Routing (Anycast / GeoDNS) đưa user tới một edge gần, healthy.
  • Một cache hierarchy (edge tới shield tới origin) bảo vệ origin và nâng hit ratio.
  • Invalidation qua TTL, purge, hoặc — tốt nhất — versioned URL.
  • Capacity là edge bandwidth và hit ratio, không phải origin compute — vài điểm hit ratio đổi chi phí origin theo cấp số nhân.
  • CDN là một cache eventually-consistent: freshness best-effort, purge eventual — ưu tiên versioned URL cho đúng đắn.
  • Cache-key hygiene là chi tiết sống còn: một dimension theo user trong key phá hit ratio.
