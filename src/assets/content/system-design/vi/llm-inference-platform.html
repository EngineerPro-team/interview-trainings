Một LLM inference platform serve các large language model ở quy mô lớn: nó biến một dàn GPU đắt tiền thành một API latency thấp, throughput cao cho chat, completion và embeddings. Đây là bài building-block với một bottleneck khác thường — GPU — nên các quyết định thú vị xoay quanh batching, memory (KV cache), parallelism và scheduling, chứ không chỉ là web tier stateless. Nó cũng là nền cho các hệ thống agentic và RAG xây bên trên.

Mental model neo lại một câu trả lời tốt: một GPU là một pool cố định gồm compute và HBM memory, và việc của bạn là giữ nó bận mà không vỡ budget memory. Gần như mọi quyết định bên dưới — continuous batching, paged attention, parallelism — tồn tại để đẩy GPU utilization và tokens/sec lên trong khi giữ tail latency (TTFT/TPOT) trong giới hạn.

Clarifying questions (scope trước)

Kiến trúc đúng phụ thuộc nhiều vào workload, nên chốt các điểm này trước khi thiết kế:

  • Chat nhạy latency hay batch/offline? Chat tương tác tối ưu TTFT và stream token; batch (eval, embeddings, summarization) tối ưu throughput và chịu được queueing.
  • Một model hay nhiều? Một model hot duy nhất cho phép pack GPU chặt; nhiều model (hoặc LoRA adapter) cần routing, multiplexing, và policy cold-start/load.
  • Kích thước model so với GPU memory? Model vừa một GPU, hay cần tensor/pipeline parallelism qua nhiều GPU? Điều đó đổi cả serving topology.
  • Context length và output length? Context dài thổi phồng KV cache và chặn concurrency; prompt ngắn với output dài thì decode-bound.
  • Cần multi-tenant fairness không? Nếu có, cần quota per-tenant và một scheduler ngăn một request lớn làm đói các request khác.

Requirements

Functional

  • Serve request chat / completion, có token streaming (server-sent events).
  • Serve nhiều model và một endpoint embeddings.
  • Hỗ trợ passthrough function-calling và stop condition / max tokens.

Non-functional

  • TTFT thấp (time-to-first-token) và TPOT (time-per-output-token) ổn định.
  • Throughput cao (tokens/sec) và GPU utilization cao — GPU chính là chi phí.
  • Autoscaling dưới tải bursty; queueing nhẹ nhàng.
  • Multi-tenant fairness và quota.

Vì sao serve LLM khác biệt

Một request không phải một function call đơn lẻ. Generation có hai phase: một prefill xử lý toàn bộ prompt trong một lượt, rồi một vòng decode autoregressive phát ra một token mỗi step, mỗi step phụ thuộc tất cả token trước đó. Hai hệ quả chi phối toàn bộ thiết kế:

  • Một request chiếm GPU qua nhiều step (một step mỗi output token), không phải một phát.
  • Mỗi step phải đọc lại attention state của tất cả token trước — được cache trong KV cache, thứ chiếm phần lớn GPU memory.

Back-of-the-envelope estimation

Ước lượng cho model 13B tham số trên GPU 40 GB:

  • Weights: 13B params × 2 bytes (FP16) ≈ 26 GB — vừa một GPU 40 GB, còn ~14 GB cho KV cache.
  • KV cache: cỡ ~0.5-1 MB mỗi token cho model này; context 2k token ≈ ~1-2 GB mỗi request → chỉ ~7-14 request đồng thời mỗi GPU. KV cache, không phải compute, mới chặn batch.
  • Throughput: decode ~30-50 tokens/s mỗi sequence; khi batch, một GPU phát ra hàng trăm tới hàng nghìn tokens/s tổng.
  • Fleet: capacity quyết định bởi budget KV-cache đồng thời và context length, không phải QPS thô — giữ 1000 chat context 2k đồng thời cần cỡ ~70-140 GPU.

Worked example. Lấy model 13B trên GPU 40 GB: weights ăn ~26 GB, còn ~14 GB cho KV cache. Nếu một request 2k token cần ~1.5 GB KV, GPU chỉ giữ ~9 request đồng thời — nên budget memory, không phải FLOPs, quyết định batch size. Giả sử decode chạy ~40 tokens/s mỗi sequence: với batch 9, GPU phát ~360 tokens/s tổng. Để serve 1000 chat đồng thời cần ~1000/9 ≈ 112 GPU chỉ cho KV residency. Đây là lý do paged attention (không reserve contiguous per-request, ~4x ít waste hơn) và quantization (weights INT8/FP8 giải phóng HBM cho thêm KV) trực tiếp nâng concurrency: mỗi GB tiết kiệm trên weights hoặc fragmentation thành thêm request trong batch. Nó cũng cho thấy một request context 8k đắt ~4x một request 2k — context dài mới là sát thủ capacity thực sự.

Core APIs

  • POST /v1/chat/completions — {model, messages[], max_tokens, temperature, stream} → SSE stream các token delta (hoặc một response đầy đủ).
  • POST /v1/completions — completion từ prompt thô.
  • POST /v1/embeddings — {model, input[]} → vector.
  • GET /v1/models — liệt kê model đang serve.
  • Streaming: Server-Sent Events; mỗi event mang một token delta, kết thúc bằng done marker.

High-level architecture

Vòng đời request và streaming

Gateway authenticate, enforce quota, và route tới worker pool của model được yêu cầu. Worker chạy prefill, rồi stream token ra khỏi vòng decode ngay khi sinh ra — nên user thấy token đầu nhanh (TTFT thấp) dù câu trả lời đầy đủ mất lâu hơn.

Continuous batching

GPU chỉ hiệu quả khi công việc được batch. "Static" batching kiểu ngây thơ chờ gom đủ một batch, chạy tới khi xong, rồi mới nhận request mới — nên một request dài giữ chân các request ngắn và GPU idle ở đuôi. Continuous batching (còn gọi in-flight batching) thay vào đó hoạt động ở mức một decode step: sau mỗi step, request đã xong rời batch và request đang chờ gia nhập. Cách này giữ GPU luôn bão hoà và cắt mạnh latency hàng đợi.

KV cache và paged attention

Mỗi request đang chạy giữ một KV cache — các attention key/value theo từng token — tăng thêm một entry mỗi token sinh ra. KV cache, chứ không phải model weights, thường là bottleneck memory và nó giới hạn bao nhiêu request lọt vào một batch. Allocator cổ điển reserve một block liên tục cho max length của mỗi request, lãng phí memory. Paged attention mượn ý tưởng virtual memory của OS: chia cache thành các block cố định và cấp phát theo nhu cầu qua một block table, nên memory chỉ dùng cho token thực sự sinh ra và có thể share (vd giữa các beam hoặc một prompt prefix chung).

Parallelism cho model lớn

Một model quá lớn cho một GPU được chia ra nhiều GPU:

  • Tensor parallelism: shard ma trận của mỗi layer ra các GPU cùng hợp tác trên mỗi token (cần interconnect nhanh, vd NVLink).
  • Pipeline parallelism: đặt các layer khác nhau lên các GPU khác nhau và stream activation giữa các stage.

Hai cái kết hợp: tensor-parallel trong một node, pipeline-parallel giữa các node. Platform giấu chuyện này sau abstraction "worker" — một logical worker có thể là nhiều GPU.

Scheduling, autoscaling và queueing

Scheduler cân bằng hai mục tiêu mâu thuẫn: throughput (batch lớn) vs latency (đừng để request chờ). Nó admit nhiều request nhất mà KV-cache memory cho phép, ưu tiên để bảo vệ TTFT, và áp fairness theo từng tenant. Vì GPU khan hiếm và khởi động chậm (weights phải load), autoscaling là thô và queue-aware: scale theo queue depth / GPU utilization với warmup rộng rãi, và shed hoặc queue tải nhẹ nhàng khi tới giới hạn.

Tối ưu thêm

  • Prefix / prompt caching: tái dùng KV cache cho một system prompt chung giữa các request — thắng lớn về TTFT cho agent.
  • Speculative decoding: một draft model nhỏ đề xuất vài token mà model lớn verify trong một step, tăng tokens/sec.
  • Quantization: serve ở INT8/FP8 để nhét model lớn hơn và nhiều KV cache hơn mỗi GPU.
  • Multi-adapter (LoRA): serve nhiều fine-tune trên một base model bằng cách swap các adapter nhỏ.

Storage & technology choices

  • API gateway (Envoy / NGINX / Kong): auth, API key, rate limiting + quota theo tenant, route tới đúng model pool.
  • Serving runtime: GPU worker chạy một inference engine thật — vLLM (PagedAttention), NVIDIA TensorRT-LLM / Triton, hoặc TGI — implement continuous batching và KV cache.
  • Model weights: file lớn bất biến → blob/object storage (S3-like), pull về NVMe local và mmap vào GPU memory lúc warm-up; một model registry (metadata trong PostgreSQL) track version.
  • KV cache: nằm trong GPU HBM, không phải database — ephemeral theo request; prefix/prompt cache có thể back bằng Redis hoặc local store để tái dùng.
  • Queue: một queue in-memory/Redis nhanh (hoặc admission queue của scheduler) giữ request chờ slot batch.
  • Orchestration/autoscaling: Kubernetes + KEDA / autoscaler tuỳ chỉnh theo queue depth và GPU utilization.
  • Metrics/logs: Prometheus + Grafana cho TTFT/TPOT/utilization; usage event chảy qua Kafka tới consumer analytics/billing.
  • Usage ledger (source of truth cho billing): billing cần một record durable idempotent, không chỉ một Kafka event — một usage ledger / billing event store key theo request_id với token count cuối, dùng semantics upsert/finalize để crash worker, retry, hay replay consumer không double-count hay undercount. Kafka transport event; ledger là record authoritative để dựng invoice.

Vì sao chọn vậy: weights khổng lồ + write-once → object storage; KV cache là hot state latency-critical → GPU memory (tài nguyên khan hiếm bạn size quanh nó). Hot path sinh token cố ý không có DB quan hệ lớn — bottleneck là GPU memory. Usage tách khỏi path đó: Kafka transport usage event, còn billing source of truth là usage ledger idempotent, finalize lúc stream kết thúc (key theo request_id), không nằm trong per-token loop.

Consistency & guarantees

Serve LLM có profile guarantee khác một service CRUD thông thường:

  • Non-deterministic mặc định: với temperature > 0, cùng một prompt cho output khác nhau; reproducibility cần seed cố định và greedy decoding, và ngay cả vậy thứ tự floating-point/batching có thể làm kết quả lệch nhẹ.
  • At-most-once generation: một request không an toàn để retry mù — một response stream dở dang bị fail nên restart sạch, không resume giữa stream, và các tool call có side-effect phải tự mang idempotency. Bill theo token thực sự gửi tới client, finalize idempotent trong usage ledger key theo request_id để crash hay retry không double-charge cũng không mất usage.
  • Không có cross-request transaction: mỗi request độc lập; shared state duy nhất là weights read-only và một prefix cache tùy chọn, vốn chỉ là tối ưu (miss thì recompute).
  • Fairness, không phải ordering nghiêm ngặt: scheduler bảo đảm quota/fairness giữa tenant, không phải FIFO — một request ngắn có thể vượt một request dài. Nói rõ điều đó thay vì hứa ordering.

Khi nào (không) nên dùng một inference platform riêng

  • Tự xây khi: bạn serve model của mình/open model ở quy mô lớn, cần kiểm soát chi phí GPU, TTFT thấp/ổn định, quota multi-tenant, hoặc data-residency loại bỏ third-party API.
  • Đừng bận tâm khi: traffic thấp hoặc spiky và một hosted API (OpenAI/Anthropic/Bedrock) rẻ hơn GPU nằm không — quản fleet GPU là chi phí vận hành thật.
  • Sai khung khi: task là ML cổ điển (ranking, classifier nhỏ) — không cần hạ tầng autoregressive decode; hoặc khi latency cần dưới 10ms, điều generation từng token không đạt được.

Pitfalls và điểm cần bàn

  • KV cache là giới hạn: batch size bị chặn bởi memory, không phải compute — tính capacity theo context length, không chỉ QPS.
  • Long context làm nổ memory: một prompt 100k token là một KV cache khổng lồ; cô lập hoặc rate-limit nó.
  • Cold start: load hàng chục GB weights mất thời gian — giữ warm pool, đừng scale từ zero dưới tải.
  • Tail latency: một generation rất dài trong batch làm chậm TPOT của mọi người — cap max tokens, cân nhắc priority lane.
  • TTFT vs throughput: batch lớn tăng throughput nhưng có thể hại TTFT — tune admission, đừng tối đa batch một cách mù quáng.

Key takeaways

  • Serve LLM là GPU-bound và stateful theo từng request (KV cache), khác web tier stateless thường gặp.
  • Continuous batching ở mức decode-step giữ GPU bão hoà và cắt latency.
  • Paged attention quản KV cache như paging của OS — không over-reserve, block share được.
  • Tensor + pipeline parallelism serve model lớn hơn một GPU.
  • Scheduling đánh đổi TTFT vs throughput; autoscaling phải tính tới warmup và queue.
