Blob (object) storage như Amazon S3 lưu bytes tuỳ ý dưới tên bucket/key với durability cực cao ở quy mô exabyte. Bài building-block này bao gồm write/read path, replication vs erasure coding, metadata sharding, multipart upload, và garbage collection.

Insight cốt lõi là tách metadata khỏi data và coi chúng là hai bài toán khác nhau: metadata nhỏ, nhiều, cần lookup indexed nhanh; data khổng lồ, bất biến, cần bytes durable rẻ. Gần như mọi quyết định thiết kế (sharding, durability scheme, consistency) suy ra từ sự tách đó, nên câu trả lời mạnh giữ hai plane này tách biệt xuyên suốt.

Clarifying questions (chốt scope trước)

  • Profile kích thước object? Đa số object nhỏ (KB) gây áp lực lên metadata và overhead per-object; media lớn (GB-TB) gây áp lực lên data path và cần multipart + chunking.
  • Mix read/write/delete và hot vs cold? Hot read-heavy muốn replication; cold archival muốn erasure coding cho cost.
  • Kỳ vọng consistency? Read-after-write cho object mới là chuẩn; còn overwrite và list-after-write (thường yếu hơn)?
  • Target durability/availability? Durability "11 nines" và failure model regional/AZ chi phối lựa chọn replication/EC và placement.

Requirements

Functional

  • PUT / GET / DELETE một object; LIST một bucket.
  • Multipart upload cho object lớn; versioning; presigned URL.

Non-functional

  • Durability ~11 nines; high availability.
  • Scale tới exabyte và hàng nghìn tỷ object.
  • Read-after-write consistency cho object mới.

Back-of-the-envelope estimation

  • Durability math: với tỉ lệ hỏng đĩa ~0.8%/năm, 3 replica cho ~6 nines; erasure coding (vd 8+4) đạt ~11 nines — lý do EC được ưu tiên cho cold data.
  • Storage overhead: 3x replication = 200% overhead; erasure coding 8+4 = 50% overhead — chênh lệch chi phí lớn ở quy mô exabyte.
  • Metadata: nghìn tỷ object × ~1 KB metadata = petabyte chỉ riêng metadata — phải shard.
  • Object size spread: từ nhỏ xíu (KB) tới khổng lồ (TB) — đóng gói object nhỏ vào file lớn; chia object lớn thành chunk.

Ví dụ có số — chi phí replication vs erasure coding. Để lưu 1 EB data dùng được: 3× replication cần ~3 EB disk thô (200% overhead) nhưng một copy bất kỳ serve read với latency thấp. Erasure coding 8+4 cần ~1.5 EB thô (50% overhead) — tức nửa phần cứng ở quy mô exabyte, tiết kiệm khổng lồ — nhưng một read có thể phải fetch và decode k=8 shard (nhiều IO + CPU + tail latency), và mất một shard kích hoạt reconstruction read qua 8 node. Rule of thumb: replication cho hot/latency-sensitive, erasure coding cho cold/cost-sensitive, và re-encode object replicated sang EC khi chúng nguội.

Core APIs

  • PUT /{bucket}/{key} — body là object → {etag, version_id}.
  • GET /{bucket}/{key} → bytes object.
  • DELETE /{bucket}/{key}; GET /{bucket}?list&prefix= → keys.
  • Multipart: POST .../uploads (init), PUT part, POST complete.

High-level architecture

Tách metadata khỏi data để mỗi cái scale độc lập: một API tier stateless, một metadata service sharded (key tới location), và data node lưu bytes thực tế dưới dạng append-only chunk.

Write path

Khi PUT, API chọn một placement group, ghi bytes tới vài data node, chờ một write quorum ack durable, rồi commit metadata entry. Read-after-write giữ được vì metadata chỉ commit sau khi data đã durable.

Replication vs erasure coding

Hai cách sống sót qua hỏng đĩa:

  • Replication: giữ N bản copy đầy đủ. Đơn giản, recovery nhanh, read latency thấp — nhưng storage cost cao (3x = 200% overhead).
  • Erasure coding: chia object thành k data shard cộng m parity shard (vd 8+4); bất kỳ k trong k+m shard tái dựng được. Rẻ hơn nhiều (50% overhead cho 8+4) và durable hơn — nhưng reconstruction đọc vài shard, thêm latency.

Rule of thumb: replication cho hot/latency-sensitive, erasure coding cho cold/cost-sensitive.

Metadata sharding và listing

Metadata (key tới location, size, version) bản thân nó khổng lồ, nên được shard — thường theo hash của bucket+key. Điều đó làm point lookup O(1) nhưng làm LIST prefix khó (key bị rải rác). Cách sửa thường gặp: giữ một index riêng, range-partition theo key để listing, chấp nhận listing eventually consistent và chậm hơn GET.

Multipart upload

Upload object 5 TB trong một request thì mong manh. Multipart upload chia thành các part upload độc lập (và song song); khi complete, service ghép các part thành một object logic. Một part fail được retry riêng, không phải cả upload.

Garbage collection và lifecycle

Delete và overwrite để lại chunk orphan; một garbage collector thu hồi không gian không còn metadata entry live nào tham chiếu (mark-and-sweep). Một lifecycle manager tier object cold sang storage rẻ hơn (vd Glacier) và có thể re-encode data replicated sang erasure coding khi nó nguội đi.

Storage & technology choices

  • Managed: AWS S3, Google Cloud Storage, Azure Blob, Cloudflare R2 — default cho đa số team.
  • Self-hosted: MinIO (tương thích S3), Ceph, SeaweedFS; Haystack/f4 của Facebook là thiết kế in-house kinh điển.
  • Metadata layer: thường một sharded relational/KV store (vd FoundationDB, DynamoDB, hoặc sharded Postgres) — tách khỏi data node.
  • Pair với: một CDN đứng trước cho media read-heavy, và lifecycle tiering sang class cold (Glacier) cho archive.

Consistency & guarantees

  • Read-after-write cho object mới: đạt bằng cách chỉ commit metadata sau khi data write quorum durable — GET sau 200 luôn resolve. (S3 hiện đại làm strong cho mọi operation; hệ cũ thì eventual.)
  • Overwrite / delete khó hơn: với versioning, PUT tạo version mới và metadata pointer flip atomic; không versioning thì overwrite đồng thời cần last-writer-wins hoặc conditional write (If-Match trên etag).
  • Listing thường yếu hơn point read: index sắp theo key update bất đồng bộ, nên key vừa ghi có thể xuất hiện trong LIST hơi muộn.
  • Durability độc lập với availability: 11 nines durability (không mất bytes) không nghĩa 11 nines availability (có thể tạm không đọc được trong lúc failure) — nêu cả hai target riêng.

Tradeoffs & khi nào không dùng object storage

  • Tốt cho: blob lớn bất biến — media, backup, log, ML dataset, static asset (thường có CDN đứng trước).
  • Sai cho: record nhỏ mutable latency thấp (dùng database/KV), append-in-place hay edit một phần in-place (object bất biến — phải rewrite), hoặc strong cross-object transaction.
  • Cost lever: lifecycle-tier object cold sang class rẻ hơn và re-encode sang EC; đa số chi phí là storage-months, không phải request.

Pitfalls và điểm cần bàn

  • Metadata là bottleneck ở quy mô object — shard nó; bản thân nó là petabyte.
  • Listing đắt với hash sharding — giữ một index sắp xếp riêng.
  • Small-object overhead: đóng gói nhiều object nhỏ vào file append-only lớn để tránh chi phí per-object.
  • EC reconstruction cost: đọc cold data có thể đụng vài shard — ổn cho cold, không cho hot.
  • Read-after-write: chỉ commit metadata sau một durable write quorum.

Key takeaways

  • Tách metadata khỏi data; shard cả hai.
  • Replication cho hot data, erasure coding cho cold — durability vs cost.
  • Commit metadata sau một write quorum để read-after-write.
  • Multipart upload + GC + lifecycle tiering xử lý scale và cost.
  • Nêu rõ guarantee: read-after-write cho object mới (metadata commit sau durable data quorum); listing thường yếu hơn; durability ≠ availability.
  • Object bất biến — model update là version/overwrite mới, không edit in-place.
