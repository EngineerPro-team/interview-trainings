Collaborative editing kiểu Google Docs cho nhiều người cùng sửa một document và luôn hội tụ về cùng kết quả. Mấu chốt là conflict resolution cho edit đồng thời — Operational Transformation (OT) hoặc CRDT — cộng với per-document ordering, persistence, và presence.

Toàn bộ bài toán quy về một guarantee: convergence — cho cùng tập edit theo bất kỳ thứ tự delivery nào, mọi client phải kết thúc với document state giống nhau từng byte. Edit đồng thời vào cùng một vùng là ca khó: nếu Alice insert tại position 5 trong khi Bob delete position 3, apply ngây thơ sẽ diverge. OT và CRDT là hai câu trả lời cho "làm sao để op đồng thời commute." Tin tốt là scale nhẹ nhàng (một doc có vài editor), nên đây là bài toán correctness, không phải throughput — và thiết kế xoay quanh một authority per-document order và transform op.

Clarifying questions (scope trước)

  • Bao nhiêu editor đồng thời mỗi doc? Vài người (doc điển hình) cho phép dồn op qua một server per-doc; hàng trăm (một whiteboard chia sẻ live) cần cẩn thận hơn.
  • OT hay CRDT? OT (server trung tâm transform) đơn giản hơn phía server và đã chinh chiến cho text; CRDT cho phép serverless/P2P và merge offline đổi lấy metadata — làm rõ có cần offline/P2P không.
  • Edit offline? Nếu client sửa offline rồi reconnect, bạn cần rebase một queue op local lên server — một requirement lớn, không phải đồ trang trí.
  • Rich content? Text thuần vs styled text, table, ảnh, comment — model giàu hơn làm phức tạp op set và transform.
  • History/audit? Full revision history và named version đổi model persistence (giữ op log + snapshot định kỳ).

Requirements

Functional

  • Nhiều user sửa cùng document đồng thời; mọi người hội tụ.
  • Thấy cursor / presence người khác; comment.
  • Version history; offline edit sync khi reconnect.
  • Sharing và permission.

Non-functional

  • Convergence latency thấp (edit hiện ra dưới một giây).
  • Consistency: mọi client đạt cùng document state.
  • Scale concurrency mỗi document và tổng số document.

Back-of-the-envelope estimation

  • Edit rate: gõ tích cực là vài keystroke/s mỗi user; doc 10 editor là vài chục op/s — nhỏ mỗi doc, nhưng có hàng triệu doc.
  • Op size: một op (insert char tại position) nhỏ xíu (vài chục byte); op log tăng nhanh nhưng compact vào snapshot.
  • Fan-out: mỗi op broadcast tới N-1 editor khác của doc đó — giới hạn bởi editor-mỗi-doc, không phải global user.
  • Storage: snapshot + op log gần đây mỗi doc; op cũ compact đi sau một snapshot.

Worked example. Các con số giải thích vì sao kiến trúc là "một owner mỗi doc, shard theo doc." Mười người gõ là ~5 keystroke/s mỗi người ≈ 50 op/s trên document đó — chẳng là gì với một server thread. Nên bạn thừa sức route mọi op của một doc tới một server authoritative (hoặc một partition), nơi gán một revision number đơn điệu và transform mỗi op tới đến lên những op nó chưa biết. Việc serialize đó là cái bảo đảm convergence, và nó rẻ vì traffic per-doc nhỏ xíu. Scale đến từ shard document qua các server (doc_id → owner), không phải làm một doc nhanh hơn — một triệu doc active × 50 op/s là 50M op/s tổng, nhưng mỗi server chỉ xử lý các doc nó sở hữu. Storage: ở ~30 byte/op và 50 op/s, một giờ edit nặng là ~5 MB op; bạn snapshot định kỳ (vd mỗi N op) và compact, nên open = load snapshot mới nhất + replay op tail ngắn, giữ open latency bounded bất kể tuổi document.

Core APIs

  • WebSocket session: open(doc_id) → snapshot + revision hiện tại.
  • submitOps(doc_id, base_revision, ops[]) → {applied_revision}.
  • Server push: remote_ops, cursor, presence.
  • GET /docs/{id}/history → revision / snapshot.

High-level architecture

Mỗi document đang mở được sở hữu bởi một collaboration server duy nhất (shard theo doc_id) — server này serialize mọi edit của doc đó. Client nối qua WebSocket; server transform/merge op, gán revision number, persist vào op log, và broadcast.

Permissions: mọi request open, submitOps, comment, history được authorize với ACL của document (view / comment / edit) trước khi collaboration server áp dụng — một viewer không thể submit edit dù forge op.

Bài toán concurrency

Nếu A insert "X" tại position 2 trong khi B delete position 1 cùng lúc, áp dụng ngây thơ cả hai cho kết quả khác nhau trên mỗi client. Hai họ giải pháp đảm bảo convergence:

  • Operational Transformation (OT): transform op đến so với op đồng thời để nó áp đúng tại position mới. Cần một server trung tâm order op; mô hình text đơn giản về ý tưởng, khó implement đúng.
  • CRDT: cho mỗi ký tự một id duy nhất, totally-ordered để insert/delete đồng thời commute — thứ tự áp dụng không còn quan trọng. Nhiều metadata mỗi ký tự hơn, nhưng hội tụ không cần transformer trung tâm (tốt cho offline/peer-to-peer).

Per-document ordering

Thiết kế đúng đơn giản nhất: shard document sao cho một server sở hữu mỗi doc và áp edit theo một thứ tự duy nhất, gán một revision tăng đơn điệu. Client submit op so với revision cuối nó thấy; server transform với bất kỳ op nào nó đã accept ở giữa, áp dụng, và ack revision mới.

Persistence: op log cộng snapshot

Document state là snapshot cộng các op áp sau nó. Persist mọi op cho full history và crash recovery; định kỳ server ghi một snapshot và compact op cũ. Khi open, client load snapshot mới nhất rồi replay phần đuôi của op log.

Presence và offline

Cursor và selection là presence event ephemeral broadcast tới co-editor (không persist). Offline editing buffer op tại local; khi reconnect client submit chúng so với revision cuối nó biết và server transform vào — cùng cơ chế với edit online, đó chính là lý do OT/CRDT quan trọng.

Storage & technology choices

  • API gateway + WebSocket gateway: REST cho open/share/history, một WebSocket persistent cho live edit stream.
  • Op log: source of truth là một append-only op table / event store theo từng document với retention vĩnh viễn và snapshot compaction (replay theo doc + revision, giữ history). Kafka có thể mirror op như một live change stream cho fanout, nhưng không phải source of truth dài hạn (retention/replay bị giới hạn).
  • Snapshot: document state compacted định kỳ trong blob/object storage (S3-like), nên open = load snapshot + replay tail.
  • Document metadata + permission/ACL: một DB quan hệ (PostgreSQL) — có cấu trúc, transactional, authority cho sharing.
  • Presence/cursor: ephemeral → Redis (pub/sub + TTL), không persist.
  • Comment / version history: một store key theo doc + range/revision (Postgres hoặc wide-column cho doc rất active).

Vì sao chọn vậy: document live hot in-memory trên collaboration server sở hữu nó; durability là op log append-only + snapshot định kỳ (log hoàn hảo cho ordered edit stream, blob cho snapshot lớn); permission nhỏ + quan hệ → SQL; cursor vứt đi → Redis. Shard single-owner-per-doc làm routing "state của doc này ở đâu" trivial.

Consistency & guarantees

  • Strong eventual consistency (convergence): guarantee cốt lõi — mọi client đã nhận cùng tập op thì giống nhau từng byte, bất kể thứ tự. OT/CRDT làm op đồng thời commute nên có đúng một converged state.
  • Total order theo từng document: server sở hữu gán một revision đơn điệu mỗi doc; client transform op local lên thứ tự của server trước khi apply — có một sequence authoritative mỗi document.
  • Apply local optimistic + rebase: một client apply edit của mình ngay (UX mượt) và sau đó rebase lên server revision; khi reconnect offline, các op local đã queue được transform lên mọi thứ xảy ra lúc vắng.
  • History durable, replay được: một op được accept được append vào durable op log trước khi broadcast là committed, nên document luôn reconstruct được (snapshot + op tail) và version cũ restore được.
  • Permission enforce mạnh: ACL là authority — một client không có quyền edit không commit op được, check server-side, không phải ở client.

Khi nào (không) nên dùng thiết kế này

  • OT + server trung tâm khi: collaborative text real-time với vài-tới-vài chục editor và một server bạn kiểm soát — path đã được chứng minh, đơn giản hơn (Docs, đa số editor).
  • CRDT khi: bạn cần offline-first, peer-to-peer, hoặc merge serverless (app local-first) và kham được metadata mỗi element.
  • Thừa khi: document được sửa bởi một người tại một thời điểm — last-writer-wins với locking/check-out đơn giản hơn nhiều OT/CRDT.
  • Thiết kế khác khi: "collaboration" thực ra là shared state tần suất cao (một game world, một whiteboard cursor-heavy hàng trăm user) — có thể cần model replication/interest-management khác với document OT.

Pitfalls và điểm cần bàn

  • OT correctness nổi tiếng tinh vi — nhiều edge case; CRDT đánh đổi điều đó lấy metadata mỗi ký tự.
  • Single-owner hotspot: một doc hàng nghìn editor gây áp lực lên một server — cap editor hoặc partition doc lớn.
  • Snapshot cadence: quá thưa thì replay dài; quá dày thì phí storage.
  • Offline divergence: offline lâu sinh transform set lớn — giới hạn và reconcile.
  • Undo phải per-user và transform-aware, không phải revert global ngây thơ.

Key takeaways

  • Convergence cần OT (server-ordered transform) hoặc CRDT (op commute).
  • Một owner duy nhất mỗi document cho ordering sạch và revision number.
  • Op log + snapshot định kỳ cho history, recovery, và open nhanh.
  • Offline edit tái dùng cùng transform path khi reconnect.
