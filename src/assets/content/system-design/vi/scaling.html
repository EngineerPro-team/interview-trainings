Giới thiệu

Mở rộng (scale) hệ thống để phục vụ hàng triệu người dùng là một hành trình phức tạp, lặp đi lặp lại, đòi hỏi tinh chỉnh và tối ưu liên tục. Chương này trình bày cách bắt đầu từ kiến trúc một máy chủ duy nhất và mở rộng từng bước để xử lý hàng triệu người dùng.

Phần 1: Kiến trúc một máy chủ (Single Server)

Ban đầu, mọi thành phần (web app, database, cache) chạy trên cùng một máy chủ.

Luồng request

  1. Người dùng truy cập ứng dụng qua tên miền (ví dụ api.mysite.com), được DNS phân giải thành địa chỉ IP.
  2. Địa chỉ IP của web server trả về trình duyệt hoặc app mobile.
  3. HTTP request gửi tới web server; server trả về HTML hoặc JSON.

Nguồn traffic

  1. Web application: Ngôn ngữ server-side (Python, Java…) xử lý business logic; client-side (JavaScript, HTML…) phụ trách giao diện.
  2. Mobile application: Giao tiếp với web server qua HTTP và JSON — nhẹ, dễ trao đổi dữ liệu.

Phần 2: Tách database

Khi lượng người dùng tăng, database được chuyển sang máy chủ riêng để scale web tier và data tier độc lập.

Lựa chọn database

  1. Relational (SQL): Dữ liệu có cấu trúc, lưu trong bảng. Ví dụ: MySQL, PostgreSQL.
  2. Non-relational (NoSQL): Phù hợp dữ liệu phi cấu trúc hoặc yêu cầu độ trễ thấp. Các loại:
    • Key-Value Store
    • Graph Database
    • Column Store
    • Document Store

Nên cân nhắc NoSQL khi:

  • ứng dụng cần độ trễ cực thấp;
  • dữ liệu phi cấu trúc hoặc không có quan hệ;
  • chỉ cần serialize/deserialize (JSON, XML, YAML…);
  • cần lưu khối lượng dữ liệu rất lớn.

Phần 3: Scale dọc vs scale ngang

Vertical scaling (scale dọc)

  • Thêm tài nguyên (CPU, RAM) cho máy chủ hiện có.
  • Bị giới hạn phần cứng và thiếu redundancy.

Horizontal scaling (scale ngang)

  • Thêm nhiều máy chủ vào pool — phù hợp hệ thống quy mô lớn.
  • Dùng load balancer để phân phối request.

Phần 4: Load balancer

Load balancer phân phối traffic giữa nhiều server. Lợi ích:

  1. Redundancy: Một server down thì traffic chuyển sang server khác.
    • Server 1 offline → toàn bộ traffic sang server 2.
  2. Scalability: Dễ thêm server khi traffic tăng đột biến.

Phần 5: Database replication

Mô hình Master–Slave

  • Master: Xử lý ghi — mọi lệnh insert, delete, update gửi về master.
  • Slave: Xử lý đọc, cải thiện hiệu năng và độ tin cậy. Vì tỷ lệ đọc/ghi thường cao, số slave thường nhiều hơn master.

Lợi ích

  1. Hiệu năng tốt hơn nhờ đọc song song.
  2. High availability và độ tin cậy dữ liệu nhờ redundancy.

Xử lý lỗi

  • Chỉ còn một slave và nó down → tạm thời đọc từ master.
  • Nhiều slave → chuyển đọc sang replica khỏe mạnh, thay server hỏng.
  • Master down → promote một slave lên master. Slave được chọn có thể chưa đồng bộ — cần script recovery (multi-master, circular replication có thể hỗ trợ).

Phần 6: Caching

Cache lưu dữ liệu truy cập thường xuyên trong memory, giảm tải database. Cache tier là lớp lưu trữ tạm, nhanh hơn database rất nhiều.

Lưu ý khi dùng cache

  1. Use case: Dữ liệu đọc nhiều, ghi ít.
  2. Expiration: Dữ liệu hết hạn bị xóa khỏi cache. Không có policy → dữ liệu nằm trong memory vĩnh viễn.
  3. Consistency: Giữ data store và cache đồng bộ. Lệch lạc xảy ra khi ghi store và cache không trong cùng transaction.
  4. Giảm SPOF: Một cache server là single point of failure — nên dùng nhiều cache server ở nhiều data center.
  5. Eviction: Cache đầy thì cần đẩy bớt dữ liệu. LRU là policy phổ biến nhất.

Phần 7: CDN (Content Delivery Network)

CDN cải thiện thời gian tải bằng cách cache nội dung tĩnh (ảnh, CSS, JS) trên các server phân tán theo địa lý.

Luồng hoạt động

  1. User request nội dung từ CDN gần nhất.
  2. Nếu chưa có, CDN lấy từ origin server rồi cache lại.

Lưu ý

  1. Chi phí: CDN bên thứ ba tính phí transfer in/out.
  2. Cache expiry: Không quá dài cũng không quá ngắn.
  3. Fallback: CDN outage tạm thời → client phát hiện và request từ origin.
  4. Invalidate: File cập nhật → invalidate cache.

Phần 8: Web tier stateless

Chuyển session data sang datastore dùng chung → web server trở nên stateless. Cho phép:

  1. Scale ngang dễ hơn.
  2. Auto-scaling theo traffic.

Phần 9: Multi data center

Triển khai nhiều data center giúp tăng availability và giảm latency.

  1. GeoDNS routing: Định tuyến user tới data center gần nhất.
  2. Data replication: Đồng bộ dữ liệu giữa các center để tránh inconsistency.

Lưu ý chính

  • Traffic redirection: Cần công cụ định tuyến hiệu quả.
  • Data synchronization: Replicate dữ liệu giữa các data center.
  • Test & deployment: CI/CD tự động giữ dịch vụ nhất quán trên mọi center.

Phần 10: Message queue

Message queue là thành phần bền vững hỗ trợ giao tiếp bất đồng bộ — đóng vai trò buffer và phân phối request async.

  • Producer/publisher tạo message và publish vào queue.
  • Consumer/subscriber kết nối queue và xử lý theo message.

Phần 11: Logging, metrics và automation

Tầm quan trọng

  1. Logging: Theo dõi lỗi và sức khỏe hệ thống.
  2. Metrics: Insight về hiệu năng và hành vi người dùng.
  3. Automation: Tự động hóa test, deploy, scale.

Phần 12: Scale database

Vertical scaling

  • Thêm phần cứng nhưng bị giới hạn vật lý và chi phí.
  • Rủi ro single point of failure cao hơn.
  • Chi phí tổng thể cao.

Horizontal scaling (Sharding)

  • Chia dữ liệu thành nhiều shard theo key (ví dụ user_id).
  • Mỗi shard cùng schema; dữ liệu trên mỗi shard là duy nhất.
  • Chọn sharding key phân bố đều là then chốt.

Thách thức

  1. Resharding: Cần khi shard không chứa thêm được, hoặc phân bố lệch. Consistent hashing giúp giải quyết.
  2. Celebrity problem: Một shard bị truy cập quá nhiều (celebrity) → quá tải; có thể tách shard riêng.
  3. Join & de-normalization: Join cross-shard khó — thường de-normalize để query trên một bảng.

Kết luận

Điểm cần nhớ

  1. Giữ web tier stateless.
  2. Xây redundancy ở mọi tầng.
  3. Dùng cache và CDN để tối ưu hiệu năng.
  4. Scale data tier bằng sharding.
  5. Tách (decouple) các thành phần để linh hoạt.

Chương này là nền tảng vững để xây hệ thống scale được hàng triệu người dùng.
